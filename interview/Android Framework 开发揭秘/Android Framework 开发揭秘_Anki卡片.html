Android 系统启动的五大步骤分别是什么？

第一步 启动电源以及系统启动：电源按下后，引导芯片代码从固化在 ROM 的预定义位置开始执行，加载引导程序到 RAM 并执行

第三步 内核：设置缓存、被保护存储器、计划列表，加载驱动；完成后在系统文件中寻找 init 文件

第四步 init 进程：用户空间第一个进程，启动 root 进程/系统第一个进程

第五步 启动 Launcher App

第一章第一节 · Android启动概览#7
init 进程的 main() 为什么会执行两次？由什么变量控制？

init 的 main 方法会执行两次，由 is_first_stage 控制，它通过检查环境变量 INIT_SECOND_STAGE 是否存在来判断。

第一阶段结束时，init 会设置 INIT_SECOND_STAGE=true，然后用 execv 重新执行自己进入第二阶段。

之所以要重新 exec：第一遍执行时进程处在 kernel domain，SELinux policy 已加载后需要重新执行 init 文件切换到 init domain。

bool is_first_stage = (getenv("INIT_SECOND_STAGE") == nullptr);
if (is_first_stage) {
    ...
    setenv("INIT_SECOND_STAGE", "true", 1);
    char* path = argv[0];
    char* args[] = { path, nullptr };
    execv(path, args);   // 重新执行 main 方法，进入第二阶段
}
// At this point we're in the second stage of init.

init 第二阶段中 epoll 是如何被使用的？监听了哪两类 fd？

init 创建 epoll 实例并进入无限循环，通过 epoll 统一等待事件：

1epoll_fd = epoll_create1(EPOLL_CLOEXEC) 创建 epoll 实例并返回文件描述符

if (nr == -1) {
    PLOG(ERROR) << "epoll_wait failed";
} else if (nr == 1) {
    ((void (*)()) ev.data.ptr)();   // 执行注册时的回调

第一章第二节 · init.rc解析#13
init.rc 中 Service 的定义语法是什么？Service 与 init 进程是什么关系？

语法：service <name> <pathname> [<argument>]*，即 <service 的名字> <执行程序路径> <传递参数>。

Service 以 service 开头，由 init 进程启动，一般运行在 init 的一个子进程，所以启动 service 前需要判断对应的可执行文件是否存在。

init 生成的子进程定义在 rc 文件中，其中每一个 service 在启动时会通过 fork 方式生成子进程。

例如 service servicemanager /system/bin/servicemanager 表示服务名为 servicemanager，执行路径为 /system/bin/servicemanager。

第一章第二节 · init.rc解析#17
Parser::ParseData() 是如何逐 token 解析 rc 文件的？三种 token 分别怎么处理？

ParseData 用一个 for(;;) 循环调用 next_token(&state)，按 token 类型分派：

T_EOF：调用 end_section() 并返回

T_NEWLINE：一行结束。若 args[0] 在 section_parsers_ 中（如 service/on/import），先 end_section() 结束上一段，再取对应 section_parser 并调用 ParseSection()；否则若已有 section_parser，则调用 ParseLineSection() 解析该段内部的行。之后清空 args

T_TEXT：把 state.text 追加到 args

解析出错时累加 *parse_errors 并打 ERROR 日志。

switch (next_token(&state)) {
case T_EOF: end_section(); return;
case T_NEWLINE:
    if (section_parsers_.count(args[0])) {
        end_section();
        section_parser = section_parsers_[args[0]].get();
        section_parser->ParseSection(std::move(args), filename, state.line);
    } else if (section_parser) {
        section_parser->ParseLineSection(std::move(args), state.line);
    }
    args.clear();
    break;
case T_TEXT: args.emplace_back(state.text); break;
}

第一章第二节 · init.rc解析#19
rc 文件中的 class_start 命令是如何最终启动 Service 的？完整调用链是什么？

调用链：on nonencrypted 中的 class_start -> do_class_start -> Service::StartIfNotDisabled -> Service::Start。

do_class_start 遍历 ServiceList::GetInstance()，凡是 classnames() 包含目标 class 名的 service 都调用 StartIfNotDisabled()。

注意：启动一个 class 不会启动那些显式 disabled 的服务，它们必须被单独启动。

StartIfNotDisabled 判断 flags_ 是否含 SVC_DISABLED，没有则 Start()，否则只置上 SVC_DISABLED_START 标志。

# init.rc
on nonencrypted
    class_start main         // class_start 是命令，由 do_class_start 处理
    class_start late_start

static Result<Success> do_class_start(const BuiltinArguments& args) {
    for (const auto& service : ServiceList::GetInstance()) {
        if (service->classnames().count(args[1])) {
            service->StartIfNotDisabled();
        }
    }
}
第一章第二节 · init.rc解析#20
Service::Start() 的核心逻辑是什么？如何创建并执行 service 进程？

1若 flags_ 已含 SVC_RUNNING，说明服务已运行，不再启动（对已运行的服务调用 start 不算错误）；若是 SVC_ONESHOT 且 disabled 则置 SVC_RESTART

2用 stat(args_[0]) 判断需要启动的 service 对应的可执行文件是否存在，不存在则置 SVC_DISABLED 并返回错误，不启动 service

3计算 SELinux 上下文 scon（seclabel_ 或 ComputeContextFromExecutable）

4若子进程没有启动，调用 fork()（有 namespace_flags_ 时用 clone）创建子进程

5在子进程中 umask(077) 后调用 ExpandArgsAndExecv(args_)（即 execv）启动 service 子进程，失败则 _exit(127)

pid_t pid = -1;
if (namespace_flags_) {
    pid = clone(nullptr, nullptr, namespace_flags_ | SIGCHLD, nullptr);
} else {
    pid = fork();
}
if (pid == 0) {              // 当前代码逻辑在子进程中运行
    umask(077);
    if (!ExpandArgsAndExecv(args_)) {
        PLOG(ERROR) << "cannot execve('" << args_[0] << "')";
    }
    _exit(127);
}

第一章第三节 · Zygote#21
Zygote 名字的含义是什么？为什么这样命名？它最初叫什么？

Zygote 中文翻译为"受精卵"，正如其名，它主要用于孵化子进程。

所有的 Java 应用程序进程及系统服务 SystemServer 进程都由 Zygote 进程通过 Linux 的 fork() 函数孵化出来，就像一个受精卵孵化出无数子进程，这就是称它为 Zygote 的原因。

Zygote 进程最初的名字不是 "zygote" 而是 "app_process"，这个名字是在 Android.mk 文件中定义的。

第一章第三节 · Zygote#22
Android 中有哪两种程序？它们分别由谁创建启动？

两种程序：

1Java 应用程序：主要基于 ART 虚拟机，所有的应用程序 apk 都属于这类

2native 程序：利用 C 或 C++ 语言开发的程序，如 bootanimation

创建者的区别：

所有 Java 应用程序进程及系统服务 SystemServer 进程，都由 Zygote 进程通过 Linux 的 fork() 函数孵化出来

native 程序则由 Init 程序创建启动

Zygote 是 Android 中的第一个 ART 虚拟机，它通过 socket 的方式与其他进程通信，这里的"其他进程"主要是系统进程 SystemServer。

第一章第三节 · Zygote#23
Zygote 的 C/S 模型是怎样的？以点击 Launcher 图标启动应用为例说明请求流程。

Zygote 是一个 C/S 模型：

服务端（Zygote 进程）负责：创建 Java 虚拟机、加载系统资源、启动 SystemServer 进程，以及在后续运行过程中启动普通的应用程序。

客户端（其他进程）向它发出"孵化"请求，Zygote 接收后就"孵化"出一个新的进程。

启动应用的流程：

1点击 Launcher 里的应用图标

2请求到达框架层核心服务 ActivityManagerService

3AMS 通过调用 Process 类发出一个"孵化"子进程的 Socket 请求

4Zygote 监听到这个请求后立刻 fork 一个新的进程出来

第一章第三节 · Zygote#25
zygote 是在哪个 trigger 中被 start 的？该 trigger 又由谁触发？

zygote 是在 on zygote-start 中被 start 的，而 zygote-start 是在 on late-init 中触发的。

late-init 内部的 trigger 顺序为：early-fs -> fs -> post-fs -> late-fs -> post-fs-data -> zygote-start -> load_persist_props_action -> firmware_mounts_complete -> early-boot -> boot。

因为文件加密需要 keymaster 解密 /data，而它依赖系统属性，所以 zygote-start 排在 post-fs-data 之后。

而 late-init 本身由 init.cpp 中根据 ro.bootmode 判断后 QueueEventTrigger 触发。

on late-init
    trigger early-fs
    trigger fs
    trigger post-fs
    trigger late-fs
    trigger post-fs-data
    trigger zygote-start      # 在这里触发 zygote 启动
    trigger early-boot
    trigger boot
第一章第三节 · Zygote#26
app_main.cpp 的 main() 有哪两种启动模式？分别传什么参数、加载哪个 Java 类？

app_main.cpp 的 main 函数主要做参数解析，有两种启动模式：

1zygote 模式：初始化 zygote 进程，传递的参数有 --start-system-server 和 --socket-name=zygote，前者表示启动 SystemServer，后者指定 socket 的名称

Zygote 是如何监控 System Server 的？System Server 崩溃后会发生什么连锁反应？

1System Server 挂掉 -> Zygote 收到 SIGCHLD -> Zygote 自杀 -> init 会重启 Zygote

2Zygote 被杀后，系统会自动给所有子进程发送 SIGHUP 信号，该信号默认处理就是退出当前进程，所以应用程序不会变成孤儿

3但一些后台进程（Daemon）可以通过设置 SIG_IGN 参数忽略 SIGHUP，从而得以在后台继续运行

static void sigchldHandler(int s) {
    pid_t pid; int status;
    while ((pid = waitpid(-1, &status, WNOHANG)) > 0) {
        if (pid == gDvm.systemServerPid) {
            kill(getpid(), SIGKILL);
        }
    }

第一章第三节 · Zygote#41
什么是写时拷贝（copy-on-write）？Linux 的 fork() 如何使用它？

Linux 的 fork() 是通过写时拷贝（copy-on-write）实现的。写时拷贝是一种可以推迟甚至避免拷贝数据的技术。

内核在 fork 时并不复制整个进程的地址空间，而是让父子进程共享同一个地址空间；只有在需要写入的时候才会复制地址空间，从而使各个进程拥有各自的地址空间。

也就是说，资源的复制是在需要写入的时候才会进行，在此之前，只有以只读方式共享。

第一章第三节 · Zygote#42
什么是孤儿进程？什么是僵尸进程？

fork 系统调用之后，父子进程将交替执行，执行顺序不定。

孤儿进程：如果父进程先退出、子进程还没退出，那么子进程的父进程将变为 init 进程（托孤给了 init 进程）。注：任何一个进程都必须有父进程。

僵尸进程：如果子进程先退出、父进程还没退出，那么子进程必须等到父进程捕获到了子进程的退出状态才真正结束；否则这个时候子进程就成为僵尸进程（僵尸进程只保留一些退出信息供父进程查询）。

第一章第三节 · Zygote#43
POSIX 标准中多线程进程调用 fork 的行为是怎样的？为什么可能导致死锁？

在 POSIX 标准中，fork 的行为是：复制整个用户空间的数据（通常使用 copy-on-write 的策略，所以速度很快）以及所有系统对象，然后仅复制当前线程到子进程。所有父进程中别的线程，到了子进程中都是突然蒸发掉的。

死锁场景：

1在 fork 之前，有一个子线程 lock 了某个锁，获得了对锁的所有权

2fork 以后，在子进程中所有的额外线程都人间蒸发了

3而锁却被正常复制了，在子进程看来这个锁没有主人，所以没有任何人可以对它解锁

4当子进程想 lock 这个锁时，不再有任何手段可以解开了，程序发生死锁

第二章第八节 · Binder面试题全解析#96
Binder 是如何做到只有一次数据拷贝的？

这主要利用了 Linux 的虚拟内存寻址方式，它有如下特性：

1用户空间的虚拟内存地址是映射到物理内存中的。

2对虚拟内存的读写实际上是对物理内存的读写，这个过程就是内存映射。

3这个内存映射过程是通过系统调用 mmap() 来实现的。

Binder 借助内存映射的方法，在内核空间和接收方用户空间的数据缓存区之间做了一层内存映射，就相当于直接拷贝到了接收方用户空间的数据缓存区，从而减少了一次数据拷贝。

第二章第八节 · Binder面试题全解析#97
MMAP 内存映射的实现过程分为哪三个阶段？

（一）进程启动映射过程，并在虚拟地址空间中为映射创建虚拟映射区域。

（二）调用内核空间的系统调用函数 mmap（不同于用户空间函数），实现文件物理地址和进程虚拟地址的一一映射关系。

（三）进程发起对这片映射空间的访问，引发缺页异常，实现文件内容到物理内存（主存）的拷贝。

注：前两个阶段仅创建虚拟区间并完成地址映射，并没有把任何文件数据拷贝至主存，真正的文件读取发生在进程发起读或写操作时。

第二章第八节 · Binder面试题全解析#98
MMAP 第一、二阶段具体做了什么？

第一阶段：进程在用户空间调用库函数 mmap（原型 void *mmap(void *start, size_t length, int prot, int flags, int fd, off_t offset)）；在当前进程虚拟地址空间中寻找一段空闲的、满足要求的连续虚拟地址；为此虚拟区分配一个 vm_area_struct 结构并初始化各个域；把新建的 vm_area_struct 插入进程的虚拟地址区域链表或树中。

第二阶段：通过待映射的文件指针，在文件描述符表中找到对应的文件描述符，再链接到内核「已打开文件集」中该文件的文件结构体 struct file；通过文件结构体链接到 file_operations 模块，调用内核函数 int mmap(struct file *filp, struct vm_area_struct *vma)；内核 mmap 通过虚拟文件系统 inode 模块定位到文件磁盘物理地址；通过 remap_pfn_range 函数建立页表，即实现文件地址和虚拟地址区域的映射关系，此时这片虚拟地址并没有任何数据关联到主存中。

第二章第八节 · Binder面试题全解析#99
MMAP 第三阶段中缺页异常是如何被处理的？脏页面何时写回文件？

进程读写访问虚拟地址空间这段映射地址时，通过查询页表发现这段地址并不在物理页面上（只建立了地址映射，硬盘数据还没拷贝到内存），因此引发缺页异常：

1缺页异常进行一系列判断，确定无非法操作后，内核发起请求调页过程。

2调页过程先在交换缓存空间（swap cache）中寻找需要访问的内存页，如果没有则调用 nopage 函数把所缺的页从磁盘装入主存。

3之后进程即可对这片主存进行读写；如果写操作改变了内容，一定时间后系统会自动回写脏页面到对应磁盘地址，也即完成写入文件的过程。

注：修改过的脏页面不会立即更新回文件，而是有一段时间延迟，可以调用 msync() 强制同步，这样所写内容就能立即保存到文件里。

Binder 机制是如何跨进程的？

1Binder 驱动在内核空间创建一块接收缓存区，并实现地址映射：将内核缓存区、接收进程用户空间映射到同一接收缓存区。

2发送进程通过系统调用（copy_from_user）将数据发送到内核缓存区。由于内核缓存区和接收进程用户空间存在映射关系，故相当于也发送到了接收进程的用户空间，从而实现了跨进程通信。

第二章第八节 · Binder面试题全解析#101
Activity 与 Service 的通信/使用机制要点分别是什么？startService 与 bindService 有何区别？

第二章第八节 · Binder面试题全解析#103
为什么 Intent 不能传递大数据？

Intent 携带信息的大小其实是受 Binder 限制的：数据以 Parcel 对象的形式存放在 Binder 传递缓存中；如果数据或返回值比传递 buffer 大，则此次传递调用失败并抛出 TransactionTooLargeException 异常。

Binder 传递缓存有一个限定大小，通常是 1Mb，但同一个进程中所有的传输共享该缓存空间；多个地方同时传输时，即使它们各自传输的数据不超出大小限制，也可能抛出 TransactionTooLargeException。

因此使用 Intent 传递数据时 1Mb 并不是安全上限（Binder 中可能正在处理其它传输工作），不同机型和系统版本这个上限值也可能不同。

简述 Handler 机制的总体原理（三个阶段）。

1Looper 准备和开启轮循：Looper#prepare() 初始化线程独有的 Looper 以及 MessageQueue；Looper#loop() 开启死循环读取 MessageQueue 中下一个满足执行时间的 Message；尚无 Message 时调用 Native 侧 pollOnce() 进入无限等待；有 Message 但 when 未满足时，调用 pollOnce() 传入剩余时长进入有限等待。

2Message 发送、入队和出队：任意线程向 Handler 发送 Message 或 Runnable 后，Message 按 when 的先后被插入 Handler 持有的 Looper 所对应的 MessageQueue 的适当位置；若 Native 处于无限等待，则 MessageQueue 调用 Native 的 wake() 唤醒线程进入下一次循环并出队；若处于有限等待，等待指定时长后 epoll_wait 返回，继续读取并因时长满足而出队。

3Looper 处理 Message：得到 Message 后回调其 callback 属性（Runnable），或依据 target 属性（Handler）执行回调——存在 mCallback 则回调 Handler$Callback，反之回调 handleMessage()。

第三章第三节 · Handler常问面试题#129
Looper 实例存在哪里？如何保证线程独有？一个 App 又有几个 Looper／ThreadLocal／MessageQueue／Handler 实例？

Looper 实例被管理在静态属性 sThreadLocal 中。

ThreadLocal 内部通过 ThreadLocalMap 持有 Looper，key 为 ThreadLocal 实例本身，value 即为 Looper 实例。

每个 Thread 都有一个自己的 ThreadLocalMap，这样可以保证每个线程对应一个独立的 Looper 实例，进而保证 myLooper() 可以获得线程独有的 Looper。

彩蛋：一个线程只有一个 Looper 实例，一个 Looper 只对应一个 MessageQueue；一个 MessageQueue 可对应多个 Message（从静态池获取，上限 50）；一个线程可以拥有多个 Handler 实例（Handler 只是发送和执行任务逻辑的入口和出口）；ThreadLocal 实例是静态的，整个进程共用一个，每个 Looper 存放的 ThreadLocalMap 均弱引用它作为 key。

第三章第三节 · Handler常问面试题#130
如何理解 ThreadLocal 在 Handler 机制中的作用？

首先要明确它并不是用来切换线程的。

它只是为了让每个线程方便地获取自己的 Looper 实例，见 Looper#myLooper()。

后续可供 Handler 初始化时指定其所属的 Looper 线程。

也可用来做线程判断，判断自己是否是主线程。

第三章第三节 · Handler常问面试题#131
主线程的 Main Looper 和一般 Looper 有哪些异同？主线程为什么不用我们自己初始化 Looper？

区别 1：Main Looper 不可 quit。主线程需要不断读取系统消息和用户输入，是进程的入口，只可被系统直接终止，因此其 Looper 创建时设置了不可 quit 的标志；而其他线程的 Looper 则可以也必须手动 quit。

区别 2：Main Looper 实例还被静态缓存。为便于每个线程获得主线程 Looper 实例（Looper#getMainLooper()），Main Looper 还作为 sMainLooper 属性缓存到了 Looper 类中。

相同点：都是通过 Looper#prepare() 间接调用 Looper 构造函数创建的实例；都被静态实例 ThreadLocal 管理，方便每个线程获取自己的 Looper 实例。

彩蛋：App 的入口并非 MainActivity 也不是 Application，而是 ActivityThread；它为了 Application、ContentProvider、Activity 等组件的运行，必须事先启动不停接受输入的 Looper 机制，所以在 main() 最后调用 prepareMainLooper() 并 loop()，不需要也不可能由我们调用。

第三章第三节 · Handler常问面试题#132
Handler（或者说 Looper）是如何完成线程切换的？

Handler 创建时指定了其所属线程的 Looper，进而持有了 Looper 独有的 MessageQueue。

Looper#loop() 会持续读取 MessageQueue 中合适的 Message，没有 Message 时进入等待。

当向 Handler 发送 Message 或 Runnable 后，会向其持有的 MessageQueue 中插入 Message。

Message 抵达并满足条件后会唤醒 MessageQueue 所属的线程，并将 Message 返回给 Looper；Looper 接着回调 Message 所指向的 Handler Callback 或 Runnable，达到线程切换的目的。

简言之，向 Handler 发送 Message 其实是向 Handler 所属线程独有的 MessageQueue 插入 Message，而该线程独有的 Looper 又会持续读取该队列，所以发送完 Message，那个线程的 Looper 将自动响应。

第三章第三节 · Handler常问面试题#133
Looper 的 loop() 是死循环，为什么不会导致应用卡死？loop() 后面的代码为什么不该写处理逻辑？

为了让主线程持续处理用户的输入，loop() 是死循环，持续调用 MessageQueue#next() 读取合适的 Message。

但当没有 Message 的时候，会调用 pollOnce() 并通过 Linux 的 epoll 机制进入等待并释放资源；同时 eventFd 会监听 Message 抵达的写入事件并进行唤醒。

这样达到了空闲时释放资源、不卡死线程，同时能持续接收输入的目的。

loop() 后的处理无法执行：因为 loop() 是死循环，直到 quit 之前后面的代码得不到执行，所以要避免把处理放在 loop() 后面。

补充：Looper 等待时调用 Linux epoll 机制，Java 侧打印该线程状态会发现线程处于 Runnable 状态，只不过 CPU 资源被暂时释放。

第三章第三节 · Handler常问面试题#134
Looper 的等待分为哪两种？各自是如何被准确唤醒的？

MessageQueue#next() 会因为 Message 尚无或执行条件未满足产生两种等待。

无限等待：队列中没有 Message，或建立了同步屏障但尚无异步 Message 时，调用 Native 侧 pollOnce() 传入参数 -1，Linux 执行 epoll_wait() 进入无限等待；等到合适的 Message 插入后调用 Native 侧的 wake() 向唤醒 fd 写入事件，触发唤醒 MessageQueue 读取的下一次循环。

有限等待：将下一个 Message 的剩余时长作为参数交给 epoll_wait()，epoll 等待一段时间后自动返回，接着回到 MessageQueue 读取的下一次循环。

第三章第三节 · Handler常问面试题#135
Message 应该如何获取？这样设计（享元模式）有什么好处和限制？

享元设计模式：通过 Message 的静态方法 obtain() 获取，因为该方法不是无脑地 new，而是从单链表池子里获取实例，并在 recycle() 后将其放回池子。

好处在于复用 Message 实例，满足频繁使用 Message 的场景，更加高效。

限制：缓存池存在上限 50，因为没必要无限制地缓存，那本身也是一种浪费。

需要留意缓存池是静态的，也就是整个进程共用一个缓存池。

第三章第三节 · Handler常问面试题#136
MessageQueue 是如何管理 Message 的？除了 Message 它还管理什么？

MessageQueue 通过单链表管理 Message；不同于进程共用的 Message Pool，它是线程独有的。

通过 Message 的执行时刻 when 对 Message 进行排队和出队。

MessageQueue 除了管理 Message，还要管理空闲 Handler（IdleHandler）和同步屏障。

第三章第三节 · Handler常问面试题#137
Message 与 MessageQueue 在「单链表」使用上的异同？

相同点：都是通过单链表来管理 Message 实例。Message 通过 obtain() 和 recycle() 向单链表获取和插入节点；MessageQueue 通过 enqueueMessage() 和 next() 向单链表插入和获取节点。

区别：Message 的单链表是静态的，是供整个进程使用的缓存池；MessageQueue 的单链表非静态，只供其所属的 Looper 线程使用。

第三章第三节 · Handler常问面试题#138
Message 的执行时刻 when 如何管理？为什么不能准时执行？onCreate() 里发送大量 Message 会卡顿吗？

发送的 Message 都按执行时刻 when 属性的先后管理在 MessageQueue 里：延时 Message 的 when 等于调用的当前时刻加 delay；非延时 Message 的 when 等于当前时刻（delay 为 0）；插队 Message 的 when 固定为 0，便于插入队列的 head 之后。

MessageQueue 会根据读取时刻和 when 比较：when 已抵达的出队；尚未抵达的算出当前时刻与目标 when 的差值，交由 Native 等待对应时长，时间到了自动唤醒继续读取。

事实上无论哪种 Message 都不能保证在其对应的 when 时刻执行，往往都会延迟一些，因为必须等当前执行的 Message 处理完了才有机会读取队列的下一个 Message；如果队列前面还有其他 Message，延迟会更加明显。

彩蛋：onCreate() 里发送大量 Message 不会卡顿，它们只是先放入队列；onCreate/onStart/onResume 本质上是同一个 Message，等它执行完才会进入读取的下一次循环，所以即便发送 FrontOfQueue 插入队首也不会立即先执行。

第三章第三节 · Handler常问面试题#139
Handler、Message 和 Runnable 三者的关系如何理解？

作为使用 Handler 机制的入口，Handler 是发送 Message 或 Runnable 的起点。

发送的 Runnable 本质上也是 Message，只不过作为 callback 属性被持有。

Handler 作为 target 属性被持有在 Message 中，在 Message 执行条件满足的时候供 Looper 回调。

事实上 Handler 只是供 App 使用 Handler 机制的 API，实质来说 Message 是更为重要的载体。

第三章第三节 · Handler常问面试题#140
IdleHandler 是什么？有什么用途？add/remove 要成对使用吗？为什么不会死循环？queueIdle() 跑在哪个线程？

适用于期望空闲时候执行、但不影响主线程操作的任务。

系统应用：Activity destroy 回调就放在了 IdleHandler 中；ActivityThread 中 GCHandler 使用了 IdleHandler，在空闲时执行 GC 操作。

App 应用：发送一个返回 true 的 IdleHandler，在里面让某个 View 不停闪烁，这样当用户发呆时可以诱导用户点击这个 View；把某部分初始化放在 IdleHandler 里不影响 Activity 的启动。

彩蛋：add/remove 不需要成对使用，回调返回 false 也可以移除；mIdleHandlers 一直不为空也不会死循环，因为执行过之后会将计数重置为 0；不建议把启动服务搬到 IdleHandler（回调时机不可控，需搭配 remove 谨慎使用）；queueIdle() 运行在哪个线程取决于该 IdleHandler add 到的 MessageQueue 所处的线程。

第三章第三节 · Handler常问面试题#141
异步 Message 和同步屏障怎么用？原理和应用是什么？

异步 Message：设置了 isAsync 属性的 Message 实例，可以用异步 Handler 发送，也可以调用 Message#setAsynchronous() 直接设置。

同步屏障：在 MessageQueue 的某个位置放一个 target 属性为 null 的 Message，确保此后的非异步 Message 无法执行，只能执行异步 Message。

原理：当 MessageQueue 轮循 Message 时发现建立了同步屏障，会跳过其他 Message，读取下一个 async 的 Message 并执行；屏障移除之前同步 Message 都会被阻塞。

应用：比如屏幕刷新 Choreographer 就使用到了同步屏障，确保屏幕刷新事件不会因为队列负荷影响屏幕及时刷新。

注意：同步屏障的添加或移除 API 并未对外公开，App 需要使用的话需要依赖反射机制。

用「生产者-容器-消费者」概括 Looper、MessageQueue、Message、Handler 四者的角色。

Message 是承载任务的载体，在 Handler 机制中贯穿始终。

Handler 是对外公开的 API，负责发送 Message 和处理任务的回调，是 Message 的生产者。

MessageQueue 负责管理待处理 Message 的入队和出队，是 Message 的容器。

Looper 负责轮循 MessageQueue，保持线程持续运行任务，是 Message 的消费者。

第三章第三节 · Handler常问面试题#143
任何线程都可以向 MessageQueue 生产 Message，Looper 又持续消费，如何保证并发安全且不产生死锁？

Looper 在消费 Message 之前要先拿到 MessageQueue 的锁，只不过在没有 Message 或 Message 尚未满足条件而进行等待前会事先释放锁——具体在于 nativePollOnce() 的调用位于 synchronized 方法块的外侧。

Message 入队前也需先拿到 MessageQueue 的锁，而这时 Looper 线程正在等待且不持有锁，可以确保 Message 成功入队；入队后执行唤醒再释放锁。

Native 收到 event 写入后恢复 MessageQueue 的读取并可以拿到锁，成功出队。

这样一种「在没有 Message 可以消费时执行等待、同时不占着锁」的机制，避免了生产和消费的死锁。

Message next() {
    for (;;) {
        nativePollOnce(ptr, nextPollTimeoutMillis); //等待在锁外侧
        synchronized (this) { ... }
        ...
    }
}
第三章第三节 · Handler常问面试题#144
Native 侧的 NativeMessageQueue 和 Looper 各自的作用是什么？

NativeMessageQueue 负责连接 Java 侧的 MessageQueue，进行后续的 wait 和 wake：它将创建 wake 的 FD，并通过 epoll 机制等待或唤醒；但并不参与管理 Java 的 Message。

Native 侧本身也需要 Looper 机制，等待和唤醒的需求是同样的，所以把这部分实现都封装到了 JNI 的 NativeMessageQueue 和 Native 的 Looper 中，供 Java 和 Native 一起使用。

第三章第三节 · Handler常问面试题#145
Native 侧如何使用 Looper？提供了哪些 API？

Looper 的 Native 部分承担了 Java 侧 Looper 的等待和唤醒，除此之外它还提供了 Message、MessageHandler 或 WeakMessageHandler、LooperCallback 或 SimpleLooperCallback 等 API。

这些部分可供 Looper 被 Native 侧直接调用，比如 InputFlinger 就广泛使用了 Looper。

主要用法是：调用 Looper 构造函数或 prepare 创建 Looper，然后通过 poll 开始轮询，接着 sendMessage 或 addEventFd，等待 Looper 的唤醒。使用过程和 Java 的调用思路类似。

第三章第三节 · Handler常问面试题#146
Handler 为什么可能导致内存泄露？如何避免？网传的 Handler$Callback 方案能解决吗？

持有 Activity 实例的匿名内部类或内部类，其生命周期应当和 Activity 保持一致，否则有内存泄露风险；Handler 使用不当会造成不一致，表现为：匿名内部类/内部类写法的 Handler、Handler$Callback、Runnable，或者 Activity 结束时仍有活跃的 Thread 线程或 Looper 子线程。

具体在于：异步任务仍然活跃或发送的 Message 尚未处理完毕，会使内部类实例的生命周期被错误地延长，造成本该回收的 Activity 实例被别的 Thread 或 Main Looper 占据而无法及时回收（活跃的 Thread 或静态属性 sMainLooper 是 GC Root 对象）。

注意：静态的 sThreadLocal 实例不持有存放 Looper 的 ThreadLocalMap，而是由 Thread 持有；从这个角度讲，Looper 会被活跃的 GC Root Thread 持有，进而也可能导致内存泄露。

建议做法：Handler、Handler$Callback、Runnable 尽量采用静态内部类 + 弱引用写法；并在 Activity 销毁时及时终止 Thread、停止子线程 Looper 或清空 Message，彻底切断 Activity 经由 Message 抵达 GC Root 的引用源头。

网传的 Handler$Callback 方案不能解决：内部类写法的 Callback 默认持有 Activity，而 Callback 被 Handler 持有，Message -> Handler -> Callback -> Activity 的链条仍然存在。

应用特别广泛，比如：Activity 生命周期的管理、屏幕刷新、HandlerThread、IntentService、AsyncTask 等。

主要利用 Handler 的切换线程、主线程异步 Message 的重要特性。

system server、media server 以及上层 App 之间更多采用 Binder IPC 方式完成跨进程通信。

第四章第三节 · 通信方式#158
Linux 现有的 6 种 IPC 机制各有什么局限或适用场景？

管道：在创建时分配一个 page 大小的内存，缓存区大小比较有限。

消息队列：信息复制两次，额外的 CPU 消耗；不合适频繁或信息量大的通信。

共享内存：无须复制，共享缓冲区直接附加到进程虚拟地址空间，速度快；但进程间的同步问题操作系统无法实现，必须各进程利用同步工具解决。

套接字：作为更通用的接口，传输效率低，主要用于不同机器或跨网络的通信。

信号量：常作为一种锁机制，防止某进程访问共享资源时其他进程也访问该资源；主要作为进程间以及同一进程内不同线程之间的同步手段。

信号：不适用于信息交换，更适用于进程中断控制，比如非法内存访问、杀死某个进程等。

第四章第三节 · 通信方式#159
从性能和稳定性两个角度看，为什么 Android 选择 Binder 作为 IPC 机制？

性能角度(数据拷贝次数)：Binder 数据拷贝只需要一次，而管道、消息队列、Socket 都需要 2 次，但共享内存一次内存拷贝都不需要。

所以从性能角度看，Binder 性能仅次于共享内存。

稳定性角度：Binder 是基于 C/S 架构的，C/S 相对独立，稳定性较好。

而共享内存实现方式复杂，没有客户与服务端之别，需要充分考虑到访问临界资源的并发同步问题，否则可能会出现死锁等问题。

第四章第三节 · 通信方式#160
从安全角度看，Binder 相比传统 Linux IPC 的优势是什么？

传统 Linux IPC 的接收方无法获得对方进程可靠的 UID/PID，从而无法鉴别对方身份：传统 IPC 只能由用户在数据包里填入 UID/PID，而可靠的身份标记只有由 IPC 机制本身在内核中添加；传统 IPC 访问接入点是开放的，无法建立私有通道。

Android 为每个安装好的应用程序分配了自己的 UID，进程的 UID 是鉴别进程身份的重要标志。

C/S 架构下 Android 系统中对外只暴露 Client 端，Client 端将任务发送给 Server 端，Server 端会根据权限控制策略判断 UID/PID 是否满足访问权限；目前权限控制很多时候是通过弹出权限询问对话框让用户选择。

第四章第三节 · 通信方式#161
从语言层面和公司战略角度，如何解释 Android 采用 Binder？

语言层面：Linux 是基于 C 语言(面向过程的语言)，而 Android 是基于 Java 语言(面向对象的语言)，Binder 恰恰也符合面向对象的思想。

Binder 模糊了进程边界，淡化了进程间通信过程，整个系统仿佛运行于同一个面向对象的程序之中。

公司战略：Linux 内核受 GPL 保护，GPL 具有“病毒式感染”的能力，一旦 SysCall 调用到底层 Kernel，上层也必须遵循 GPL。

Google 巧妙地将 GPL 协议控制在内核空间，用户空间采用 Apache-2.0 协议(允许基于 Android 的开发商不向社区反馈源码)。

同时在 GPL 与 Apache-2.0 之间的 Lib 库中采用 BSD 授权方法，有效隔断了 GPL 的传染性，让 GPL 止步于内核空间，这是 Google 在 GPL Linux 下开源与商业化共存的一个成功典范。

IInterface：也是一个 Base 接口，用来表示 Server 提供了哪些能力，是 Client 和 Server 通信的协议，Client 和 Server 都要实现此接口。

Binder：IBinder 的子类，Java 层提供服务的 Server 进程持有一个 Binder 对象从而完成跨进程间通信。

BinderProxy：在 Binder.java 这个文件中定义，表示 Binder 代理对象，它同样实现了 IBinder 接口；Client 中拿到的实际上是这个代理对象。

手写简化版 AMS 的前两步分别是什么？asInterface() 的逻辑是怎样的？

第一步：定义 IActivityManager 接口(继承 IInterface)，含 binder 描述符 DESCRIPTOR、方法编号 TRANSACTION_startActivity，并声明一个启动 activity 的方法(为了简化只传入 intent 参数)。

第二步：实现 ActivityManagerService 侧的本地 Binder 对象基类 ActivityManagerNative extends Binder implements IActivityManager。

asInterface(IBinder obj)：先用 obj.queryLocalInterface(DESCRIPTOR) 判断，若拿到本地对象则直接返回；否则返回 new ActivityManagerProxy(obj) 代理对象。

asBinder() 返回 this。

public interface IActivityManager extends IInterface {
    String DESCRIPTOR = "android.app.IActivityManager";
    int startActivity(Intent intent) throws RemoteException;
}
public abstract class ActivityManagerNative extends Binder implements IActivityManager {
    public static IActivityManager asInterface(IBinder obj) {
        IActivityManager in = (IActivityManager) obj.queryLocalInterface(DESCRIPTOR);
        return (in != null) ? in : new ActivityManagerProxy(obj);
    }
}

什么是 Activity 窗口的内容区域（Content Region）/内容边衬（Content Insets）和可见区域（Visible Region）/可见边衬（Visible Insets）？WMS 最终要算出哪三个数据？

1从 Activity 窗口剔除掉状态栏所占用的区域之后所得到的区域就是内容区域；假设窗口四周都有一块类似状态栏的区域，剔除后中间的那块是内容区域，被剔除出来的区域组成内容边衬区域，用四元组（content-left, content-top, content-right, content-bottom）描述内容区域与窗口区域的左右上下边界距离。

2从 Activity 窗口剔除掉状态栏和输入法窗口所占用的区域之后所得到的区域是可见区域；被剔除出来的区域组成可见边衬区域，用（visible-left, visible-top, visible-right, visible-bottom）描述。

3大多数情况下内容区域和可见区域的大小是一致的；状态栏和输入法窗口所占用的区域又称为屏幕装饰区。

4WMS 实际上就是要根据屏幕以及可能出现的状态栏、输入法窗口的大小，算出 Activity 窗口的整体大小、内容区域边衬大小和可见区域边衬大小这三个数据，之后 Activity 窗口才能对 UI 元素进行测量、布局和绘制。

关于 WMS 组织窗口的方式，可以得到哪五点结论？

        mWindows.add(pos, win);

moveInputMethodDialogsLocked(pos) 中参数 pos 的含义是什么？两种情况如何处理？

1调用前必须保证输入法窗口已被移动到窗口堆栈的正确位置；pos 描述的或者是输入法窗口在窗口堆栈中的位置，或者是输入法对话框在窗口堆栈中的起始位置；pos 也可以小于 0，表示系统当前没有需要显示输入法窗口的窗口。

5情况二 pos < 0：系统当前不存在需要显示输入法窗口的窗口，就根据对话框自身属性调用 reAddWindowToListInOrderLocked 把它们放到窗口堆栈的合适位置，并把每个 mTargetAppToken 设置为 null（表示没有目标窗口）。

WallpaperX/WallpaperY、WallpaperXStep/WallpaperYStep、XOffset/YOffset 分别表示什么？偏移绝对值如何计算？

1壁纸窗口的大小可以大于屏幕大小，这时需要显示壁纸的窗口要指定壁纸在 X/Y 轴上的偏移位置，以便把壁纸的某一部分作为窗口背景。

2WallpaperX、WallpaperY 是取值 0.0~1.0 的偏移比例：都为 0.0 取壁纸左上角区域，都为 0.5 取中间区域，都为 1.0 取右下角区域。

3偏移绝对值：XOffset =（WallpaperWidth - DisplayWidth）* WallpaperX，YOffset =（WallpaperHeight - DisplayHeight）* WallpaperY。

4WallpaperXStep/WallpaperYStep 描述壁纸窗口跨越了多少个虚拟屏幕：若窗口在 X 轴有 N 个、Y 轴有 M 个虚拟屏幕，则分别设置为 1.0/(N-1) 和 1.0/(M-1)。WMS 并不关心 Step 值，它只关心 WallpaperX/Y；Step 值是传递给提供壁纸的服务的，让它知道有多少个虚拟屏幕。

5这六个状态对应 WindowState 的 mWallpaperX、mWallpaperY、mWallpaperXStep、mWallpaperYStep、mXOffset、mYOffset；WMS 另用 mLastWallpaperX、mLastWallpaperY、mLastWallpaperXStep、mLastWallpaperYStep 记录壁纸窗口上一次使用的值。

6设置流程：Activity 调 WallpaperManager.setWallpaperOffsetSteps 与 setWallpaperOffsets -> Session.setWallpaperPosition -> WMS.setWindowWallpaperPositionLocked（仅当 x、y 与上次不同才保存四个值） -> updateWallpaperOffsetLocked 计算 XOffset/YOffset -> BaseIWindow.dispatchWallpaperOffsets -> Engine.doOffsetsChanged -> Engine.onOffsetsChanged（一般由子类重写实现自己的壁纸效果）。

7两参数版 updateWallpaperOffsetLocked 先把 mWallpaperTarget（或 changingTarget，当目标窗口的值小于 0 时）的 mWallpaperX/mWallpaperY 记录到 mLastWallpaperX/mLastWallpaperY，再遍历 mWallpaperTokens 中每个壁纸窗口调用四参数版本；有变化时调用 computeShownFrameLocked。

第五章第五节 · 壁纸窗口管理#217

第五章第八节 · 窗口切换 App Transition#241

第五章第八节 · 窗口切换 App Transition#243
performLayoutAndPlaceSurfacesLockedInner 的 9 个步骤是什么？循环和事务上有哪些限制？

1计算各窗口大小（performLayoutLockedInner），以便各窗口布局自己的 UI 元素；2. 计算各窗口接下来要执行的动画；3. 执行各窗口的动画；4. 检查 mAppTransitionReady 是否为 true，若是则执行 Activity 切换操作（实际就是给参与切换的 Activity 应用一个切换动画）；5. 更新各窗口的绘图表面；6. 销毁需要销毁的绘图表面；7. 删除正在退出的 WindowToken；8. 删除正在退出的 AppWindowToken；9. 检查是否需要再次刷新系统 UI。

2第 1～4 步放在一个 do...while(changes != 0) 循环里，因为第 2～4 步会导致窗口堆栈或布局变化；该循环最多执行 7 次，且只有前 4 次才重新计算窗口大小。

3第 1～5 步在 Surface.openTransaction 与 Surface.closeTransaction 之间执行，只有 closeTransaction 之后 SurfaceFlinger 才会把 UI 渲染到帧缓冲区，前面的修改只反映在图形缓冲区中。

4第 9 步：窗口堆栈/布局变化时 needRelayout 为 true，以 0 为参数调用 requestAnimationLocked 马上刷新；若只是动画未结束（animating 为 true），则以约 1000/60 为参数调用，即以 60fps 显示动画。

第五章第八节 · 窗口切换 App Transition#247

3正在关闭的：之后把 waitingToHide 置为 false，并强制把 allDrawn 置为 true——不管它是否已绘制完成，都要让前面设置的动画得以执行。

第五章第九节 · 窗口动画原理#248
一个窗口在打开（关闭）过程中可能被设置哪三个动画？窗口动画的本质是什么？

1窗口本身设置的进入（退出）动画：Self Transformation。

2从被附加窗口传递过来的动画：Attached Transformation。

3宿主 Activity 组件传递过来的切换动画：App Transformation。

4窗口动画的本质就是对原始窗口施加一个变换（Transformation）；在线性数学中，变换物体形状是通过乘以一个矩阵实现的，用于偏移、旋转、缩放、切变、反射和投影，所以给窗口设置动画实际上就是给窗口设置一个变换矩阵。

5这三个 Transformation 组合成一个变换矩阵，以 60fps 的速度应用在窗口的原始形状之上，完成动画过程；因此显示动画前还必须先算好窗口的原始位置和大小并布局绘制好 UI。

第五章第九节 · 窗口动画原理#249
三个参数版本的 applyAnimationLocked(win, transit, isEntrance) 是如何为窗口创建动画的？

1若 win.mLocalAnimating 为 true 且 mAnimationIsEntrance 等于 isEntrance，说明正在显示的就是所要求的同类动画，直接返回 true，不重新设置。

2只有屏幕未冻结（mDisplayFrozen 为 false）且屏幕点亮（mPolicy.isScreenOn() 为 true）时才真正创建动画，否则设置了也无法显示。

3先问窗口管理策略：anim = mPolicy.selectAnimationLw(win, transit)；若 anim != 0 就用 AnimationUtils.loadAnimation 创建动画。

4否则把 transit 转换为对应的动画样式属性——TRANSIT_ENTER→windowEnterAnimation、TRANSIT_EXIT→windowExitAnimation、TRANSIT_SHOW→windowShowAnimation、TRANSIT_HIDE→windowHideAnimation，再用 loadAnimation(win.mAttrs, attr) 从窗口布局参数中创建。

5若创建成功则调用 win.setAnimation(a)（把 Animation 保存在 WindowState.mAnimation 中），并把 isEntrance 记录到 mAnimationIsEntrance；返回值为 win.mAnimation != null。

6进入动画的入口是 applyEnterAnimationLocked：若 mEnterAnimationPending 为 true 则用 TRANSIT_ENTER（并清除该标志），否则用 TRANSIT_SHOW；退出动画在 relayoutWindow 中以 TRANSIT_EXIT 设置。

第五章第九节 · 窗口动画原理#250
setTokenVisibilityLocked 是如何给 Activity 及其窗口设置动画的？runningAppAnimation 的作用是什么？

1先判断 wtoken.hidden 是否等于 visible：不相等说明当前可见性已经就是要设置的可见性，就不用再设置切换动画。

2若 transit 是有效类型（不等于 TRANSIT_UNSET）：先判断 wtoken.animation 是否就是 sDummyAnimation（哑动画），若是则置为 null，因为要重新设置一个新的动画；然后调用四个参数版本的 applyAnimationLocked(wtoken, lp, transit, visible) 创建切换动画；若创建成功（animation != null），把 delayed 和 runningAppAnimation 都置为 true。

3runningAppAnimation 为 true 意味着该 Activity 的窗口接下来要执行切换动画，此时就不必再为这些窗口单独设置进入/退出动画。

4否则遍历 wtoken.allAppWindows：窗口当前不可见（isVisibleNow() 为 false）而 visible 为 true，用 TRANSIT_ENTER 设置动画；窗口当前可见而 visible 为 false，用 TRANSIT_EXIT 设置动画。

5返回值 delayed 为 true 表示该 Activity 要执行切换动画，其窗口要延迟到切换动画结束后才真正显示出来。

在推进窗口动画的过程中为什么要调用 beginAnimationLw、animatingWindowLw 和 finishAnimationLw？

1这三个是 mPolicy（PhoneWindowManager）的成员函数：计算所有窗口下一步动画之前调用 beginAnimationLw，每计算完一个窗口调用 animatingWindowLw，全部计算完成后调用 finishAnimationLw。

4如果状态栏或锁屏窗口的可见性发生了变化，finishAnimationLw 的返回值就不等于 0，说明窗口堆栈发生变化，需要重新布局，这也是第一、二、三步要放在一个循环中执行的原因；该循环最多 7 次，窗口大小位置最多重复计算 4 次。

    readPermissionsFromXml(f, permissionFlag);
}

第六章第七节 · PMS之权限扫描#292
readPermissionsFromXml() 解析 group 和 permission 标签时分别做了什么？

group 标签：取 gid 属性，通过 android.os.Process.getGidForName(gidStr) 把 gid 字符串转换为整型，保存到 mGlobalGids 中（appendInt）

permission 标签：取 name 属性，perm.intern() 后调用 readPermission(parser, perm) 处理，存入 mPermissions

如果 name/gid 为空则打印警告并 XmlUtils.skipCurrentTag(parser)

    if (gidStr != null) {
        int gid = android.os.Process.getGidForName(gidStr);
        mGlobalGids = appendInt(mGlobalGids, gid);
    }
} break;
case "permission": {
    String perm = parser.getAttributeValue(null, "name");
    perm = perm.intern();

} break;

platform.xml 中的各类标签含义分别是什么？

<group>：根据 name 获取 gid

<permission>：把属性 name 描述的权限赋予 <group> 中 gid 表示的用户组，一个权限可有一个或多个 group，APK 被授权时同时属于这几个组

<assign-permission>：把 name 描述的权限赋予 uid 属性所表示的用户

<split-permission>：一个权限可以扩展出一个新的权限

<library>：除 framework 中动态库以外，所有系统会自动加载的动态库

<feature>：硬件支持的一些 feature

<oem-permission>：oem 厂商自己定义的一些权限

<privapp-permission>：来自 system、vendor、product、system_ext 的 privapp 权限分别存储，防止供应商分区 xml 授权系统分区私有应用权限
