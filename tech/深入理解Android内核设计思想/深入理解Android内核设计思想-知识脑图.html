第1章Android系统简介

从2008年Android 1.0发布至今，Android已走过十余年发展历程。本章以发展史为主线，为后续原理分析提供背景知识。截至Google I/O 2016大会，全球激活设备已达9亿，Play商店收录超70万应用，安装量达480亿次。

Android发展简史与生态现状
2008年9月Google发布Android 1.0，凭借开放联盟和Linux内核迅速与iOS、Windows Phone形成三足鼎立，渗透至手机、平板、电视、MP4等各类电子设备。
Android的独特魅力来源
从系统架构演进、生态圈建设、开放合作联盟（OHA）三个维度探讨Android"势不可当"的原因，为后续原理分析铺垫背景。

第3章Android编译系统

"庖丁解牛"式还原庞大而严谨的Android编译系统。Makefile提供了一种"规则"执行机制，从最简单的GNU make规则不断扩展堆叠，最终形成可编译整个Android工程的庞大体系。

Makefile基础规则
TARGET: PREREQUISITES + COMMANDS，每个COMMAND前必须有TAB。理解TARGET、PREREQUISITES、COMMANDS三要素及其依赖推导逻辑。
高级Makefile特性
  • Target-Specific Variable：目标私有变量，如PRIVATE_DEX_FILE，解决依赖构建中变量值漂移问题
  • Static Pattern Rules：静态模式规则，多目标场景下统一处理依赖关系
  • 隐含规则：自动推导简化依赖编写
  • 变量与函数：避免重复输入，构建灵活脚本
Android编译系统全景
从Android.mk到Android.bp（Soong），从Makefile到Blueprint/Ninja的演进路径，剖析大型工程编译系统的设计哲学。

第4章操作系统基础

硬件是软件的基石。本章为后续Android原理分析提供扎实的理论根基，从计算机体系结构到操作系统核心概念一应俱全。

计算机体系结构
  • 冯·诺依曼结构：二进制 + 程序存储思想，运算器/控制器/输入输出设备
  • 哈佛结构：指令与数据分开存储，可并行访问，吞吐量更高，ARM9/ARM11/AVR等采用
  • 计算机基本元素：CPU、内存储器、I/O设备
操作系统核心定义
"负责管理系统硬件，并为上层应用提供稳定编程接口和人机交互界面的软件集合"。两大重任：面向下层管理硬件、面向上层提供API与UI。
操作系统分类

按应用领域

桌面型 / 服务器型 / 嵌入式

按实时性

RTOS（实时） / 分时系统

按源码开放

开源（Linux/Android） / 闭源（Windows）

按POSIX兼容

兼容 / 不兼容或不完全兼容

Android为何选择Linux Kernel
Patrick Brady在2008年Google I/O《Android Anatomy and Physiology》中指出：优秀的内存与进程管理、基于权限的安全模型、成熟的驱动模型、对共享库的支持、已是开源项目。

第5章Android进程/线程和程序内存优化

通过4个递进实验：Activity工程、Service工程、同包多组件、同包同进程，揭示四大组件与进程的真实关系。主线程由ZygoteInit启动，最终执行ActivityThread.main()。

进程与线程基本概念
进程是程序运行实例，线程是CPU调度基本单位。多任务分时执行，时间片调度让用户感觉"同时"运行。
四大组件与进程的关系
Activity/Service等组件只是application的"零件"，并非完整进程实例。一个简单的Activity工程就启动了包括main thread + 2个Binder Thread在内的多线程。
主线程ActivityThread.main()
  • 由ZygoteInit启动，经一系列调用执行onCreate()
  • Looper.prepareMainLooper()：仅主线程可调用
  • Looper.loop()：主循环开始，处理消息队列
  • 主线程Handler用于UI消息处理
程序内存优化策略
避免内存泄露、合理使用对象池、关注Bitmap内存占用、减少不必要对象创建、采用弱引用等机制。

第6章进程间通信——Binder

Binder是Android中使用最广泛的IPC机制。它既是"捆绑者"也是"黏合剂"，让Android系统中形形色色的进程与组件统一成有机整体。与TCP/IP网络惊人相似：Binder驱动≈路由器、Service Manager≈DNS、Binder Client/Server≈客户端/服务器。

智能指针（Smart Pointer）
  • 设计动机：解决C/C++中指针未初始化、new/delete不配对、野指针三大顽疾
  • 核心机制：引用计数（Reference Counting）
  • 轻量级指针sp<T>：在生命周期内自动管理
  • 强指针wp<T>：弱引用，需promote后才能使用
  • 引用计数控制类：RefBase提供onFirstRef/onLastStrongRef等生命周期回调
Binder驱动与协议
  • 注册为misc device，主设备号10，通过/dev/binder节点访问
  • 使用device_initcall(binder_init)而非module_init
  • 提供6个核心接口：open/ioctl/mmap/poll/flush/release
  • binder_open：分配binder_proc结构体，记录进程信息
  • binder_mmap：内核虚拟地址与用户虚拟地址映射，数据零拷贝
  • binder_ioctl：核心命令处理（BINDER_WRITE_READ等）
Service Manager
Binder中的"DNS"，全局唯一标志为0。管理Binder实体与名字的映射，提供查询服务，所有Server必须先向ServiceManager注册才能被Client找到。
Binder Client与Server通信
  • Client通过ServiceManager查询获得Server的Binder句柄
  • 通过ioctl(BINDER_WRITE_READ)发起跨进程调用
  • 数据经Binder驱动路由到目标进程
  • Server进程中的Binder线程负责处理请求
  • 返回值通过相同路径回传给Client

第7章Android启动过程

Android设备的启动经历3个阶段：Boot Loader、Linux Kernel、Android系统服务。Android实际是运行于Linux内核之上的一系列"服务进程"，它们的"老祖宗"是init进程（PID=0）。

第一个系统进程init
通过解析init.rc脚本来构建系统初始运行状态。其他Android服务大多在rc脚本中描述并被相继启动。init.rc采用纯文本格式，可读性高，是厂商控制启动状态的关键。
init.rc语法规则
  • Action（动作）：on <trigger> + 多个command
  • Command（命令）：class_start、mount、setprop、chmod、mkdir、symlink等
  • Service（服务）：service <name> <path> + 多个option
  • Options（选项）：class、user、group、critical、onrestart等
  • 常用触发事件：boot、<name>=<value>、device-added/removed、service-exited
Android启动流程
BootLoader → Kernel → init进程 → Zygote（孵化器）→ SystemServer（核心服务）→ Launcher（桌面）。Zygote通过fork方式快速创建应用进程，大幅提升启动效率。

第8章ActivityManagerService（AMS）

AMS是Android用于管理Activity和其他组件运行状态的系统进程，是编写APK时使用最频繁的系统服务。从功能概述到ActivityStack、ActivityTask的核心实现，层层深入。

AMS功能概述
统一管理与Activity、Service、BroadcastReceiver、ContentProvider相关的进程、任务栈、内存、权限等，是整个应用层的"调度中心"。
ActivityStack（Activity栈）
Activity的记录者与管理者。维护Activity任务栈、生命周期调度、状态保存恢复、Task关联等。理解ActivityStack是理解Activity启动模式（standard/singleTop/singleTask/singleInstance）的基础。
ActivityTask（任务）
Task是Android应用程序中的逻辑容器。一个Task可包含多个Activity，来自不同应用，体现"任务"概念。涉及Activity affinity、Intent flag、launch mode等复杂逻辑。
AMS的进程管理
维护LRU进程列表、根据优先级回收内存、LowMemory Killer机制、OomAdj调整等核心调度能力。

第9章GUI系统——SurfaceFlinger

GUI即图形用户界面。评判GUI系统优劣的三个核心条件：流畅性（Project Butter）、友好性、可扩展性。Android的GUI系统基于OpenGL/EGL实现。

GUI系统基础
图形用户界面的三大评判准则：流畅性（避免画面滞后）、友好性（人性化与一致性）、可扩展性（支持无限创意）。
SurfaceFlinger核心职责
  • 合成多个Layer：接收各应用Surface，进行混合（Composition）
  • 投递到显示设备：通过OpenGL/EGL/HWComposer输出
  • VSync同步：配合Project Butter保证画面流畅（Choreographer机制）
  • BufferQueue管理：GraphicBuffer跨进程传递
Surface与Layer
每个窗口对应一个Surface，SurfaceFlinger内部以Layer管理。Surface本质是生产者-消费者模型的BufferQueue。

第10章GUI系统之"窗口管理员"——WMS

"Window"+"Manager"=窗口管理员。WMS既负责"输出"——全局窗口管理，也负责"输入"——事件管理与派发，是SurfaceFlinger(ViewRoot/WMS三者中的"导演"角色。

WMS与SurfaceFlinger、ViewRoot的协作
SurfaceFlinger=摄像机、WMS=导演、ViewRoot=演员个体。三者各司其职，呈现"视觉盛宴"：SurfaceFlinger负责客观捕获与呈现，WMS负责编排与排序，ViewRoot负责自身展现。
WMS的输出功能——窗口管理
管理WindowState（窗口状态对象），维护窗口层级（Z-Order）、位置、尺寸、可见性等属性。处理窗口添加、删除、调整、焦点切换等请求。
WMS的输入功能——事件派发
管理多种事件源：键盘、触摸屏、鼠标、轨迹球等。通过InputManagerService将事件派发给目标窗口。
Window的多种视角

用户视角

一个"界面"（如拨号面板）

SurfaceFlinger视角

一个Layer，承载界面数据和属性

WMS视角

一个WindowState，用于管理状态

第11章让你的界面炫彩起来的GUI系统——View体系

真正与终端用户产生直接联系的部分。几乎所有APK应用的UI界面都由View体系描述。理解View体系是从"应用层"角度理解Android GUI的关键。

View树结构
ViewGroup作为容器，View作为叶子节点。整个UI界面构成一棵View树，遍历和测量机制（如measure/layout/draw三阶段）都基于此结构。
ViewRoot与Window连接
ViewRoot是View树与WMS/SurfaceFlinger之间的桥梁。负责UI渲染、事件分发根节点、Traversal调度等核心工作。
事件分发机制
MotionEvent从Activity → Window → DecorView → ViewGroup → View的传递链，涉及dispatchTouchEvent、onInterceptTouchEvent、onTouchEvent等关键方法。
自定义View
onMeasure（测量）、onLayout（布局）、onDraw（绘制）三方法是自定义View的核心。理解MeasureSpec、ViewGroup.LayoutParams等概念。

第12章InputManagerService与输入事件

"问渠哪得清如许，为有源头活水来"——事件就是Android系统的"活水源头"。Android具备从Linux内核到上层应用的完整事件产生、投递及处理机制。

IMS的架构与职责
InputManagerService（IMS）作为系统服务，运行在SystemServer进程中。负责从EventHub读取输入事件，分发给对应的窗口。
事件处理流程

1. 事件读取

EventHub监听/dev/input设备节点

2. 事件封装

RawEvent → KeyEvent/MotionEvent

3. 事件分发

通过InputChannel跨进程传递

4. 事件消费

由目标View消费或继续派发

应用层消息处理
Handler-Looper-MessageQueue机制构成应用层消息循环。Choreographer配合VSync实现60fps流畅渲染。理解消息处理是掌握Android异步编程的基础。

第13章应用不再同质化——音频系统

多媒体（Multi-Media）是多种形式媒体内容的组合，是产品在"同质化"市场中脱颖而出的关键。本章以音频回放为重点，自下而上分析整个音频系统。

音频基础知识
采样率、位深、声道数、编码格式等核心概念。理解音频处理的目标是正确还原/录制声音信号，并保证时序同步。
三大核心模块

AudioFlinger

系统服务，驻留mediaserver进程，负责音频混音、路由到设备

AudioPolicyService

系统服务，负责音频策略管理（音量、设备选择、流的优先级）

AudioTrack/AudioRecorder

应用层API，实现音频回放和录制

音频数据流核心问题
  • 路径规划：AudioPolicy正确规划音频流路径，处理混音与设备选择
  • 速度控制：保证音频流以合理速度传输到音频设备
  • 跨进程数据传递：从MediaPlayer创建到真正回放涉及多进程通信
音频系统上层建筑
MediaPlayer和MediaRecorder是应用开发中最常用的多媒体API。理解其背后的AudioFlinger/AudioPolicyService实现，对于性能调优、问题排查至关重要。

第14章Intent的匹配规则

如果说Binder是程序间的"沟通媒介"，那么Intent就是系统判断需要在哪两个进程间建立Binder关联的重要考量因素。本章借"婚介所"类比，详细解释Intent匹配过程。

Intent的组成
  • Component name：目标组件的完整类名（显式Intent）
  • Action：要执行的动作（如ACTION_VIEW）
  • Data：URI和MIME类型数据
  • Category：类别信息（如CATEGORY_LAUNCHER）
  • Extras：附加键值对数据
  • Flags：启动标志位
Intent匹配算法
系统在PackageManagerService中查询符合Intent条件的组件。匹配规则包括Action匹配、Category匹配、Data匹配（含MIME和URI scheme/host/path等）。多个匹配项时弹出选择器由用户决定。
显式Intent vs 隐式Intent

显式Intent

明确指定Component name，直接启动目标组件，效率高

隐式Intent

通过action/category/data描述意图，由系统匹配目标，灵活

第15章APK应用程序的资源适配

Android设备种类繁多、硬件配置五花八门，特别是层出不穷的屏幕分辨率和尺寸，对应用UI影响巨大。本章结合Android的通用适配方案，学习在项目开发初期控制适配问题。

设备资源适配的通用流程

1. 未知设备

应用发布后运行在什么配置设备上是未知数

2. 提取设备参数

屏幕尺寸、密度、系统语言、系统版本等

3. 资源池

应用程序提供的"可选资源"集合

4. 最佳匹配

通过匹配算法从资源池遴选最合适资源

资源限定符体系
  • 屏幕尺寸：small/normal/large/xlarge
  • 屏幕密度：ldpi/mdpi/hdpi/xhdpi/xxhdpi/xxxhdpi
  • 方向：land/port
  • 语言区域：en/zh-rCN/ja等
  • API Level：v21、v23等
最佳匹配规则
Android采用一套优先级匹配算法，依次按配置限定符筛选，最终选出最匹配设备配置的资源。理解该算法是处理复杂适配场景的前提。

第16章Android字符编码格式

字符编码问题是让不少工程师头痛的"乱码"问题，特别是产品涉及国际化时。本章从字符串编码基础入手，过渡到Android项目的实际解决方案。

字符编码基础
ASCII、ISO-8859-1、GBK/GB2312、Unicode、UTF-8/UTF-16等编码格式的发展历史与特点。理解字符集与字符编码的区别。
Java中的字符串处理
Java的String内部使用UTF-16编码，InputStreamReader/OutputStreamWriter进行字节流与字符流转换，Charset类管理各种字符集。
Android中的字符编码实践
XML资源的UTF-8编码、网络数据编解码、文件I/O、本地化字符串资源（res/values-zh-rCN等）的处理策略。

第17章Android和OpenGL ES

Surface、SurfaceFlinger、View体系都直接或间接以OpenGL ES为设计核心。本章引导学习与Android设计相关的OpenGL ES知识，揭开GUI底层图形库的奥秘。

OpenGL与Khronos组织
OpenGL最初由SGI开发，现由Khronos组织管理。下设OpenGL SC、OpenKODE、OpenGL ES、EGL、OpenGL VG、OpenML、WebGL、Vision等多个工作组。
OpenGL ES版本演进

ES 1.0/1.1

Fixed function hardware，Android 1.0开始支持

ES 2.0

Programmable hardware，支持可编程着色器，Android 2.2开始

更多新特性：统一纹理压缩、几何体实例化等，Android 4.3开始

第18章"系统的UI"——SystemUI

SystemUI以应用程序（标准APK）形式提供系统UI界面的统一管理方案，需要同时支持Phone和Tablet两类产品。理解SystemUI是理解Android系统级UI的关键。

System Bars（系统栏）

Status Bar（状态栏）

手机屏幕上方，划分左右部分：左为通知图标、右为系统状态（时间/电量/信号）

Navigation Bar（导航栏）

Android 4.0后加入，提供Home/Back/Recents/Menu功能

Combined Bar

专为Tablet设计，合并状态栏与导航栏

Notifications（通知栏）
下拉显示通知条目。新特性包括：通知信息格式可定制、支持更多手势操作（左右滑动删除）、支持更多常用功能（如截图分享）。
其他系统UI功能

第19章Android常用的工具"小插件"——Widget机制

Widget俗称"小插件"，给Android带来更便捷的用户体验。Android定义了一套完整的Widget添加/移除和显示机制，使任何应用都能充当"Widget提供者"或"Widget容器"。

Widget架构三要素

AppWidgetProvider

Widget提供者（如天气插件），继承自BroadcastReceiver

AppWidgetHost

Widget容器（如Launcher），负责承载显示Widget

AppWidgetService

全局Widget管理器，跨进程管理所有Widget

Widget实现原理
通过RemoteViews实现跨进程UI更新。Provider提供RemoteViews，Host端通过AppWidgetHostView承载，并通过bind机制实现数据刷新。
Widget使用场景
音乐播放器控制、天气时钟、快捷开关、日程提醒等，Widget是Android桌面的重要扩展能力。

第20章Android应用程序的编译和打包

APK应用程序有三种编译方式：系统编译、IDE工具（ADT/AS）、命令行。本章系统讲解隐藏在"ADT"背后的细节，包括编译、打包、签名等完整流程。

APK编译流程

1. 资源处理

aapt/aapt2编译资源，生成R.java/资源表

2. 代码编译

Java/Kotlin编译为.class字节码

3. DEX转换

dx/d8将class转换为.dex格式

4. 打包签名

apkbuilder+签名生成最终APK

APK签名机制
  • v1签名：基于JAR签名（MANIFEST.MF/CERT.SF/CERT.RSA）
  • v2签名：Android 7.0引入，针对整个APK的签名
  • v3签名：支持密钥轮换
  • 签名验证：安装时验证、应用升级时验证
APK结构剖析
META-INF（签名信息）、AndroidManifest.xml（应用声明）、classes.dex（字节码）、resources.arsc（资源表）、res/（资源文件）、lib/（原生库）、assets/（资产文件）。

第21章Android虚拟机

Java凭借"Write once, Run anywhere"征服了无数开发者。Android选择Java作为首选应用语言，但又无法直接使用商用JVM，因此自研Dalvik/ART运行时环境。本章是理解Android应用运行机制的核心。

Java虚拟机核心概念
  • JVM规范：Oracle官方的Java虚拟机协议规范
  • JVM实现：如HotSpot等
  • JVM实例：运行时态的虚拟机进程
  • JVM内部模型：while(true) { 取指令→执行→调整PC }
JVM运行时结构
ClassLoader（类加载器）、运行时数据区（方法区/堆/栈/PC寄存器/本地方法栈）、执行引擎（Interpreter/JIT）、本地方法接口JNI等。
ClassLoader与双亲委派模型

Bootstrap ClassLoader

C/C++实现，加载[JAVA_HOME]/lib核心类

Extension ClassLoader

加载[JAVA_HOME]/lib/ext扩展类

System ClassLoader

应用程序类加载器，加载CLASSPATH

User ClassLoader

用户自定义加载器

双亲委派机制
用户自定义ClassLoader优先委派parent加载，直到Bootstrap ClassLoader。避免类关系混乱，保证基础类唯一性。Android中ClassLoader.loadClass()遵循此机制。
Dalvik与ART

Dalvik VM

Android 5.0前默认虚拟机，基于寄存器架构，使用.dex字节码

ART（Android Runtime）

Android 5.0后默认，支持AOT预编译和JIT，安装时将dex编译为oat

DEX文件格式

专为移动设备优化的字节码格式，共享常量池，节省内存

GC机制

标记-清除、复制算法；CMS、G1等不同GC策略

第22章Android安全机制透析

安全性是Android系统重点改进方向之一。本章从Kernel层和应用程序层两个角度，透析Android系统的安全设计与实现。

Kernel层安全保障
  • UID/GID机制：每个Android程序对内核是独立进程
  • Android特色Sandbox：所有应用都有唯一User ID
  • 文件系统UGO模型：应用私有数据受保护
  • SELinux/SEAndroid：即便Root也降低重要资源破坏力
  • DAC：自主访问控制
应用程序层安全保障
默认仅能访问有限资源：Camera、Location(GPS)、Bluetooth、Telephony、SMS/MMS、Network/Data等。严格控制涉及费用、隐私的操作。
Permission机制
权限分为normal/dangerous/signature等级。开发者在AndroidManifest.xml中声明，应用安装时用户授权，运行时动态检查。理解Permission是理解Android安全模型的核心。
Android安全拓展话题
设备Root原理、程序加固方案、程序注入与防护、密钥管理与证书体系、移动安全生态演进。

第25章系统调试辅助工具

Android系统调试需要用到几个核心工具：Emulator、ADB（Android Debug Bridge）等。掌握这些工具是日常开发和问题排查的基础。

Android Emulator基于QEMU，可模拟各种设备和Android版本。支持硬件加速、传感器仿真、网络仿真。是日常开发、测试的必备工具。
ADB核心命令

设备管理

adb devices / connect / disconnect

应用管理

adb install / uninstall / shell pm

文件传输

adb push / pull / shell

调试相关

adb logcat / bugreport / forward

高级调试工具
Systrace（性能分析）、TraceView（方法耗时）、Hierarchy Viewer（UI层级）、MAT（内存分析）、Stetho（网络监听）、LeakCanary（内存泄露检测）等。
