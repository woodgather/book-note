从覆盖范围看，本书大部分内容在讨论 Service（服务），因为 Android Java 层 Framework 的核心正是这些服务。

2.2 Java层中的Binder架构分析

2.2.1 Binder架构总览

Java 层 Binder 实际上是 Native 层 Binder 架构的镜像，C/S 架构一致：

  • IBinder 接口类：Binder 家族最顶层接口，定义跨进程调用契约
  • DeathRecipient 接口：服务端死亡时的回调接口
  • Binder 类：实现 IBinder，作为服务端 Bn 的代表
  • BinderProxy 类：实现 IBinder，作为客户端 Bp 的代表
  • BinderInternal 类：Binder 架构内部使用，含 GcWatcher 处理 GC
  • Parcel 类：承载跨进程通信数据

注意 FLAG_ONEWAY 标志：客户端发起调用后立即返回，不等待服务端结果。Java 层 Framework 中大量使用 FLAG_ONEWAY，常配合回调机制使用。

2.2.2 初始化Java层Binder框架

SystemServer 启动后，通过 JNI 注册 Java 层 Binder 类。android_util_Binder.cpp 负责把 Native 端 IBinder 与 Java 端 IBinder 桥接起来，建立 Java Binder 框架的根基。

2.2.3 addService实例分析

以 ServiceManager.addService 为例，分析服务注册流程：

  1. Java 端 ServiceManager 调用 native AddService
  2. JNI 桥接到底层 svc 链表
  3. Parcel 序列化服务名称与 Binder 对象
  4. 服务端通过 IServiceManager.addService 接收并存储

2.2.4 Java层Binder架构总结

Java 层 Binder 通过 JNI 调用 Native 层 Binder，本质上是一套 C/S 通信框架。掌握 IBinder / Binder / BinderProxy / Parcel 之间的关系，是理解后续 Service 通信的关键。

2.3 心系两界的MessageQueue

2.3.1 MessageQueue简介

MessageQueue 既是 Java 层 Handler 机制的"信箱"，又通过 JNI 与 Native Looper 联动，能处理 Native 层的消息。

2.3.2 提取消息

Java 端 MessageQueue.next() 通过 JNI 调用 native 层 Looper::pollOnce，从 Native 消息队列中提取消息。该函数使用 epoll 机制监听多个文件描述符。

2.3.3 nativePollOnce函数分析

深入分析 Looper::pollOnce → Looper::pollInner → epoll_wait 调用链，理解 Java MessageQueue 如何与 Native 事件源（Input/Window/Sensor 等）通信。

2.3.4 MessageQueue总结

MessageQueue 承担 Java 消息调度与 Native 事件监听的双重角色，是 Android 系统响应外部事件的核心。

2.4 本章小结

本章分析了 Java 层 Binder 框架与 MessageQueue，是后续所有服务分析的基础。

3第3章 深入理解SystemServer服务总入口

本章主要分析：SystemServer，以及第五类相对独立服务，包括 EntropyService、DropBoxManagerService、DiskStatsService、DeviceStorageMonitorService、SamplingProfilerService、ClipboardService。

涉及源代码

SystemServer.java (frameworks/base/services/java/com/android/server/SystemServer.java) com_android_server_SystemServer.cpp (frameworks/base/services/jni/) System_init.cpp (frameworks/base/cmds/system_server/library/System_init.cpp) EntropyService.java / DropBoxManagerService.java / DiskStatsService.java DeviceStorageMonitorService.java / SamplingProfilerService.java SamplingProfilerIntegration.java / SamplingProfiler.java ClipboardService.java / ClipboardManager.java / ClipData.java

3.1 概述

SystemServer 是 Android 系统中绝大部分核心服务的容器进程。SystemServer 启动后，会依次创建并注册 7 大类共 43 项服务，是 Framework 的"总管家"。

3.2 SystemServer分析

3.2.1 SystemServer启动流程

Zygote fork 出 system_server 进程后，main 函数创建 ServerThread；ServerThread.run 中按顺序启动 7 大类服务。System_init.cpp 中调用 register_jni_procs 注册 JNI 回调。

3.2.2 Service群英会

7 大类服务分组概览：

第一类 核心服务
ActivityManagerService、WindowManagerService、PackageManagerService 等
第二类 通信服务
WifiService、ConnectivityService、TelephonyRegistry 等
第三类 系统功能
AudioService、MountService、UsbService、NetworkPolicyManagerService
第四类 辅助服务
BatteryService、VibratorService、AlarmManagerService
第五类 独立服务（本章重点）
EntropyService、DropBoxManagerService、DiskStatsService、DSMS、SamplingProfilerService、ClipboardService、Watchdog
第六类 蓝牙
BluetoothService、BluetoothManagerService
第七类 UI
StatusBarService、NotificationManagerService、WallpaperManagerService

3.3 EntropyService分析

EntropyService 负责为系统提供高质量的随机数种子：

  • 读取 /dev/urandom、/dev/random 输出
  • 写入 /proc/sys/kernel/random/entropy_avail 等文件
  • 支持 addRandomness 累计熵

3.4 DropBoxManagerService分析

3.4.1 DBMS概述

DBMS 用于收集系统/应用的错误日志、ANR、Crash 报告等，存储到 /data/system/dropbox/ 目录下的文本/二进制文件。

3.4.2 dropbox日志文件的添加

客户端通过 DropBoxManager.add() → DBMS.add() 流程：检查 tag 黑名单 → 检查文件大小 → 加锁写入 tmp 文件 → 重命名为最终文件。

3.4.3 DBMS和settings数据库

DBMS 借助 Settings 数据库设置策略（文件保留时长、占用空间上限等），通过 ContentObserver 监听配置变化。

3.5 DiskStatsService和DeviceStorageMonitorService分析

3.5.1 DiskStatsService分析

通过读取 /proc/diskstats 与 /proc/vmstat 获取磁盘 I/O 统计，对外提供 dumpsys diskstats 调试信息。

3.5.2 DeviceStorageManagerService分析

DSMS 监控设备存储空间：定期检查 low memory 阈值；当剩余空间不足时启动缓存清理或弹出提示。

3.6 SamplingProfilerService分析

3.6.1 SamplingProfilerService概述

采样分析器，定时对 system_server 进程进行栈采样，并将结果保存为 trace 文件，辅助性能分析。

3.6.2 SamplingProfilerIntegration分析

SamplingProfilerIntegration 把采样器集成到 Dalvik 虚拟机，通过 VMStack.getThreadStackTrace 获取调用栈。

3.7 ClipboardService分析

3.7.1 CBS启动与copy

ClipboardService 启动时建立 ClipboardManager 内部表示；copy 时通过 ClipData 包装多种 MIME 类型（文本、Uri、Intent）。

3.7.2 从剪切板粘贴数据

客户端 ClipboardManager.getPrimaryClip() 跨进程调用 CBS，提取 ClipData 并按 MIME 解析。

3.7.3 CBS中的权限管理

3.0 之前所有应用可访问；3.0 之后只允许前台应用读取，限制后台访问以保护用户隐私。

3.8 本章小结

本章分析了 SystemServer 的整体结构以及 6 个独立服务的实现原理，呈现了 SystemServer 在 Android 系统中的核心地位。

4第4章 深入理解PackageManagerService应用管理

本章主要分析 PackageManagerService（PKMS），该服务负责 Android 系统中的 Package 信息查询和 APK 安装、卸载、更新等方面的工作。

涉及源代码

SystemServer.java (frameworks/base/services/java/com/android/server/SystemServer.java) IPackageManager.aidl (frameworks/base/core/android/java/content/pm/) PackageManagerService.java (frameworks/base/services/java/com/android/server/pm/) Settings.java (frameworks/base/services/java/com/android/server/pm/) PackageParser.java (frameworks/base/core/java/android/content/pm/) installd.c / commands.c (frameworks/base/cmds/installd/) pm 脚本 / Pm.java (frameworks/base/cmds/pm/) DefaultContainerService.java UserManager.java / UserInfo.java

4.1 概述

PKMS 是 Android Framework 的核心服务之一，承担了"应用管家"的角色：APK 解析、安装卸载、权限管理、Intent 解析等核心功能都由它负责。

4.2 初识PackageManagerService

PKMS 在 SystemServer 的 ServerThread 中创建：

  1. 读取 vold.decrypt 决定 onlyCore 模式（设备加密场景）
  2. 调用 PackageManagerService.main()，构造 PKMS 实例
  3. 调用 isFirstBoot() 判断是否首次启动
  4. 调用 performBootDexOpt() 做 dex 优化
  5. 调用 systemReady() 通知系统就绪

4.3 PKMS的main函数分析

4.3.1 构造函数入口

PKMS 构造函数完成环境初始化、扫描路径设置、sharedUserId/权限树搭建等准备工作。

4.3.2 扫描Package

扫描系统预装目录 /system/framework、/system/app、/data/app、/vendor/app 等，调用 PackageParser.parsePackage() 解析每个 APK/AndroidManifest.xml，构建内存中的 Package 信息结构。

4.3.3 构造函数扫尾工作

处理权限树、四大组件注册到 AMS、Provider 跨进程数据迁移、Settings 数据库的恢复等收尾步骤。

4.3.4 PKMS构造函数总结

PKMS 构造是 Android 启动中最耗时的环节之一，是后续应用管理与安装流程的基础。

4.4 APK Installation分析

4.4.1 APK安装流程概览

APK 安装涉及 pm 客户端 → PackageInstaller → PKMS → installd 的多进程协作流程。

4.4.2 pm分析

pm 是 shell 工具，通过调用 Pm.main() 处理 install/uninstall 等命令；其内部通过 IPackageManager 与 PKMS 通信。

4.4.3 installPackageWithVerification函数分析

  2. 调用 PackageParser 解析包
  3. 签名验证 (Verification)
  4. 权限检查
  5. 调用 installd 完成 dex 优化与文件迁移
  6. 更新内存中的 Package 信息

4.4.4 APK安装流程总结

完整流程涉及 shell、pm、PKMS、installd 四个角色，理解它们之间的分工是关键。

4.4.5 Verification介绍

Package Verification 机制确保 APK 来源可信，支持自定义验证器（如 Google Play）。

4.5 queryIntentActivities分析

4.5.1 Intent匹配流程概览

Intent 解析是 Android 系统解耦的关键：通过 action/category/data 与已注册的 Activity 列表匹配。

4.5.2 Activity信息的管理

4.5.3 Intent匹配查询分析

queryIntentActivities 内部流程：filter 规则匹配 → intent-filter 排序 → best-match 选定 → 返回 ResolveInfo 列表。

4.5.4 queryIntentActivities总结

理解 Intent 解析过程对应用开发与系统定制都至关重要。

4.6 installd及UserManager介绍

4.6.1 installd介绍

installd 是 native 守护进程，处理具体的文件操作（创建目录、移动 APK、优化 dex 等），把 PKMS 与底层文件系统解耦。

4.6.2 UserManager介绍

UserManager 实现多用户管理，每个用户拥有独立的应用空间与设置。Android 4.0 引入多用户支持，4.1 进一步引入用户配置文件限制。

5第5章 深入理解PowerManagerService电源管理

PMS 承担"电源策略大脑"职责，与底层 HAL、Native 服务协作完成系统电源管理。

5.3.1 WakeLock概述

WakeLock 是 Android 应用层阻止系统进入休眠的机制。底层依赖 suspend blocker + Linux wake_lock。

acquireWakeLock() 流程：参数校验 → 加锁 mWakeLocks 列表 → 累加引用计数 → 调用 nativeSetPowerMode → 必要时唤醒屏幕。

5.3.4 WakeLock总结

5.4 userActivity及Power按键处理分析

BatteryStatsService 记录应用/硬件的耗电统计，生成 batterystats 报告；通过 WakeLock、CPU、传感器等使用情况估算耗电。

5.5.3 BatteryService及BatteryStatsService总结

两服务共同支撑 Android 系统的电量管理与耗电统计。

6第6章 深入理解ActivityManagerService系统核心

本章以 ActivityManagerService（AMS） 为分析重点。AMS 是 Android 的核心服务，本章对其启动、Activity 创建与启动、BroadcastReceiver 工作原理、进程管理、Crash 处理等内容进行深入研究。

AMS 管理 Activity、Service、Broadcast、Provider 四大组件的启动与调度，并控制进程生命周期，是 Framework 中最复杂的服务之一。
