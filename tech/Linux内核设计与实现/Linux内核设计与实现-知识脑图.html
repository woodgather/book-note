CH 01

Linux 内核简介

1.1

Unix 的历史

1969 年 Bell Labs 的 Ken Thompson 与 Dennis Ritchie 在 PDP-7 上开发出 Unix 雏形，后用 C 语言重写，开创了现代操作系统的先河。

Unix 以简洁、优雅、"一切皆文件"的设计哲学深刻影响了现代操作系统，其分支 BSD、System V 推动了标准化进程（POSIX）。

1.2

Linux 简介

1991 年 Linus Torvalds 基于 Intel 80386 开发，从一个自学项目发展为全球最大的开源协作项目，吸引了数千名开发者贡献代码。

Linux 是类 Unix（Unix-like）内核，但并非 Unix 源代码的衍生。支持多处理器、内核抢占、多线程、虚拟内存、动态模块加载等现代特性。

1.3

操作系统与内核简介

1.3.1内核的角色
  • 管理硬件资源：CPU、内存、I/O 设备、文件系统、网络等
  • 向上提供系统调用（syscall）接口，向下驱动硬件
  • 处于最高特权级（内核态 / ring 0），用户程序运行在用户态（ring 3）
1.3.2单内核 vs 微内核
  • 单内核（Monolithic）：全部内核功能在同一地址空间，性能高，Linux 采用
  • 微内核（Microkernel）：内核仅提供 IPC、内存、调度等最小功能，服务在用户态，可靠性高但性能损耗
  • Linux 是模块化单内核：整体是单内核架构，但具备模块动态加载/卸载能力
1.4

Linux 与传统 Unix 内核的比较

支持内核模块（kernel module）动态加载，无需重新编译整个内核。

支持内核抢占（preempt），可在内核态中抢占当前执行的进程，提升响应性。

线程实现轻量：Linux 将线程视为共享地址空间等资源的进程（轻量级进程），不区分进程与线程。

面向对象思想融入数据结构设计，但代码本身使用纯 C 语言编写。

1.5

Linux 内核版本

版本号形如 主.次.释出，2.6 起进入长期稳定演进模式，不再以奇偶数区分开发/稳定版。

主线（mainline）由 Linus 维护，各发行版在此基础上打补丁并做定制。

1.6

Linux 内核开发者社区

全球数千名开发者，通过邮件列表（LKML 及各子系统列表）协作开发。

子系统有各自的维护者与 git 树，补丁经过 review 后进入 -next 树，最终合并到主线。

CH 02

从内核出发

2.1

获取内核源码

2.1.1使用 Git
  • Git 是 Linux 内核开发的版本控制工具，由 Linus 本人发起设计
  • 主仓库：git.kernel.org
  • 常用命令：git clone、git log、git diff、git bisect
2.1.2安装内核源代码
  • 源码通常放置于 /usr/src/linux 或用户自定义目录
  • 解压后需先配置（make config 等）再编译
2.1.3使用补丁
  • 补丁以 patch 文件形式分发，使用 patch -p1 < file 应用
  • git apply 与 git am 是更现代的补丁应用方式
2.2

内核源码树结构

核心顶层目录包括：arch/（架构相关）、block/（块 I/O）、crypto/（加密）、Documentation/（文档）、drivers/（驱动）、fs/（文件系统）。

以及：include/（头文件）、init/（启动初始化）、ipc/（进程间通信）、kernel/（核心子系统：调度、信号等）、lib/（通用库函数）、mm/（内存管理）、net/（网络栈）、scripts/（脚本）、security/（安全模块）、sound/（音频）、usr/（早期用户空间）。

2.3

编译内核

2.3.1配置内核
  • 多种配置方式：make config（文本）、make menuconfig（ncurses 菜单）、make xconfig（图形）
  • 配置保存在 .config 文件中，可直接修改
  • make defconfig 使用默认配置；make oldconfig 在旧配置基础上仅确认新增项
2.3.2减少编译垃圾信息
  • 使用 make > /dev/null 或重定向输出，静默编译
2.3.3并行编译
  • make -jN 以 N 个并行作业加速编译，通常取 CPU 核心数 +1
2.3.4安装新内核
  • make modules_install 安装模块到 /lib/modules/
  • 将内核镜像拷到 /boot 并更新引导加载器（grub）
2.4

内核开发的特点

2.4.1无 libc / 无标准头文件
  • 内核不能链接用户空间 C 库，需自行实现所需函数
  • 头文件来自内核源码 include/ 目录，不包含用户空间头
2.4.2GNU C 扩展
  • 内联函数、内联汇编、分支预测宏 likely() / unlikely()
  • __attribute__ 系列：packed、aligned、section 等
  • 零长数组、case 范围、语句表达式等 GCC 扩展被大量使用
2.4.3没有内存保护机制
  • 内核访问非法内存会触发 oops 甚至 panic，导致系统崩溃
  • 内核编程必须严谨，不能像用户态那样被 OS 保护
2.4.4不轻易使用浮点数
  • 内核态使用浮点需要手动保存/恢复 FPU 上下文，代价高且易出错
  • 绝大多数场景使用整数运算即可满足需求
2.4.5小而固定的栈
  • 内核栈通常只有 8KB 或 4KB（单页栈），远小于用户态栈
  • 避免大的局部变量和深层递归，尽量用动态分配
2.4.6同步和并发
  • 多处理器 + 内核抢占 + 中断，使得竞态无处不在
  • 必须使用锁、原子操作等同步机制保护共享数据
2.4.7可移植性
  • Linux 支持数十种架构，代码需注意字节序、字长、对齐、页大小等差异
  • 使用内核提供的类型与宏，避免硬编码平台假设
CH 03

进程管理

3.1

进程

进程是处于执行期的程序，是资源分配的基本单位。每个进程拥有独立的地址空间、打开的文件描述符、信号处理、一个或多个执行线程。

线程是内核调度的基本单位。Linux 以轻量级进程（LWP）方式实现线程，线程本质上是共享资源的进程。

3.2

进程描述符及任务结构

3.2.1分配进程描述符
  • 类型为 struct task_struct，通过 slab 分配器创建，便于复用
  • thread_info 位于栈底（或栈顶），存放与硬件上下文相关信息
3.2.2进程描述符的存放
  • PID 唯一标识一个进程，类型为 pid_t
  • 当前进程通过 current 宏获取，由 thread_info 的 task 成员指向
3.2.3进程状态
  • TASK_RUNNING：运行或就绪
  • TASK_INTERRUPTIBLE：可中断睡眠（信号可唤醒）
  • TASK_UNINTERRUPTIBLE：不可中断睡眠（等待 I/O 完成，信号不响应）
  • __TASK_TRACED：被调试追踪
  • __TASK_STOPPED：停止状态（收到 SIGSTOP 等）
  • EXIT_ZOMBIE：僵尸进程，已退出但父进程尚未调用 wait()
3.2.4设置当前进程状态
  • 使用 set_task_state(task, state) 宏，带内存屏障
  • set_current_state(state) 直接设置当前进程状态
3.2.5进程上下文
  • 用户态程序通过系统调用或异常进入内核态时，称为进程上下文
  • 进程上下文中 current 有效，可以睡眠、调度
3.2.6进程家族树
  • init 进程（PID 1）是所有用户进程的祖先
  • task_struct 通过 parent、children、sibling 指针构成树
  • 可通过 for_each_process 遍历系统中所有进程
3.3

进程创建

3.3.1写时拷贝（COW）
  • fork 后父子进程共享物理页，仅当任一方写入时才复制页
  • 极大降低 fork 的开销，避免不必要的内存复制
3.3.2fork()
  • 内核实现为 do_fork() → copy_process()
  • 复制 task_struct、页表、文件描述符、信号处理等资源
  • 子进程从 fork 返回 0，父进程返回子进程 PID
3.3.3vfork()
  • 与 fork 类似，但不复制父进程页表，子进程共享父进程地址空间
  • 父进程阻塞直到子进程 exec 或 exit
  • 历史遗留接口，现代应优先使用 fork + COW
3.4

线程在 Linux 中的实现

3.4.1创建线程
  • 通过 clone() 系统调用，指定共享哪些资源（VM、文件、信号等）
  • 线程本质上是与父进程共享地址空间等资源的轻量级进程
  • POSIX 线程库（pthread）在用户态封装此机制
3.4.2内核线程
  • 内核线程运行在内核态，没有独立地址空间（mm 为 NULL）
  • 由 kthreadd 创建，用于后台任务（如 pdflush、kswapd）
  • 使用 kthread_create() 创建，wake_up_process() 启动
3.5

进程终结

3.5.1删除进程描述符
  • 进程调用 do_exit() 释放大部分资源，进入 EXIT_ZOMBIE 状态
  • 父进程调用 wait() 后，子进程描述符才被最终释放
3.5.2孤儿进程
  • 父进程先于子进程退出时，子进程变为孤儿，由 init 进程收养
  • init 负责 wait() 清理僵尸进程，防止僵尸泄漏
CH 04

进程调度

4.1

多任务

多任务操作系统通过快速切换进程，营造多个进程同时运行的假象。分为抢占式（preemptive）与非抢占式（cooperative），Linux 采用抢占式调度。

4.2

Linux 的进程调度

Linux 2.6 引入 CFS（完全公平调度器）作为普通进程的默认调度类。调度器是模块化的，不同调度类管理不同类型的进程，按优先级从高到低依次检查。

4.3

策略

4.3.1I/O 消耗型 vs CPU 消耗型
  • I/O 消耗型：多数时间在等待 I/O，响应性重要，需要频繁调度
  • CPU 消耗型：多数时间在计算，需要长时间运行以利用缓存局部性
  • 调度器需要在响应速度与吞吐率之间权衡
4.3.2进程优先级
  • nice 值：-20 到 +19，数值越小优先级越高
  • 实时优先级：0 到 99，高于所有普通进程
4.3.3时间片
  • 进程可连续运行的时长，用完后触发调度
  • CFS 不再使用固定时间片，而是用权重分配 CPU 时间比例
4.3.4调度策略的活动
  • 高优先级进程先运行、运行更久；低优先级后运行
  • 交互进程响应快，批处理进程不影响前台体验
4.4

Linux 调度算法

4.4.1调度器类
  • 模块化结构，每种调度类管理一类进程（stop、dl、rt、fair、idle）
  • 核心数据结构：struct sched_class，定义 enqueue/dequeue/pick_next 等钩子
  • 按优先级从高到低依次检查，找到第一个有可运行进程的类
4.4.2Unix 进程调度演进
  • 传统 Unix 使用 nice 值 + 时间片机制，高负载下交互性变差
  • O(1) 调度器（2.6 早期）：数组 + bitmap，O(1) 复杂度，但交互性判断复杂
  • CFS 是当前主流，基于公平思想设计
4.4.3公平调度 CFS
  • 核心思想：每个进程获得公平的 CPU 份额，而非固定时间片
  • 使用 vruntime（虚拟运行时间） 记录每个进程的运行时间
  • 总是选择 vruntime 最小的进程运行
  • 使用红黑树管理可运行队列，查找最小节点 O(log n)
  • nice 值作为权重，影响 vruntime 增长速度
4.5

Linux 调度的实现

4.5.1时间记账
  • 每个调度周期更新 se.vruntime，根据权重（nice）缩放
  • 周期由 sysctl_sched_latency（目标调度延迟）与最小粒度决定
4.5.2进程选择
  • 从红黑树中取最左侧节点（vruntime 最小者），即下一个运行的进程
  • __pick_next_entity() 完成选择逻辑
4.5.3调度器入口
  • 主调度函数 schedule()，找到最高优先级的可运行进程并切换
  • 可由 need_resched 标志触发，在合适检查点检查（如返回用户态前）
4.5.4睡眠和唤醒
  • 睡眠：进程将自己加入等待队列，设为 TASK_INTERRUPTIBLE/UNINTERRUPTIBLE，然后调度
  • 唤醒：事件发生时，wake_up() 唤醒等待队列上的进程，设为 TASK_RUNNING 并加入运行队列
4.6

抢占和上下文切换

4.6.1用户抢占
  • 从系统调用或中断返回用户态时，若 need_resched 置位则触发调度
  • 进程被抢占前处于用户态，状态可安全保存
4.6.2内核抢占
  • 2.6 引入：只要没有持有锁，内核态也可被抢占
  • preempt_count 计数器记录抢占禁用层数，为 0 时可抢占
  • 中断返回内核态时检查 need_resched 和 preempt_count
4.7

实时调度策略

SCHED_FIFO：先进先出，无时间片，高优先级实时进程可抢占低优先级实时进程。

SCHED_RR：带时间片的轮转实时调度，同优先级进程轮询运行。

实时优先级范围 0~99，数值越大优先级越高，均高于 CFS 普通进程。

4.8

与调度相关的系统调用

4.8.1策略与优先级
  • nice() / setpriority()：调整 nice 值
  • sched_setscheduler()：设置调度策略与参数
4.8.2处理器绑定
  • CPU 亲和性掩码（cpumask_t）控制进程可在哪些 CPU 上运行
  • 可用于缓存亲和、NUMA 优化、实时应用等
4.8.3放弃处理器时间
  • sched_yield()：主动让出 CPU，回到运行队列尾部

系统调用

5.1

与内核通信

系统调用是用户空间与内核之间的受控接口，提供访问硬件和内核功能的通道。通过软中断（如 int 0x80）或 syscall/sysenter 指令从用户态陷入内核态。

5.2

API、POSIX 和 C 库

API（如 POSIX）是应用程序层面的接口标准。C 库（glibc）封装系统调用，提供符合 POSIX 的 API。一个系统调用可能对应多个库函数，一个库函数也可能调用多个系统调用。

5.3

系统调用

5.3.1系统调用号
  • 每个系统调用有唯一编号（syscall number），用于索引 sys_call_table
  • 编号一旦分配不再改变，保证 ABI 兼容性
5.3.2系统调用的性能
  • 上下文切换（用户态↔内核态）有一定开销
  • Linux 通过快速系统调用指令（sysenter/sysexit、syscall/sysret）降低切换成本
5.4

系统调用处理程序

5.4.1指定恰当的系统调用
  • x86 32 位通过 eax 寄存器传递调用号，64 位使用 rax
  • 内核查表后跳转到对应处理函数
5.4.2参数传递
  • 参数通过寄存器传递：ebx/ecx/edx/esi/edi/ebp（x86-32）、rdi/rsi/rdx/r10/r8/r9（x86-64）
  • 参数数量通常不超过 6 个，更多时使用结构指针
5.5

系统调用的实现

5.5.1实现系统调用
  • 通常以 SYSCALL_DEFINEN(name, ...) 宏定义
  • 需要在 sys_call_table 中登记，并分配调用号
5.5.2参数验证
  • 验证指针是否合法：是否属于用户空间、是否有读写权限
  • 使用 access_ok()、copy_from_user()、copy_to_user()
  • 绝不能信任用户空间传入的任何数据
5.6

系统调用上下文

5.6.1绑定系统调用的最后步骤
  • 注册 syscall 号、将函数加入 sys_call_table、各架构需同步定义
  • 系统调用必须编译进内核（不能作为模块）
5.6.2从用户空间访问系统调用
  • 应用程序通过 glibc 或 syscall() 宏直接调用
5.6.3为什么不通过系统调用实现
  • 系统调用一旦合入主线就需要长期维护 ABI 兼容性
  • 优先考虑：设备节点、sysfs、procfs、netlink 等更灵活的接口

内核数据结构

6.1

链表

6.1.1单向链表与双向链表
  • 单向链表：只有 next 指针，只能单向遍历，插入删除快但查找需从头
  • 双向链表：有 prev 和 next 指针，可双向遍历，删除效率高
6.1.2环形链表
  • 首尾相连，遍历不会到尽头，需注意终止条件
  • Linux 内核大量使用双向环形链表
6.1.3沿链表移动
  • 线性时间复杂度 O(n)，不适合频繁查找
  • 适合顺序访问和动态插入/删除
6.1.4Linux 内核实现
  • 侵入式链表：struct list_head 嵌入宿主结构
  • 通过 container_of 宏由成员指针得到宿主结构指针
  • 头文件：<linux/list.h>
6.1.5操作链表
  • list_add() / list_add_tail()：头部/尾部插入
  • list_del()：删除节点
  • list_empty()：判断是否为空
6.1.6遍历链表
  • list_for_each_entry(pos, head, member)：安全遍历宿主结构
  • list_for_each_entry_safe()：遍历时可安全删除当前节点
6.2

队列 kfifo

6.2.1kfifo 结构
  • 内核通用的 FIFO（先进先出）缓冲区实现
  • 环形缓冲区，天然适用于生产者-消费者模型
6.2.2创建与操作
  • kfifo_alloc() 动态创建，kfifo_init() 静态创建
  • kfifo_in() 入队、kfifo_out() 出队
  • 大小必须为 2 的幂，便于用掩码实现环形索引
6.3

映射 idr

6.3.1idr 机制
  • 将整数 ID 映射到指针的高效数据结构
  • 广泛用于文件描述符、IPC ID、SCSI ID 等场景
6.3.2常用操作
  • idr_init() 初始化；idr_alloc() 分配 ID 并绑定指针
  • idr_find() 查找；idr_remove() 删除
6.4

二叉树

6.4.1二叉搜索树 BST
  • 左子树节点 < 根 < 右子树节点，中序遍历有序
  • 最坏情况退化为链表（O(n)），需自平衡
6.4.2自平衡二叉搜索树
  • 红黑树（rbtree）：Linux 内核广泛使用的自平衡 BST
  • 五条性质保证 O(log n) 的查找、插入、删除
  • CFS 运行队列、VMA 树、匿名区间树等均使用红黑树
6.5

数据结构的选择

需要遍历且插入多 → 链表；需要 FIFO → 队列；需要 ID 映射 → idr；需要有序查找 → 红黑树；需要哈希查找 → 哈希表（hlist）。

6.6

算法复杂度

6.6.1算法基础
  • 时间复杂度与空间复杂度是评估算法的两个核心维度
6.6.2大 O 符号
  • O(1) 常数、O(log n) 对数、O(n) 线性、O(n log n) 线性对数、O(n²) 平方
6.6.3大 Θ 符号
  • Θ 表示紧确界（上下界同阶），O 表示上界，Ω 表示下界
6.6.4时间复杂度
  • 选择数据结构时需根据数据规模与操作频率权衡
  • 内核中常见操作多为 O(1) 或 O(log n)，避免 O(n) 及以上的热路径
CH 07

中断和中断处理

7.1

中断

硬件设备通过中断信号通知 CPU 事件发生，打断当前执行流程。中断号（IRQ）唯一标识中断源。异常（Exception）是同步的，由 CPU 在执行指令时产生（如缺页、除零）。

7.2

中断处理程序

响应特定中断而执行的内核函数，注册在对应中断线上。异步执行、不可阻塞、运行速度要快，避免影响系统响应性。

7.3

上半部与下半部的对比

上半部（top half）：中断处理程序本身，快速应答硬件，做最紧要的工作。

下半部（bottom half）：将不那么紧急的工作推后到稍后安全时机执行。

划分原则
对时间敏感、操作硬件、不能被其他中断打断的放在上半部；其余耗时工作放下半部。
7.4

注册中断处理程序

7.4.1中断处理程序标志
  • IRQF_DISABLED：处理期间禁用所有中断（快速中断）
  • IRQF_SHARED：中断线可在多设备间共享
  • IRQF_TIMER：系统定时器专用标志
  • IRQF_SAMPLE_RANDOM：此中断贡献给随机数熵池
7.4.2注册与释放
  • request_irq(irq, handler, flags, name, dev) 注册中断
  • 成功返回 0，失败返回非 0；dev 在共享中断中用于区分设备
  • free_irq(irq, dev) 注销中断处理函数
7.5

编写中断处理程序

7.5.1共享的中断处理程序
  • 多个设备共享一条 IRQ 线，处理程序需通过 dev_id 和状态寄存器判断
  • 返回 IRQ_HANDLED 表示处理了该中断，IRQ_NONE 表示不是本设备
7.5.2中断处理程序实例
  • 典型流程：检查设备状态 → 读取数据 → 清除中断 → 将数据交给下半部处理
  • 使用 iowrite*/ioread* 等宏操作 I/O 端口/寄存器
7.6

中断上下文

中断上下文不与任何进程关联，current 指向被中断的进程。不能睡眠（不能调用可能阻塞的函数），不能调用 schedule()。栈空间有限，执行应尽可能短。

7.7

中断处理机制的实现

硬件 → IDT → 通用中断处理程序 → do_IRQ() → handle_IRQ_event() → 调用注册的处理函数。每个 CPU 都有自己的中断向量表，APIC 负责分发中断到不同 CPU。

7.8

/proc/interrupts

用户空间查看中断统计的接口，显示每个 IRQ 在各 CPU 上的触发次数。第一列是中断号，后面各列是各 CPU 的计数，最后是设备名。

7.9

中断控制

7.9.1禁止和激活中断
  • local_irq_disable() / local_irq_enable()：本地 CPU 全局开关
  • local_irq_save(flags) / local_irq_restore(flags)：保存并恢复状态，可嵌套
7.9.2禁止指定中断线
  • disable_irq() / enable_irq()：针对某条 IRQ 线
  • disable_irq_nosync()：不等待当前处理完成立即返回
7.9.3中断系统的状态
  • irqs_disabled()：检查本地中断是否被禁用
  • in_interrupt()：判断当前是否处于中断上下文
CH 08

下半部和推后执行的工作

8.1

下半部

8.1.1为什么要用下半部
  • 中断处理要快，但实际工作往往量大（如网络数据包解析、块 I/O 完成处理）
  • 将工作分为两部分：上半部快速响应硬件，下半部处理耗时部分
  • 下半部运行时允许响应其他中断，提升系统并发性
8.1.2下半部的环境
  • 软中断和 tasklet：运行在中断上下文，不能睡眠
  • 工作队列：运行在内核线程（进程上下文），可以睡眠
8.2

软中断 softirq

8.2.1软中断的实现
  • 静态分配，编译时确定，共约 10 种（HI、TIMER、NET_TX、NET_RX、BLOCK、TASKLET 等）
  • 由 do_softirq() 在中断返回前执行，同类型可在多个 CPU 上并行运行
  • 需要自行保证并发安全，适合高性能场景（如网络栈）
8.2.2使用软中断
  • open_softirq() 注册处理函数
  • raise_softirq() 触发软中断
8.3

tasklet

8.3.1tasklet 的实现
  • 基于软中断实现（TASKLET_SOFTIRQ 和 HI_SOFTIRQ）
  • 同一 tasklet 只在一个 CPU 上执行（串行），但不同 tasklet 可并行
  • 实现简单，无需复杂同步，是驱动中最常用的下半部机制
8.3.2使用 tasklet
  • DECLARE_TASKLET(name, func, data) 静态声明
  • tasklet_schedule(&t) 调度执行，tasklet_kill() 销毁
8.3.3老的 BH 机制
  • 2.6 以前的老下半部机制，已废弃，仅作历史了解
8.4

工作队列 workqueue

8.4.1工作队列的实现
  • 由内核线程（worker thread）从工作队列中取出任务执行，运行在进程上下文
  • 每个 CPU 有默认的 events/n 内核线程处理工作项
  • 2.6.36 后引入 CMWQ（并发管理工作队列），更高效管理线程池
8.4.2使用工作队列
  • INIT_WORK(work, func) 初始化工作项
  • schedule_work(&work) 提交到默认工作队列
  • 可创建自定义工作队列 create_workqueue()
  • cancel_work_sync() 取消并等待完成
8.4.3老的任务队列机制
  • 早期内核的 tq 机制，已被工作队列取代
8.5

下半部机制的选择

需要高性能、能自行处理并发同步 → 软中断。接口简单、驱动常用、不需并行 → tasklet。需要睡眠、需要进程上下文 → 工作队列。

8.6

在下半部之间加锁

软中断可能并发，需用自旋锁保护共享数据。tasklet 同类型不会并发，互斥需求低。工作队列在进程上下文，可使用互斥体等可睡眠锁。

8.7

禁止下半部

local_bh_disable() / local_bh_enable()：本地 CPU 禁用软中断和 tasklet。通过 per-CPU 计数器实现，可嵌套使用。常在进程上下文与下半部共享数据时配合自旋锁使用。

内核同步介绍

9.1

临界区和竞争条件

9.1.1为什么需要保护
  • 临界区：访问和操作共享数据的代码段
  • 多个执行路径同时进入临界区会导致数据不一致，即竞态条件
  • 同步的目的就是避免竞态，保证共享数据的一致性
9.1.2单个变量
  • 即使是单个变量的读写，在多处理器或抢占下也可能出现中间状态
  • 需要原子操作或锁来保证操作的不可分割性
9.2

加锁

9.2.1造成并发执行的原因
  • 中断：任何时刻打断当前代码
  • 软中断 / tasklet：同样异步触发
  • 内核抢占：一个内核路径抢占另一个
  • 多处理器：两个 CPU 同时执行同一段代码
  • 睡眠与调度：进程上下文睡眠后被另一个进程取代
9.2.2了解要保护些什么
  • 核心原则：保护数据，而不是保护代码
  • 识别所有共享的数据结构和变量，确定访问路径并加锁
  • 加锁粒度要合适：太粗性能差，太细则易死锁且维护成本高
9.3

死锁

死锁的四个必要条件：互斥、持有并等待、不可抢占、循环等待，四个同时成立时发生死锁。避免方法：按固定顺序加锁、避免循环等待、使用定时器或检测机制。最简单有效的方法：始终按相同的顺序获取多个锁。

9.4

争用和扩展性

锁争用：锁被占用时其他执行路径等待的情况。细粒度锁、per-CPU 数据、读写锁等可以降低争用。

扩展性：系统负载/CPU 增加时性能能否近似线性提升。过早优化是万恶之源：先保证正确性，再根据瓶颈优化锁粒度。

CH 10

内核同步方法

10.1

原子操作

10.1.1原子整数操作
  • atomic_t 类型提供整数原子操作，由架构底层指令保证不可分割
  • 常用：atomic_read()、atomic_set()、atomic_add()、atomic_inc()、atomic_dec_and_test()
10.1.264 位原子操作
  • atomic64_t 类型，32 位架构可能用锁实现，64 位架构原生支持
10.1.3原子位操作
  • 对内存中某一位进行原子操作：set_bit()、clear_bit()、test_and_set_bit() 等
  • 操作对象是普通内存地址，无特殊类型
10.2

自旋锁

10.2.1自旋锁方法
  • 获取锁时循环等待（自旋）直到锁可用，适用于短时间持有
  • spin_lock() / spin_unlock()：基本操作
  • spin_lock_irqsave()：保存并关本地中断，防止死锁
  • 不可递归持有同一自旋锁，会自己把自己锁死
10.2.2其他操作
  • spin_trylock()：尝试获取，失败立即返回非零
  • spin_is_locked()：检查锁是否被持有
10.2.3自旋锁和下半部
  • 数据被进程上下文和下半部共享 → spin_lock_bh()
  • 数据被中断处理程序和下半部共享 → spin_lock_irqsave()
10.3

读-写自旋锁

读者可以并发持有，写者互斥。适用于读多写少的场景。read_lock() / read_unlock()、write_lock() / write_unlock()。注意可能存在写者饥饿问题。

10.4

信号量

10.4.1计数信号量和二值信号量
  • 信号量是睡眠锁，获取失败时进程挂起等待，不占用 CPU
  • 计数信号量允许多个持有者（count > 1）；二值信号量 count = 1
  • 只能在进程上下文使用（因为会睡眠）
10.4.2创建和初始化
  • sema_init(sem, val) 初始化；init_MUTEX(sem) 初始化为互斥
10.4.3使用信号量
  • down() 获取信号量（不可中断）
  • down_interruptible() 可被信号打断，返回 -EINTR
  • up() 释放信号量，唤醒等待者
10.5

读-写信号量

类似读-写自旋锁，但是睡眠锁，适用于读多写少且持有时间较长的场景。down_read()、up_read()、down_write()、up_write()。

10.6

互斥体 mutex

10.6.1信号量 vs 互斥体
  • mutex 是更简单、更专用的互斥机制，等同于 count = 1 的信号量但更轻量
  • 不能递归持有、只能由加锁者解锁、不能在中断上下文使用
  • 推荐：只要满足约束，优先用 mutex 而非信号量
10.6.2自旋锁 vs 互斥体
  • 持有时间短、不能睡眠、中断上下文 → 自旋锁
  • 持有时间长、可能睡眠、进程上下文 → mutex
10.7

完成变量

用于一个任务等待另一个任务完成某件事的同步场景。init_completion() 初始化，wait_for_completion() 等待，complete() / complete_all() 唤醒。比信号量更语义化地表达"完成通知"。

10.8

BLK 大内核锁 BKL

全局内核锁 lock_kernel() / unlock_kernel()，历史遗留。粗粒度全局锁，严重影响多处理器扩展性，在 2.6 中逐步被细粒度锁取代，后续版本已完全移除。

10.9

顺序锁 seqlock

为读多写少且写不能被读者阻塞的场景设计。读者通过序号判断读期间是否发生了写，若有则重试。写者永远可以获取锁。典型使用：jiffies 64 位读取。

10.10

禁止抢占

preempt_disable() / preempt_enable()：禁用/启用内核抢占。通过 per-CPU 计数实现，可嵌套。per-CPU 数据访问时常使用，确保不会被抢占到其他 CPU。

10.11

顺序和屏障

编译器和 CPU 可能重排内存访问顺序，多处理器场景需用内存屏障保证顺序。rmb() 读屏障、wmb() 写屏障、mb() 全屏障。smp_rmb() 等 SMP 版本在 UP 上为空操作。常用于无锁数据结构（如环形缓冲区的头尾指针）。

CH 11

定时器和时间管理

11.1

内核中的时间概念

内核需要感知时间的流逝，用于调度、超时、统计、定时等。系统定时器以固定频率产生中断（tick），驱动时间计数前进。相对时间 vs 绝对时间，墙上时间（wall time）vs 系统运行时间。

11.2

节拍率 HZ

11.2.1理想的 HZ 值
  • HZ 是每秒的时钟中断次数，常见值：100、250、1000（x86 常用 250）
  • HZ 值越高，时钟中断越频繁，时间精度越高但系统开销越大
11.2.2高 HZ 的优势
  • 更高的时间精度：定时器精度提高，poll/select 超时更准确
  • 更好的响应性：进程时间片更细粒度，交互体验更好
11.2.3高 HZ 的劣势
  • 时钟中断占 CPU 比例增加，减少了有用工作时间
  • 更频繁打断缓存，降低缓存命中率
  • 功耗增加（笔记本 / 移动设备）
  • 现代内核支持 tickless / NO_HZ 模式，idle 时停止 tick 节省能源
11.3

jiffies

11.3.1jiffies 的内部表示
  • 全局变量 jiffies 记录自系统启动以来的节拍数
  • 每次时钟中断加 1，是内核中最重要的时间基准之一
  • 32 位（jiffies）与 64 位（jiffies_64）两种表示，32 位会回绕
11.3.2jiffies 的回绕
  • 32 位 jiffies 在高 HZ 下可能在较短时间内溢出回绕
  • 使用 time_after()、time_before()、time_in_range() 等宏安全比较
11.3.3用户空间和 HZ
  • 用户空间看到的 HZ 可能与内核实际 HZ 不同（USER_HZ）
  • 内核将统计信息导出到用户空间时进行单位转换，保证 ABI 稳定
11.4

硬时钟和定时器

11.4.1实时时钟 RTC
  • 独立于 CPU 的硬件时钟，系统掉电后仍运行（靠电池）
  • 用于保存墙上时间，启动时读取以初始化系统时间
11.4.2系统定时器
  • 可编程间隔定时器 PIT、HPET、本地 APIC 定时器等
  • 产生周期性时钟中断，驱动内核时间子系统运行
11.5

时钟中断处理程序

上半部：更新 jiffies、更新墙上时间、更新进程时间统计（utime/stime）。下半部：运行到期的内核定时器、调度器 tick 计算、负载均衡等。

11.6

实际时间

xtime 变量保存当前墙上时间（秒 + 纳秒）。do_gettimeofday() 获取高精度墙上时间。NTP 可调整时钟频率以逐步同步。

11.7

定时器

11.7.1使用定时器
  • struct timer_list：定时器结构
  • init_timer() 初始化、add_timer() 启动、mod_timer() 修改、del_timer() 删除
  • 以 jiffies 为单位，到期时在软中断上下文执行回调
11.7.2定时器竞争条件
  • 定时器到期与删除可能在不同 CPU 上同时发生
  • 使用 del_timer_sync() 确保删除后没有其他 CPU 还在运行处理函数
11.7.3定时器的实现
  • 使用时间轮（timer wheel）算法，O(1) 的插入与删除
  • 五级时间轮，按到期时间远近分布在不同桶中
  • 在 TIMER_SOFTIRQ 软中断中处理到期定时器
11.8

延迟执行

11.8.1忙等待
  • 循环读取 jiffies 直到指定时间，占着 CPU 什么也不做，浪费资源
  • 仅在极短延迟且不能睡眠的场景考虑
11.8.2短延迟
  • udelay()、ndelay()、mdelay()：微秒/纳秒/毫秒级忙等待
  • 基于循环次数计算，由 BogoMIPS 校准
  • 用于极短硬件延迟场景（如等待寄存器就绪）
11.8.3schedule_timeout()
  • 将当前进程睡眠指定时间，到期唤醒
  • 进程上下文可用，不占 CPU，是最常用的延迟手段
  • 精度受 HZ 限制，且可能因信号提前返回
CH 12

内存管理

12.1

页 page

内存管理的基本单位，物理内存被划分为固定大小的页。常见页大小 4KB（x86），也支持大页（2MB、1GB）。struct page 描述每个物理页，页帧号（PFN）与 page 结构一一对应。

12.2

区 zone

由于硬件限制，物理内存被划分为多个区：ZONE_DMA（可用于 DMA 的低端内存）、ZONE_NORMAL（常规映射内存）、ZONE_HIGHMEM（高端内存，32 位下 > 896MB 部分）。64 位架构通常没有高端内存问题。每个区有自己的空闲链表和水位线。

12.3

获得页

12.3.1获得填充为 0 的页
  • alloc_pages(gfp_mask, order)：分配 2^order 个连续物理页
  • __get_free_pages()：返回内核逻辑地址
  • get_zeroed_page()：分配并清零一页
12.3.2释放页
  • __free_pages(page, order) / free_pages(addr, order) 释放页
  • 务必成对使用，避免内存泄漏
12.4

kmalloc()

12.4.1gfp_mask 标志
  • kmalloc 是内核最常用的内存分配函数，返回虚拟地址，物理上连续
  • GFP_KERNEL：常用，可能睡眠，进程上下文使用
  • GFP_ATOMIC：原子分配，不睡眠，中断上下文使用
  • GFP_DMA：从 ZONE_DMA 分配
  • GFP_HIGHUSER：从高端内存分配用户页
12.4.2kfree()
  • 释放 kmalloc 分配的内存，传入 NULL 安全
  • 必须与 kmalloc 匹配使用
12.5

vmalloc()

分配虚拟地址连续但物理地址不一定连续的内存。通过修改页表实现，性能低于 kmalloc（需要建立页表映射）。只能在进程上下文调用（可能睡眠）。适合分配大块内存、对物理连续性无要求的场景。

12.6

slab 层

12.6.1slab 层的设计
  • slab 分配器在伙伴系统之上提供对象级缓存，减少频繁分配/释放的开销
  • 三级结构：缓存（cache）→ slab → 对象
  • 每个缓存管理一种对象类型（如 task_struct、inode 等）
  • 三种状态：满、部分满、空。分配优先从部分满的 slab 取
12.6.2slab 分配器接口
  • kmem_cache_create() 创建缓存，kmem_cache_destroy() 销毁
  • kmem_cache_alloc() 分配对象，kmem_cache_free() 释放
  • kmalloc 底层即基于 slab 通用缓存实现
12.7

栈上的静态分配

12.7.1单页内核栈
  • 内核栈大小有限（通常 8KB 或 4KB），非常宝贵
  • 2.6 起支持单页栈（4KB），中断栈独立，减少内存占用
12.7.2在栈上工作
  • 避免大的局部变量、深层递归
  • 大数据结构应使用动态分配（kmalloc 等）
12.8

高端内存的映射

12.8.1永久映射
  • kmap() 将高端内存页映射到内核地址空间
  • 映射数有限，使用后需调用 kunmap() 释放
12.8.2临时映射
  • kmap_atomic() 建立临时映射，持有时间短，不会阻塞
  • 固定插槽，使用后立即释放，可在中断上下文使用
12.9

每个 CPU 的分配

per-CPU 数据：每个 CPU 有自己的副本，访问无需加锁，可避免缓存失效。DEFINE_PER_CPU(type, name) 编译时声明。get_cpu_var() / put_cpu_var() 访问并禁用抢占。

12.10

新的每个 CPU 接口

12.10.1编译时 per-CPU 数据
  • DEFINE_PER_CPU(type, name) / DECLARE_PER_CPU(type, name)
  • 数据存放在特殊段中，各 CPU 有独立实例
12.10.2运行时 per-CPU 数据
  • alloc_percpu(type) 运行时动态分配 per-CPU 数据
  • free_percpu(pointer) 释放
12.11

使用 per-CPU 数据的原因

减少锁竞争：各 CPU 独立访问自己的副本。提高缓存命中率：减少缓存抖动（cache bouncing）。使用时需注意：访问期间禁用抢占，跨 CPU 访问要同步。

12.12

分配函数的选择

需要物理连续页 → __get_free_pages / kmalloc / slab。只需虚拟连续 → vmalloc。小块且频繁分配 → slab 缓存。中断上下文且原子 → GFP_ATOMIC 标志。高端内存页 → alloc_pages + kmap。每 CPU 独立数据 → per-CPU 接口。

CH 13

虚拟文件系统

13.1

通用文件系统接口

VFS（Virtual File System）是内核提供的抽象层，向上提供统一的文件系统接口。用户通过 open/read/write 等系统调用访问文件，VFS 转发给具体文件系统。使得 Linux 支持众多不同文件系统（ext2/3/4、XFS、Btrfs、NFS、proc、sysfs 等）。

13.2

文件系统抽象层

VFS 定义了所有文件系统都必须实现的接口（超级块、索引节点、目录项、文件等对象及其操作）。具体文件系统注册到 VFS，并填充这些对象的函数指针。VFS 使用面向对象设计思想，用 C 语言实现（结构 + 函数指针表）。

13.3

Unix 文件系统

Unix 文件四要素：文件、目录项、索引节点（inode）、超级块。"一切皆文件"：普通文件、目录、设备、管道、套接字都通过文件接口访问。每个文件由 inode 唯一标识，存放元数据（权限、大小、时间戳、数据块指针等）。目录是特殊文件，存放目录项（文件名 → inode 号的映射）。

13.4

VFS 对象及数据结构

四大核心对象：超级块对象（super_block）、索引节点对象（inode）、目录项对象（dentry）、文件对象（file）。每个对象都包含一个操作函数表，由具体文件系统实现。

13.5

超级块对象

struct super_block 表示一个已挂载文件系统的控制信息。存储文件系统整体信息：块大小、魔数、超级块操作表、inode 链表等。s_op 指向超级块操作表。

13.6

超级块操作

主要操作：alloc_inode() 分配 inode、destroy_inode() 销毁 inode、read_inode() / write_inode() 读写 inode、put_super() 卸载时释放超级块、statfs() 获取文件系统统计信息。

13.7

索引节点对象

struct inode 表示磁盘上的一个文件（元数据）。包含：i_ino（inode 号）、i_mode（权限与类型）、i_nlink（硬链接数）、i_uid/i_gid、i_size、i_atime/i_mtime/i_ctime、i_blocks、i_op（inode 操作）、i_fop（文件操作）、i_mapping（地址空间）等。

13.8

索引节点操作

主要操作：create() 创建普通文件、lookup() 在目录中查找文件名、link() / unlink() 硬链接增删、mkdir() / rmdir() 目录操作、symlink() / readlink() 符号链接、rename() 重命名。

13.9

目录项对象

13.9.1目录项状态
  • struct dentry 表示路径中的一个分量（文件名 + inode）
  • 三种状态：被使用（used）、未被使用（unused）、负状态（negative，inode 不存在）
13.9.2目录项缓存
  • dcache 缓存最近使用的目录项，加速路径查找
  • LRU 管理，内存紧张时回收未使用的目录项
13.10

目录项操作

主要操作：d_revalidate() 重新验证有效性（网络文件系统常用）、d_hash() 计算哈希、d_compare() 比较文件名、d_delete() 删除、d_release() 释放。

13.11

文件对象

struct file 表示一个已打开的文件，是进程与 inode 之间的交互实例。包含：f_pos（当前读写位置）、f_dentry（对应 dentry）、f_op（文件操作）、f_flags（打开标志）、f_mode（访问模式）、private_data 等。

13.12

文件操作

主要操作：llseek() 修改偏移、read() / write() 读写、readdir() 读取目录条目、mmap() 内存映射、open() / release() 打开/关闭、fsync() 同步到磁盘、ioctl() 设备控制、poll() 多路复用。

13.13

文件系统相关数据结构

struct file_system_type 描述一种文件系统类型（如 ext3、proc），用于注册。struct vfsmount 描述一个挂载点的实例信息。

13.14

进程相关数据结构

struct files_struct：进程打开的文件表（文件描述符数组）。struct fs_struct：进程的文件系统信息（根目录、当前工作目录、umask）。struct mm_struct：进程的地址空间，包含 VMA 树和页表。

CH 14

块 I/O 层

14.1

剖析一个块设备

块设备：以块为单位随机访问的设备（硬盘、SSD、光盘等），最小寻址单元是扇区（通常 512 字节）。字符设备：按字节流顺序访问（串口、键盘）。块大小是文件系统一次操作的逻辑块大小，通常是扇区的整数倍。

14.2

缓冲区和缓冲区头

缓冲区（buffer）是块在内存中的表示，每个缓冲区对应一个 struct buffer_head。缓冲区头描述块的状态：脏、上锁、映射的设备与块号、对应的内存页。2.6 中缓冲区头逐渐被 bio 结构取代，bio 更灵活高效。

14.3

bio 结构体

14.3.1I/O 向量
  • struct bio 是块 I/O 层的核心结构，表示一次块 I/O 操作
  • 使用 bio_vec 数组（I/O 向量）描述操作涉及的页、偏移、长度
  • 支持分散-聚集 I/O，一个 bio 可包含多个不连续的内存页
  • bi_sector：起始扇区号；bi_size：总字节数；bi_rw：读写方向
14.3.2新老方法对比
  • buffer_head 代表单个缓冲区，bio 代表一次 I/O 操作（可能多个块、多个页）
  • bio 更轻量，不需要每个块都一个头结构，减少开销
  • bio 支持高端内存页，便于实现直接 I/O 和 DMA
14.4

请求队列

块设备维护一个 request_queue 请求队列，存放待处理的 I/O 请求。I/O 调度程序从队列中取出请求并排序、合并后提交给设备。每个请求（struct request）可能包含多个 bio（合并结果）。

14.5

I/O 调度程序

14.5.1I/O 调度程序的工作
  • 将随机 I/O 请求排序、合并，减少磁头寻道时间，提升吞吐量
  • 两类操作：合并（merge）相邻请求、排序（sort）按扇区号排列
  • 也需要考虑公平性和饥饿问题
14.5.2Linus 电梯
  • 2.4 内核的默认调度器，以扇区排序为核心
  • 存在写者饥饿读的问题
14.5.3最终期限 I/O 调度（Deadline）
  • 读/写分别维护排序队列和 FIFO 到期队列
  • 读请求到期时间 500ms，写请求 5s，防止长期得不到服务
  • 适合数据库等对延迟敏感的读密集负载
14.5.4预测 I/O 调度（Anticipatory）
  • 在 Deadline 基础上增加预测：完成一个读后短暂等待，预测会有相邻读到来
  • 对随机读密集型工作负载（如数据库）有显著吞吐量提升
  • 预测错误则损失性能
14.5.5完全公正排队 CFQ
  • 为每个进程维护独立的 I/O 队列，按时间片轮转调度
  • 提供进程级别的 I/O 公平性，类似进程调度的 CFS
  • 是多数桌面发行版的默认调度器
14.5.6空操作 Noop
  • 只做简单合并，不排序，按 FIFO 处理
  • 适用于 SSD、RAM 盘等随机访问性能与顺序相近的设备
14.5.7调度程序的选择
  • 机械盘 → Deadline / CFQ / Anticipatory
  • SSD 等随机访问设备 → Noop
  • 桌面交互 → CFQ；数据库 → Deadline
CH 15

进程地址空间

15.1

地址空间

每个进程有独立的虚拟地址空间，32 位下 4GB（用户 3GB + 内核 1GB），64 位下更大。虚拟地址通过页表映射到物理地址，实现内存隔离与保护。地址空间由多个虚拟内存区域（VMA）组成：代码段、数据段、堆、栈、mmap 区等。

15.2

内存描述符

15.2.1mm_struct 结构
  • struct mm_struct：进程地址空间的核心描述结构
  • 包含：mmap（VMA 链表）、mm_rb（VMA 红黑树）、pgd（页全局目录）
  • mm_users（使用计数）、mm_count（引用计数）
  • start_code/end_code、start_data/end_data、start_brk/brk（堆）、start_stack
15.2.2撤销内存描述符
  • mm_count 降为 0 时释放 mm_struct 及相关资源（页表、VMA 等）
  • 由 mmput() 和 exit_mmap() 完成
15.2.3mm_struct 与内核线程
  • 内核线程没有用户地址空间，mm 为 NULL
  • 内核线程运行时借用上一个用户进程的页表（active_mm），减少 TLB 刷新
15.3

虚拟内存区域 VMA

15.3.1VMA 标志
  • struct vm_area_struct：描述一段连续的虚拟地址区间
  • vm_start / vm_end：区间起止地址
  • vm_flags：访问属性（VM_READ / VM_WRITE / VM_EXEC / VM_SHARED / VM_PRIVATE 等）
15.3.2VMA 操作
  • vm_operations_struct：VMA 的操作函数表
  • open / close：VMA 被复制或删除时调用
  • fault：缺页异常处理，当访问未映射页时由内核调用，负责填充页
15.3.3树结构与链表结构
  • mmap 链表按地址排序，便于遍历
  • mm_rb 红黑树按地址索引，便于快速查找某个地址所属 VMA（O(log n)）
  • 两种结构并存，分别适合不同访问模式
15.3.4实际使用中的内存区域
  • 典型分布：代码段、数据段（data/bss）、堆、文件映射区、栈、动态库、共享内存等
  • /proc/<pid>/maps 可查看进程的 VMA 布局
15.4

操作内存区域

15.4.1find_vma()
  • 查找给定地址所在或之后第一个 VMA
  • 优先在红黑树中查找，O(log n)
15.4.2find_vma_prev()
  • 在 find_vma 基础上同时返回前一个 VMA
15.4.3find_vma_intersection()
  • 查找与给定地址区间有任何重叠的第一个 VMA
15.5

mmap() / do_mmap()

mmap() 系统调用：在进程地址空间中创建或扩展一个 VMA。内核实现为 do_mmap()，负责分配虚拟地址并建立 VMA。支持文件映射（MAP_SHARED / MAP_PRIVATE）与匿名映射（MAP_ANONYMOUS）。

15.6

munmap() / do_munmap()

从地址空间中移除指定范围的 VMA，可能分割相邻 VMA。同时负责释放对应的物理页和页表项。

15.7

页表

虚拟地址到物理地址的映射表，分级结构（PGD → PUD → PMD → PTE，具体分级取决于架构）。每个 PTE 项包含物理页帧号和权限/状态位（存在、读写、用户、脏、访问等）。TLB（转译后备缓冲器）缓存页表项，加速地址翻译。

CH 16

页高速缓存和页回写

16.1

缓存手段

16.1.1写缓存
  • 页高速缓存（page cache）将磁盘文件内容缓存在内存中，减少磁盘 I/O
  • 写缓存策略：通写、回写、不缓存
  • Linux 使用回写策略：写操作直接写缓存，标记为脏，稍后异步刷回磁盘
16.1.2缓存回收
  • 内存不足时，回收干净的缓存页或将脏页写回后回收
  • LRU 策略的变体：双链活动/不活动链表
  • kswapd 内核线程负责在内存水位线以下时触发回收
16.2

Linux 页高速缓存

16.2.1address_space 对象
  • struct address_space：页高速缓存的核心对象，关联一个 inode 的所有缓存页
  • 每个 inode 有一个 i_mapping 指向 address_space
  • 包含 page_tree（页缓存的基树）、nrpages（缓存页数）、a_ops（操作方法表）等
16.2.2address_space 操作
  • readpage() / writepage()：从磁盘读 / 写回单页
  • readpages() / writepages()：批量读写
  • set_page_dirty()：标记页为脏
  • bmap()：逻辑块号到物理块号映射
16.2.3基树 radix tree
  • 页缓存在 address_space 中以 radix tree（基树）组织
  • 键是文件内偏移（页索引），值是 page 指针
  • 支持快速查找、插入、删除，O(1) 级别的树高（固定深度）
  • 可在节点中标记脏页、写回页等状态，便于批量查找
16.2.4以前的页散列表
  • 早期内核用全局哈希表管理页缓存，查找效率低且扩展性差
  • 2.6 起改用 per-inode 的 radix tree，大幅提升性能与扩展性
16.3

缓冲区高速缓存

buffer cache 缓存块设备的原始块，与页缓存部分重叠。2.4 之前 buffer cache 独立存在，2.6 中以 buffer_head 的形式依附在页缓存上。文件元数据（如 inode 块）通过 buffer cache 访问。

16.4

flusher 线程

16.4.1回写触发时机
  • 空闲内存低于阈值时：flusher 线程将脏页写回磁盘，腾出可回收页
  • 脏页驻留时间超过阈值时：定期写回，避免数据长期停留在内存
  • 用户调用 sync() / fsync() 时：显式触发回写
16.4.2历史演进
  • bdflush + kupdated：早期单线程回写机制
  • pdflush：2.6 早期多线程回写，数量动态调整
  • flusher threads：2.6.32 后引入，每个设备独立回写线程
16.4.3避免拥塞：多线程
  • flusher 线程按设备维度分布，不同设备的回写互不阻塞
  • 每个 flusher 线程对应一个 backing_dev_info
  • 遇到设备拥塞时跳过，防止 I/O 堆积
16.4.4膝上型计算机模式
  • laptop_mode：笔记本节能模式，尽量合并 I/O，减少磁盘唤醒次数
  • 延长回写间隔，将更多脏页集中一次刷写，降低功耗
CH 17

设备与模块

17.1

设备类型

字符设备：按字节流顺序访问，如串口、终端、键盘。块设备：以块为单位随机访问，如硬盘、U盘。网络设备：通过 socket 接口访问，对应网络接口（eth0 等）。主设备号标识设备类型，次设备号标识同类型的具体设备实例。

17.2

模块

17.2.1Hello World
  • Linux 内核模块是可动态加载到内核的代码片段，扩展内核功能无需重新编译
  • 最小模块：module_init() 入口、module_exit() 出口、MODULE_LICENSE() 等元信息
17.2.2构建模块
  • 编写 Makefile，使用 make -C <kernel_src> M=$PWD modules 编译
  • 依赖内核头文件和配置，必须与目标内核版本/配置匹配
17.2.3安装模块
  • make modules_install 将模块安装到 /lib/modules/$(uname -r)/
17.2.4模块依赖性
  • depmod 命令分析模块间依赖，生成 modules.dep 文件
  • modprobe 可自动加载依赖的模块
17.2.5载入模块
  • insmod：加载单个模块（不处理依赖）
  • modprobe：智能加载，自动加载依赖
  • rmmod：卸载模块（需无引用）
  • modprobe -r：卸载模块及未使用的依赖
17.2.6管理配置选项
  • 模块对应内核配置项（tristate：y 编译进内核 / m 编译为模块 / n 不编译）
17.2.7模块参数
  • 使用 module_param(name, type, perm) 定义可从外部传入的参数
  • 加载时通过 insmod mod.ko param=value 设置
17.2.8导出符号表
  • EXPORT_SYMBOL(sym)：导出符号，其他模块可使用
  • EXPORT_SYMBOL_GPL(sym)：仅 GPL 许可模块可使用
  • 未导出的符号模块无法调用，限制模块可用的内核 API 范围
17.3

设备模型

17.3.1kobject
  • struct kobject：设备模型的基础对象，提供引用计数、父子关系、名称等
  • 通常嵌入在更大的结构中（如 device、device_driver、bus_type）
  • 对应 sysfs 中的一个目录
17.3.2ktype
  • struct kobj_type：kobject 的类型描述，定义默认属性、析构函数等
  • 同类 kobject 共享同一个 ktype
17.3.3kset
  • struct kset：kobject 的集合，相当于同类 kobject 的容器
  • kset 自身也包含一个 kobject，可以被纳入 sysfs 层级
17.3.4三者的相互关系
  • kobject 是基本单元，ktype 描述类型，kset 是集合/容器
  • kset 决定 kobject 在 sysfs 中的父节点位置，ktype 决定属性和行为
17.3.5管理和操作 kobject
  • kobject_init() 初始化，kobject_add() 加入 sysfs，kobject_del() 移除
17.3.6引用计数
  • kobject 内嵌 kref 引用计数
  • kobject_get() 引用 +1，kobject_put() 引用 -1，减到 0 时调用释放函数
17.4

sysfs

17.4.1添加和删除 kobject
  • sysfs 是挂载在 /sys 的虚拟文件系统，展示设备模型的层级关系
  • kobject_add 自动在 sysfs 中创建目录，kobject_del 删除
  • 目录结构：devices/、bus/、class/、block/、firmware/ 等
17.4.2向 sysfs 添加文件
  • kobject 对应目录，属性（attribute）对应目录中的文件
  • 通过 sysfs_create_file() 创建属性文件，每个属性有 show 和 store 方法
  • 用户读写这些文件即与内核交互，替代部分 ioctl 功能
17.4.3内核事件层 uevent
  • uevent：内核向用户空间发送设备热插拔等事件
  • 通过 netlink 或 uevent_helper（/sbin/hotplug）通知用户空间
  • udev 守护进程监听这些事件，动态管理 /dev 下的设备节点
CH 18

调试

18.1

准备开始

内核调试比用户程序困难：没有保护、崩溃影响全局、复现条件可能复杂。开发前应启用内核调试配置，准备好源码与符号表。保持代码整洁、多用断言、加锁规范，从源头减少 bug。

18.2

内核中的 bug

常见类型：空指针引用、死循环、死锁、越界访问、竞态条件、内存泄漏。表现：oops、panic、死机、性能下降、数据损坏。定位难度从简单（有 oops 栈）到极难（偶发竞态）不等。

18.3

通过打印来调试

18.3.1健壮性
  • printk() 是内核最基本的调试手段，任何上下文都可调用
  • 有日志缓冲区，不会丢失；并发安全，可在中断或进程上下文调用
18.3.2日志等级
  • 8 个等级，从高到低：KERN_EMERG（0）、KERN_ALERT（1）、KERN_CRIT（2）、
  • KERN_ERR（3）、KERN_WARNING（4）、KERN_NOTICE（5）、KERN_INFO（6）、KERN_DEBUG（7）
  • 低于 console_loglevel 的消息才会输出到控制台
18.3.3记录缓冲区
  • 内核日志存放在环形缓冲区中，大小可配置
  • 通过 syslog 系统调用或 /proc/kmsg 读取
  • dmesg 命令可查看内核日志
18.3.4syslogd 和 klogd
  • klogd：读取内核消息并转发给 syslogd
  • syslogd：收集系统日志，写入 /var/log/messages 等文件
18.3.5printf 到 printk 的转换
  • printk 支持格式符大部分与 printf 相同，但有差异（%pF 打印符号名、%zd 等）
  • printk 不会使用浮点；注意每行加换行符和日志级别前缀
18.4

oops

oops 是内核报告的严重错误信息，通常由访问非法地址等异常触发。内容包括：错误地址、错误码、寄存器值、栈回溯（call trace）。是定位内核崩溃最重要的线索。

18.4.1ksymoops
  • 老工具，将 oops 中的十六进制地址翻译成符号名，需配合 System.map
  • 已被 kallsyms 取代
18.4.2kallsyms
  • CONFIG_KALLSYMS：编译时将所有内核符号表编入内核
  • oops 时可直接打印符号名，无需外部工具翻译
18.5

内核调试配置选项

常用调试配置：CONFIG_DEBUG_KERNEL 总开关、CONFIG_DEBUG_SLAB slab 调试、CONFIG_DEBUG_PAGEALLOC 页分配调试、CONFIG_DEBUG_PREEMPT 抢占调试、CONFIG_DEBUG_SPINLOCK 自旋锁调试、CONFIG_KGDB 内核 GDB 支持、CONFIG_LOCKDEP 死锁检测。

18.6

引发 bug 并打印信息

BUG() / BUG_ON(cond)：触发 oops，用于不应发生的情况。WARN() / WARN_ON(cond)：打印警告和栈回溯，但不崩溃。panic()：更严重，直接使内核崩溃并停止运行。

18.7

神奇的系统请求键

Magic SysRq 键（Alt + SysRq + 功能键），即使系统半挂也可触发。功能：r（重新接管键盘）、e（终止所有进程）、i（杀掉所有进程）、s（同步磁盘）、u（重新挂载所有文件系统为只读）、b（立即重启）。经典救援组合：reisub。

18.8

内核调试器

18.8.1gdb
  • 可用 gdb 读取 vmlinux 符号，分析 oops、查看变量结构
  • 但无法像用户程序那样设置断点、单步运行（没有 kgdb 时）
18.8.2kgdb
  • 内核 GDB 存根，通过串口或网口连接宿主机 gdb
  • 支持断点、单步、查看内存/寄存器，是真正的内核源码级调试
  • 需要两台机器（目标机 + 调试机）和对应配置
18.9

探测系统

18.9.1用 UID 作为选择条件
  • 通过当前进程 UID 控制调试代码是否执行，实现部分用户触发的条件调试
18.9.2使用条件变量
  • 全局变量作为调试开关，可通过 proc/sysfs 或 gdb 动态修改
18.9.3使用统计量
  • 计数器、直方图等统计手段，用于分析性能问题或异常分布
  • per-CPU 计数器减少竞态开销
18.9.4重复频率限制
  • 调试信息太多会刷屏或拖慢系统，使用 printk_ratelimit() 限制频率
18.10

二分查找法定位变更

当 bug 是某个版本引入时，用二分法在版本历史中定位首个出问题的提交。对数级次测试即可定位，非常高效。

18.11

使用 Git 进行二分搜索

git bisect start 开始二分。git bisect bad 标记当前版本有 bug。git bisect good <rev> 标记某旧版本正常。git 自动跳到中间版本，测试后标记 good/bad，直到锁定第一个坏提交。

18.12

求助社区

无法定位时，可将问题和分析发到相应的内核邮件列表求助。提供完整信息：内核版本、架构、配置、oops 信息、复现步骤、已做分析。发往正确的子系统列表而不是全部抄送，回复率更高。

CH 19

可移植性

19.1

可移植操作系统

Linux 支持数十种架构：x86、x86-64、ARM、PowerPC、MIPS、SPARC、IA-64、s390 等。良好的可移植性是 Linux 的重要优势，代码分层清晰。通用代码放在 kernel/、mm/、fs/ 等目录，架构相关代码放在 arch/<arch>/。

19.2

Linux 移植史

最初只支持 x86，早期端口到 Alpha、SPARC、M68k、PowerPC。随后扩展到更多架构，嵌入式领域（ARM、MIPS）占比越来越大。每个架构有自己的 arch 目录，维护底层代码。

19.3

字长和数据类型

19.3.1不透明类型
  • 内核使用大量 typedef 隐藏架构差异：pid_t、uid_t、size_t、ssize_t 等
  • 使用这些类型，不要假设其底层宽度
19.3.2指定数据类型
  • C 标准类型的宽度在不同平台可能不同（long 在 32 位是 4B，64 位是 8B）
  • 明确需要特定大小时使用 u8/u16/u32/u64 及对应有符号类型
19.3.3长度明确的类型
  • <linux/types.h> 中定义：__u8、__u16、__u32、__u64 及有符号版
19.3.4char 型的符号问题
  • char 在不同架构上可能是有符号或无符号的（x86 通常有符号，ARM 默认无符号）
  • 需要明确符号时使用 signed char 或 unsigned char
19.4

数据对齐

19.4.1避免对齐引发的问题
  • 某些架构（如 ARM、MIPS）不支持非对齐访问，会触发异常或得到错误结果
  • x86 虽支持非对齐访问但性能下降
  • 编写可移植代码时始终保证数据自然对齐
19.4.2非标准类型的对齐
  • 复杂类型（结构体）的对齐遵循其最严格成员的对齐要求
  • 编译器自动处理，但手动操作内存时要注意
19.4.3结构体填补
  • 为满足对齐要求，编译器可能在结构体成员之间插入填充字节（padding）
  • 不同架构/编译器填充方式可能不同，跨架构交换结构时要小心
  • 使用 __attribute__((packed)) 可禁止填充（但可能降低性能）
19.5

字节顺序

大端：高字节存低地址（网络字节序、PowerPC 部分模式）。小端：低字节存低地址（x86、ARM 多数模式）。内核提供转换宏：cpu_to_le32()、le32_to_cpu()、cpu_to_be32() 等。

19.6

时间

不要假设 HZ 值，使用 jiffies 和 HZ 宏换算时间。墙上时间用 struct timespec 或 struct timeval。高分辨率时间用 ktime_t。

19.7

页长度

页大小因架构而异（4KB、8KB、16KB、64KB 等）。使用 PAGE_SIZE 宏、PAGE_SHIFT、PAGE_MASK，不要硬编码。按页对齐用 PAGE_ALIGN() 等宏。

19.8

处理器排序

不同架构的内存排序模型不同：x86 是强有序（TSO），ARM/PowerPC 是弱有序。需要内存顺序时使用内存屏障（rmb/wmb/mb 等）。SMP 版本的屏障在 UP 上是空操作，保证可移植且无额外开销。

19.9

SMP、抢占、高端内存

代码应同时考虑 SMP 和 UP、有抢占和无抢占、有高端内存和无高端内存的情况。使用内核提供的抽象（如 smp_* 屏障、preempt_disable、kmap 等）自动适配。避免依赖特定配置假设，保证在不同配置下都能正确工作。

CH 20

补丁、开发和社区

20.1

社区

Linux 内核是全球最大的开源协作项目之一，数千名开发者参与。主要沟通渠道是邮件列表（LKML 及各子系统列表）。子系统维护者各自管理其 tree，经 -next 树整合后进入 Linus 的主线树。开发流程：讨论 → 补丁 → review → 合入子系统 tree → 合入主线。

20.2

Linux 编码风格

20.2.1缩进
  • 使用 8 字符宽的 tab 缩进，不用空格
  • 理由：让嵌套层级一目了然，鼓励减少嵌套深度
20.2.2switch 语句
  • switch 的 case 标签与 switch 对齐（缩进同一层级），不额外缩进
20.2.3空格
  • 关键字后加空格：if、switch、case、for、while、return 等
  • 函数名后不加空格；二元运算符两侧加空格
20.2.4花括号
  • 函数的花括号另起一行；非函数语句的左花括号同行
  • 右花括号单独一行；else 与右花括号同行（K&R 风格）
  • 只有一行的语句块也要加花括号（避免后续扩展出错）
20.2.5每行代码长度
  • 建议不超过 80 字符（传统限制，源自终端宽度）
  • 超过时合理换行，保持可读性
20.2.6命名规范
  • 变量、函数用小写 + 下划线（snake_case），不用驼峰
  • 名称要描述性强，避免匈牙利命名法或含糊缩写
20.2.7函数
  • 函数应短小精悍，做一件事且做好
  • 函数退出点集中，使用 goto 跳转到统一清理处是常见模式
20.2.8注释
  • 注释描述代码做什么、为什么做，而不是怎么做
  • 使用 C 风格块注释，不用 C++ 行注释
20.2.9typedef
  • 尽量避免 typedef 隐藏指针或结构体，除非是不透明类型
  • 理由：降低可读性，调试时不便
20.2.10多用现成的东西
  • 不要重复造轮子：内核已有链表、红黑树、哈希表、分配器等通用基础设施
  • 优先使用内核提供的 API，保持代码风格一致且经过验证
20.2.11减少使用 ifdef
  • 尽量把条件编译放到头文件或独立的编译单元，而不是在 .c 文件里随处 ifdef
  • 过多 ifdef 降低可读性和可维护性
20.2.12结构初始化
  • 使用 C99 风格的指定初始化器（designated initializer）
  • 清晰、可扩展，新增字段时不易遗漏
20.2.13代码的事后修正
  • 内核代码永远在演进，随时可以提交改进补丁（清理、优化、修复）
  • 保持代码整洁本身就是贡献
20.3

管理系统

使用 Git 作为版本控制系统，配合邮件列表协作。各子系统有自己的 git 仓库和维护者，定期发 pull request 给 Linus。linux-next 树整合各子系统的 pending 补丁，提前暴露集成问题。

20.4

提交错误报告

发现 bug 时，报告给正确的邮件列表（对应子系统维护者）。包含：内核版本、架构、配置、详细复现步骤、oops 或警告信息、期望行为。信息越完整，被关注和修复的概率越高。

20.5

补丁

20.5.1创建补丁
  • 补丁应只做一件事，尽量原子化，便于 review 和回退
  • 每个补丁附带清晰的变更说明（Subject + body）
  • 注意：不要修改与本次变更无关的内容（如空格清理与功能修改分开）
20.5.2用 Git 创建补丁
  • git format-patch 生成标准补丁邮件（含提交信息、署名等）
  • Signed-off-by: 开发者签名，表示开发者对补丁的来源和合规性负责
  • 提交前用 git diff 检查变更，用 checkpatch.pl 脚本检查风格
20.5.3提交补丁
  • 将补丁邮件发送到对应子系统的邮件列表，抄送维护者
  • 在邮件正文简要说明背景、变更内容、测试情况
  • 根据 review 反馈迭代更新补丁（v2、v3...），直到合入
  • 首次贡献可从简单的清理、修复开始，逐步建立信誉
