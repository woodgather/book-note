1.1 系统架构

1.1.1 Android 系统架构

四层架构（自下而上）
① Linux 内核层
  • 包含 Linux 内核及驱动（USB / Camera / 蓝牙等）
  • 本书以 Android 2.2（Froyo）/ Linux 2.6 为蓝本
② Libraries 层（Native）
  • 动态库（共享库）+ Android 运行时库 + Dalvik 虚拟机
  • 以 C/C++ 为主，可视为 Native 层
③ Framework 层（Java）
  • Android 平台 Java 世界的基石
  • zygote、SystemServer、Handler/Looper 等
④ Applications 层
  • 与用户直接交互的应用（Java 实现）
  • 典型代表：MediaProvider、Phone
核心观点：Android 表面是 Java 世界，底层依赖 Google 隐藏的 Native 世界。Java 经由 JNI 通过 IPC（Binder / Socket）与 Native 交互。

1.1.2 本书的架构

  • Nativeinit、Audio（Track/Flinger/PolicyService）、Surface（SurfaceFlinger）、RefBase/sp/wp、Vold、Rild
  • Java Frameworkzygote、SystemServer、Handler/Looper
  • Java ApplicationMediaProvider、Phone

2.1 JNI 概述

  • JNI = Java Native Interface，中文"Java 本地调用"
  • Java 函数可调用 Native（C/C++）函数，反之亦然
  • 存在的意义：
    • 承载 Java 的虚拟机本身由 Native 实现，JNI 屏蔽不同 OS 差异（如 Windows 的 OpenFile vs Linux 的 open）
    • 复用已有 Native 模块、追求效率/速度的场合
Android 平台上 JNI 即是连接 Java 与 Native 世界的"桥梁"，没有它将寸步难行。

2.2 学习 JNI 的实例：MediaScanner

选择 MediaScanner 作为实例的原因：

  • Java 框架层调用 → JNI → Native 实现 → 媒体库 → ContentProvider，跨层完整
  • 代码量适中，逻辑清晰

2.3 Java 层的 MediaScanner 分析

2.3.1 加载 JNI 库

static {
    System.loadLibrary("media_jni");   // 加载 libmedia_jni.so
}

2.3.2 Java 的 native 函数和总结

  • native_init()：构造 Native 层 MediaScanner 对象，缓存字段 ID
  • processFile(String path, String mimeType, MediaScannerClient client)：处理单个文件
  • processDirectory(String path, String extensions, MediaScannerClient client)：处理目录
  • 小结：Java 层职责薄，主要把请求透传到 JNI 层

2.4 JNI 层 MediaScanner 的分析

对应文件：android_media_MediaScanner.cpp

2.4.1 注册 JNI 函数

两种注册方式：

① 静态注册（默认）
  • 函数命名规则：Java_包名_类名_方法名
  • 依赖包路径，反编译即可看到
② 动态注册（RegisterNatives）
  • JNINativeMethod 数组 + RegisterNatives
  • 灵活性高、可读性更好、本书重点

2.4.2 数据类型转换

  • 基本类型：jint ↔ int、jlong ↔ long 等
  • 引用类型：jobject、jclass、jstring、jarray 等
  • 使用原则：明确生命周期，避免内存泄漏

2.4.3 JNIEnv 介绍

  • JNIEnv* 是线程局部存储，指向函数表指针
  • Native 方法第一个参数都是 JNIEnv*
  • 通过它调用 JNI 函数（如 FindClass、GetMethodID）

2.4.4 通过 JNIEnv 操作 jobject

  • 获取字段：GetFieldID + Get<Type>Field
  • 设置字段：Set<Type>Field
  • 调用方法：Call<Type>Method / CallStatic<Type>Method

2.4.5 jstring 介绍

  • GetStringUTFChars：获取 UTF-8 字符指针
  • ReleaseStringUTFChars：必须成对释放
  • GetStringChars / ReleaseStringChars：Unicode 形式
  • NewStringUTF / NewString：创建 Java 端 String

2.4.6 JNI 类型签名介绍

Java 类型    签名
-------------------------
byte        B
char        C
short       S
int         I
long        J
float       F
double      D
boolean     Z
void        V
对象         L<完整类名>;
数组         [类型

2.4.7 垃圾回收

  • JNI 中通过 NewLocalRef / NewGlobalRef 控制引用
  • Local 引用：方法返回后自动释放
  • Global 引用：跨方法/跨线程使用，需 DeleteGlobalRef 释放
  • Weak 引用：NewWeakGlobalRef，不阻止 GC

2.4.8 JNI 中的异常处理

  • 检查：ExceptionCheck / ExceptionOccurred
  • 抛出：Throw / ThrowNew
  • 清除：ExceptionClear
  • JNI 中抛出异常不会自动返回，需手动检查并处理

第 3 章 · 深入理解 init

init 是 Android 用户空间的第一个进程（PID=1），负责孵化关键进程（如 zygote）和提供 property service。
本章目录
  1. 3.1 概述
  2. 3.2 init 分析

3.1 概述

  • init 负责孵化关键进程（尤其 zygote）
  • init 提供 property service（属性服务）统一管理系统属性

3.2 init 分析

3.2.1 解析配置文件

  • 主配置文件：init.rc（system/core/rootdir/init.rc）
  • 解析入口：init_parse_config_file，使用关键字表 keywords.h
  • 四种关键语句：
    • Action：on <trigger> 触发条件
    • Command：Action / Service 中的命令
    • Service：service <name> <path> [args] 启动守护进程
    • Option：Service 的属性（class、socket 等）

3.2.2 解析 service

  • service_start → fork → 子进程 execve
  • Service 结构体记录 name、path、args、pid、flags、sockets 等
  • 通过 class_start default 启动一类服务

3.2.3 init 控制 service

  • SIGCHLD 信号触发 sigchld_handler，回收僵尸进程
  • 通过 restart_on_failure 等机制重启服务
  • write_file、chmod 等 builtins 工具

3.2.4 属性服务

  • 实现文件：properties_service.c、properties.c
  • 服务端：init 创建 socket 监听客户端的 set/get 请求
  • 客户端 API：property_set、property_get
  • 属性区域（prop 区）：init 启动时从 /default.prop 等文件加载
  • 关键点：只有 init 进程可写，其他进程通过 socket 请求修改
关键流程：init.rc 中 on boot 触发 class_start core → 启动 service_manager、zygote、media 等服务。

4.2 zygote 分析

4.2.1 AppRuntime 分析

  • zygote 进程入口：app_main.cpp
  • AppRuntime 继承 AndroidRunTime，负责创建虚拟机、调用 CallMain

4.2.2 Welcome to Java World

  • 调用 startVM 创建 Dalvik 虚拟机
  • 注册 JNI 函数
  • 调用 ZygoteInit.main 进入 Java 世界

4.2.3 关于 zygote 的总结

  • zygote 是 Native 与 Java 的"接驳点"
  • 预加载常用类与资源（preloadClasses、preloadResources）以加速 fork

4.3 SystemServer 分析

4.3.1 SystemServer 的诞生

  • zygote 通过 forkSystemServer 创建 SystemServer 进程
  • 启动类路径：com.android.server.SystemServer

4.3.2 SystemServer 的重要使命

  • 启动核心服务（线程）：
    • ActivityManagerService (AMS)
    • WindowManagerService (WMS)
    • PackageManagerService (PMS)
    • PowerManagerService、BatteryService 等
  • 通过 ServiceManager.addService 注册到 Binder 大管家

4.3.3 关于 SystemServer 的总结

SystemServer 是 Android Framework 的"总装车间"，几乎所有 Java 层服务都在这里完成启动。

4.4 zygote 的分裂

4.4.1 ActivityManagerService 发送请求

  • AMS 通过 Process.start → Process.startViaZygote
  • 将启动参数打包成 socket 消息发给 zygote

4.4.2 有求必应之响应请求

  • zygote 监听 socket：ZygoteInit.runSelectLoop
  • 读取参数后调用 ZygoteConnection.runOnce
  • 核心：forkAndSpecialize（普通应用） / forkSystemServer（系统服务）

4.4.3 关于 zygote 分裂的总结

所有 Java 进程（含应用）几乎都源于 zygote 的 fork。这种方式天然共享已加载的类与资源，启动快。

4.5 拓展思考

4.5.1 虚拟机 heapsize 的限制

  • dalvik.vm.heapgrowthlimit：普通应用上限
  • dalvik.vm.heapsize：系统进程上限
  • 大内存应用需在 manifest 声明 largeHeap="true"

4.5.2 开机速度优化

  • 优化 init.rc 中服务启动顺序与并发度
  • 精简预加载类（preloaded-classes）
  • 使用 read-ahead、dm-verity 优化 IO

4.5.3 Watchdog 分析

  • 位于 system_server 中，定期检查关键线程
  • 如果主线程 Looper 卡住 > 30s，抓取 trace 并重启系统

5.2 以"三板斧"揭秘 RefBase、sp 和 wp

Android 智能指针借鉴 C++ 11 的 shared_ptr / weak_ptr。

5.2.1 第一板斧——初识影子对象

  • 每个 RefBase 子类内部持有一个 weakref_impl（影子对象）
  • 影子对象统一管理 强引用计数（mStrong）和 弱引用计数（mWeak）

5.2.2 第二板斧——由弱生强

  • wp::promote() → weakref_type::promote() 尝试升级为 sp
  • 目标对象未死时返回有效 sp；已死时返回空 sp

5.2.3 第三板斧——破解生死魔咒

  • 当强引用计数归零，触发 onLastWeakRef → onLastStrongRef → delete
  • 通过 extendObjectLifetime(OBJECT_LIFETIME_WEAK) 等策略可调整生命周期

5.2.4 轻量级引用计数控制类 LightRefBase

  • 不区分强弱，仅一个原子计数；开销最小
  • 适合线程局部、不需要 weak 引用的对象

5.2.5 题外话——三板斧的来历

作者受武侠文化启发，把"看影子—升级—判生死"的过程形象化为三板斧。

5.3 Thread 类及常用同步类分析

5.3.1 一个变量引发的思考

  • 多线程下 ++i 不是原子操作，需要互斥
  • 引出 Mutex、Condition、Semaphore 等同步原语

5.3.2 常用同步类

Mutex（互斥锁）
  • Mutex::Autolock 利用 RAII 自动加解锁
  • 不可重入（线程内重复 lock 会死锁）
Condition（条件变量）
  • wait / waitRelative / signal
  • 必须与 Mutex 配合使用
Semaphore（信号量）
  • 基于计数的同步，适合生产者-消费者
Barrier（栅栏）
  • 所有线程到达后一起放行

5.4 Looper 和 Handler 类分析

5.4.1 Looper 类分析

  • 一个线程最多一个 Looper，通过 prepare 创建
  • 核心循环：loopOnce → pollOnce → epoll_wait
  • getMainLooper 返回主线程 Looper

5.4.2 Handler 分析

  • 绑定 Looper + MessageQueue
  • sendMessage / post(Runnable) 入队
  • dispatchMessage 分发到 callback / handleMessage

5.4.3 Looper 和 Handler 的同步关系

  • Handler 与 Looper 不必同线程，但操作 MessageQueue 时需 epoll 唤醒
  • Native 层有对应 Looper（用于无 Java 线程的轮询）

5.4.4 HandlerThread 介绍

  • 封装"启动线程 + 准备 Looper"的工具类
  • 对外提供 getLooper 让其他 Handler 投递消息

  • 每个进程一个 ProcessState（单例）
  • 负责打开 binder 设备、内存映射（mmap）、管理线程池

6.2.3 时空穿越魔术——defaultServiceManager

  • ServiceManager 本身是 Binder 服务，无注册地址
  • 通过特殊句柄 0 拿到 ServiceManager 代理（BpServiceManager）

6.2.4 注册 MediaPlayerService

  • 实例化 MediaPlayerService 并调用 addService
  • 内部通过 IPCThreadState::self() 发送 BC_TRANSACTION

6.2.5 StartThreadPool 和 joinThreadPool

  • startThreadPool 启动工作线程，循环 talkWithDriver
  • joinThreadpool 阻塞等待 binder 事件

6.2.6 你彻底明白了吗

通过 MediaServer 流程梳理"打开 binder 设备 → 注册服务 → 启动线程池 → 进入循环"四步曲。

6.3 服务总管 ServiceManager

6.3.1 ServiceManager 的原理

  • 独立进程 /system/bin/servicemanager
  • 维护 svclist（服务列表），提供 addService / checkService

6.3.2 服务的注册

  • 服务进程通过 binder 句柄 0 调用 SVC_MGR_ADD_SERVICE
  • ServiceManager 写入 svclist，赋予唯一句柄

6.3.3 ServiceManager 存在的意义

  • 是服务的"黄页"，让 Client 按名字查找
  • 无中心目录则所有 Client 必须硬编码服务地址，扩展性差

6.4 MediaPlayerService 和它的 Client

6.4.1 查询 ServiceManager

  • Client 通过 defaultServiceManager()->checkService(name) 拿到远程代理 Bp

6.4.2 子承父业

  • MediaPlayer 客户端通过 Binder 代理跨进程调用 Server 方法
  • 最终由 BBinder::transact / BnMediaPlayerService 处理请求

6.5 拓展 / 6.6 学以致用

6.5.1 Binder 和线程的关系

  • Server 端一个 binder 实体可被多线程并发访问
  • 需要 IPCThreadState 保证线程安全

6.5.2 有人情味的讣告

当 Client 异常退出，Server 通过 linkToDeath / unlinkToDeath 收到死亡通知，释放资源。

6.5.3 匿名 Service

  • 不上报 ServiceManager，直接在进程间互传 binder 句柄

7.2.1 用例介绍
