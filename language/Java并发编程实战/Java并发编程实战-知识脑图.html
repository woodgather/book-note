第1章

简介

本章介绍了多线程编程的历史背景、线程带来的主要优势以及潜在风险。即使读者已熟悉线程相关的基本概念，仍需关注 1.4 节中关于"线程无处不在"的内容，因为随着框架与组件的广泛使用，线程问题会不经意地出现在日常开发中。

1.1并发简史

  • 操作系统的出现使计算机每次能运行多个程序，不同程序通过进程隔离。
  • 线程（Thread）允许同一个进程内同时存在多个程序控制流，是更细粒度的并发单元。
  • 线程共享进程范围内的资源（如内存句柄、文件句柄），因此编写/调试/测试难度更高。
  • Java 从诞生起就内置了对线程的支持，并提供跨平台的内存模型（从 Java 5.0 起重新修订）。

1.2线程的优势

发挥多处理器的强大能力
充分利用多核 CPU 提升吞吐。理论上多线程在多处理器上可线性提升计算速度，但需避免瓶颈（如频繁加锁）。
建模的简单性
将复杂异步流程分解为多个并发任务，使程序结构更贴近业务模型，提升可读性。
异步事件的简化处理
为每个请求分配独立线程，避免事件回调地狱；服务程序可同时处理多个连接。
响应更灵敏的用户界面
将耗时操作放入后台线程，UI 线程保持响应。AWT/Swing/SWT 通过事件分发线程实现。

1.3线程带来的风险

⚠️ 安全性问题：多线程下的竞态条件（Race Condition）可能导致错误的结果。最常见的表现是"读-改-写"操作被其他线程打断。
🔄 活跃性问题：包括死锁（Deadlock）、活锁（Livelock）、饥饿（Starvation）等，使线程无法继续执行。
⏱️ 性能问题：线程调度、上下文切换、同步开销等都会带来额外成本。需要权衡并发带来的收益。
  • 线程安全的核心目标：避免错误、保持活跃、保证性能。
    • 安全性（Safety）："不发生坏事"。
    • 活跃性（Liveness）："好事终将发生"。
    • 性能（Performance）："做事要快"。

1.4线程无处不在

  • 每个 Java 程序都会启动多个线程，包括主线程、垃圾回收线程、终结器线程等。
  • Timer、Servlet、JSP、RMI、Application Server（如 JBoss、Tomcat）都会自动创建线程池。
  • AWT/Swing 的事件分发线程、SwingUtilities.invokeLater 等是 UI 编程的基础。
  • 常用框架与组件的并发行为：
    • Timer：单线程执行所有任务，任务异常会影响后续任务。
    • Servlet/JSP：每个请求由 Servlet 容器中的某个线程处理，需注意共享资源。
    • RMI：远程方法调用、对象序列化、GC 都涉及后台线程。
    • Swing/AWT：事件分派线程（EDT）单线程处理所有 UI 事件。
PART 1

第一部分 · 基础知识

第2章至第5章。本部分将介绍并发性与线程安全性的基本概念，并讲解如何使用类库提供的基本并发构建块来构建线程安全的类。这些知识是后续所有内容的基础，建议在编写任何并发代码之前务必阅读。

第2章

线程安全性

线程安全性的核心是"对共享的可变状态进行正确的管理"。本章是全书的基石，几乎所有线程安全规则都源于这两章内容。

2.1什么是线程安全性

定义：当多个线程访问某个类时，不管运行时环境采用何种调度方式或者这些线程将如何交替执行，并且在主调代码中不需要任何额外的同步或协同，这个类都能表现出正确的行为，那么这个类就是线程安全的。
  • 无状态对象（如 Servlet 中无字段的服务方法）一定是线程安全的，因为它们不持有共享状态。
  • 线程安全性体现在"竞态条件不会发生在该对象上"。

2.2原子性

2.2.1 竞态条件

竞态条件（Race Condition）：由于不恰当的执行时序而出现不正确的结果。最常见类型是"先检查后执行"（Check-Then-act），如单例的延迟初始化。

2.2.2 示例：延迟初始化中的竞态条件

  • if (instance == null) { instance = new Instance(); } 看似安全，实则多个线程可能同时看到 instance == null，导致创建多个实例。
  • 可以通过 synchronized 或提前初始化（Eager Initialization）解决。

2.2.3 复合操作

  • 复合操作（Compound Action）：包含了一组必须以原子方式执行的复合操作。
  • Java 5.0 之后，可以使用 java.util.concurrent.atomic 包中的原子变量类（如 AtomicLong、AtomicReference）实现无锁的复合操作。
  • 使用 AtomicLong 替代 long + ++ 即可解决竞态条件。

2.3加锁机制

2.3.1 内置锁

  • Java 提供 synchronized 关键字支持内置锁（Monitor Lock）。每个 Java 对象都可以用作一个实现同步的锁。
  • synchronized 修饰方法或代码块时，线程进入前自动获得锁，退出时（无论是正常返回还是抛出异常）自动释放锁。
  • 内置锁是可重入的：同一线程可以多次获取同一把锁，避免了"自己死锁"的问题。

2.3.2 重入

  • 重入锁的粒度是"线程"，而不是"调用"。
  • 子类覆写父类的 synchronized 方法并调用 super.method() 是合法的，因为外层方法已持有锁。
  • 重入简化了面向对象并发代码的编写，但也可能导致某些设计问题（如外层方法持有锁后调用重写方法）。

2.4用锁来保护状态

  • 对于可能被多个线程同时访问的可变状态变量，在访问它时都需要持有同一个锁。
  • 每个共享的、可变的变量都应该只由一个锁来保护，从而使维护人员知道是哪一把锁。
  • 并非所有数据都需要锁保护：线程封闭（Thread Confinement）、只读共享（不可变对象）等方法可以避免加锁。
  • 常见错误：用 synchronized(this) 保护一个字段，但其他方法不通过锁来访问该字段。

2.5活跃性与性能

  • 通过缩小同步代码块的范围（"快进快出"），可以平衡安全性与性能。
  • 但简单性与性能之间是有冲突的，常常需要在这两者之间做权衡。优先保证正确性。
  • 同步的开销包括：锁获取/释放、线程调度、共享内存的同步（缓存刷新）等。
第3章

对象的共享

第2章讨论了如何防止线程在访问对象时看到不一致的状态。本章将讨论如何确保对象被正确地发布与共享，包括可见性、发布逸出、线程封闭、不可变对象等关键概念。

3.1可见性

可见性问题：某个线程对共享变量的修改，其他线程可能看不到。这是由现代处理器和编译器优化（指令重排序、缓存等）造成的。

3.1.1 失效数据

  • 在没有同步的情况下，线程可能读取到"过期"的值（Stale Data）。
  • 即使失效数据不会导致程序出错，活跃性问题（如意外的 NullPointerException）也可能发生。

3.1.2 非原子的 64 位操作

  • JVM 规范允许把 64 位的 double / long 变量读写分解为两个 32 位操作，因此可能读到"撕裂写"的高低位组合。
  • 使用 volatile 或加锁可以保证原子性。

3.1.3 加锁与可见性

  • 加锁不仅能保证互斥，还能保证内存可见性。锁的获取会强制从主内存重新读取数据，锁的释放会强制将数据写回主内存。

3.1.4 Volatile 变量

  • volatile 关键字提供了一种轻量级的同步机制：对该变量的写操作会立即刷新到主内存，读操作会从主内存重新加载。
  • 通常用作状态标志、一次性安全发布（one-time safe publication）等场景。
  • 使用条件：写入时不依赖变量的当前值，且变量不需要与其他状态变量共同参与不变性条件。
  • 加锁可以保证可见性与原子性；volatile 只能保证可见性。

3.2发布与逸出

发布（Publishing）：使对象能够在当前作用域之外的代码中使用。例如将引用保存到其他代码可以访问的地方，或者在非私有的方法中返回引用，或者通过其他线程发布。
逸出（Escape）：当某个不应该被发布的对象被发布时，就称为逸出。逸出会导致对象的状态被意外的修改，破坏封装性。
  • 常见的逸出场景：在构造函数中启动线程（this 引用被发布给新线程）、在构造函数中注册监听器等。
  • 原则：不要在构造函数中使 this 引用逸出。

3.3线程封闭

线程封闭（Thread Confinement）：把对象封闭在一个线程中，使得它天然线程安全，即使对象本身不是线程安全的。

3.3.1 Ad-hoc 线程封闭

  • 完全靠约定（如文档、注释）来维护线程封闭，非常脆弱，建议尽量少用。

3.3.2 栈封闭

  • 只能通过局部变量才能访问对象，本质上是栈封闭。局部变量天生封闭在线程中。
  • 对于基本类型的局部变量，无论如何都不会破坏栈封闭。

3.3.3 ThreadLocal 类

  • ThreadLocal 提供了线程级别的变量副本，每个线程独立拥有，互不影响。
  • 常见用途：JDBC 连接、Session、单实例的全局变量（避免传参）。
  • 注意：ThreadLocal 会持有对象引用，需谨慎避免内存泄漏（线程池中的 ThreadLocal 变量需在使用后清理）。

3.4不变性

不可变对象（Immutable Object）：对象创建后其状态不可修改。不可变对象一定是线程安全的。
  • 不可变对象满足条件：状态在创建后不可修改、所有字段都是 final、正确构造（无 this 逸出）。

3.4.1 Final 域

  • final 修饰的字段在构造完成后不可修改，JMM 保证 final 字段在构造函数结束后对其他线程可见（无需同步）。

3.4.2 示例：使用 Volatile 类型来发布不可变对象

  • 将对象的引用保存到 volatile 类型或者 AtomicReference 中，可以实现安全发布。
  • 每次发布时，发布一个新对象（如 VolatileCachedFactorizer 的方式），避免可变状态。

3.5安全发布

3.5.1 不正确的发布：正确的对象被破坏

问题：没有正确同步的对象引用，其他线程看到的对象可能处于不一致状态（部分构造）。即使在构造时使用了不变性条件，缺少同步也会破坏该条件。

3.5.2 不可变对象与初始化安全性

  • JMM 为共享不可变对象提供了初始化安全性保证：任何线程只要获得了不可变对象的引用，就一定能看到由构造函数正确初始化的值。

3.5.3 安全发布的常用模式

  • 使用 volatile、AtomicReference、synchronized、final 域或并发容器来安全发布对象。
  • 事实不可变对象（Effectively Immutable）需要在发布时使用上述技术之一。

3.5.4 事实不可变对象

  • 对象本身可变，但在发布后不会再被修改。通过安全发布可以避免同步。

3.5.5 可变对象

  • 可变对象在发布后仍可能被修改，因此不仅发布时需要同步，每次访问时也都需要同步。

3.5.6 安全地共享对象

  • 在并发程序中使用和共享对象时，可以采用以下实用策略：
    • 线程封闭：对象只由一个线程持有。
    • 只读共享：使用只读 / 不可变对象（无需同步）。
    • 线程安全共享：对象内部实现同步（如 ConcurrentHashMap）。
    • 保护对象：通过加锁保护可变对象。
第4章

对象的组合

第3章介绍了如何发布对象，本章将讨论如何将小的线程安全类组合成更大的线程安全类，以及如何识别哪些类需要哪些保护。

4.1设计线程安全的类

  • 设计线程安全类的三个基本要素：找出构成对象状态的所有变量、找出约束状态变量的不变性条件、建立一个并发访问策略。

4.1.1 收集同步需求

  • 明确类的不变性条件（如 count >= 0）和后验条件（如 remove 后 size 必须减小）。
  • 使用原子操作或加锁来保证状态转换是原子的。

4.1.2 依赖状态的操作

  • 类中的某些方法可能依赖于对象当前状态，必须基于当前状态进行判断与执行（如"如果当前状态为 X，则执行 Y"）。
  • 需要在复合操作中先检查状态，再执行相应动作；这通常需要加锁来保证原子性。

4.1.3 状态的所有权

  • 状态的所有权决定了谁应该负责保护它。
  • 如果一个对象被发布出去，则其状态归外部代码所有，外部代码需要在访问时加锁。

4.2实例封闭

实例封闭（Instance Confinement）：将数据封装在对象内部，并限制外部代码直接访问，必须通过对象的方法访问。

4.2.1 Java 监视器模式

  • 把类的所有可变状态封装起来，并由类自己的内置锁保护所有方法。这是 Java 最常用的对象线程安全设计模式。

4.2.2 示例：车辆追踪

  • 通过 ConcurrentHashMap + 同步的 MutablePoint 实现线程安全的车辆位置追踪器。

4.3线程安全性的委托

线程安全性的委托：如果类中的各个组件都是线程安全的，是否类本身也线程安全？答案为"取决于组合方式"。

4.3.1 示例：基于委托的车辆追踪器

  • 将位置信息发布为不可变对象 ImmutablePoint，避免共享可变状态。

4.3.2 独立的状态变量

  • 如果类中的状态变量彼此独立（不存在不变性条件），则可以为每个状态变量分别使用独立的锁。

4.3.3 当委托失效时

  • 当状态变量之间存在不变性条件时，简单的委托不足以保证线程安全，需要额外的同步机制（如加锁、原子类组合）。

4.3.4 发布底层的状态变量

  • 如果必须发布底层状态变量，应发布其不可变副本或使用线程安全包装。

4.3.5 示例：发布状态的车辆追踪器

  • 使用 ConcurrentMap + AtomicReference，在不破坏安全性的前提下支持位置快照。

4.4在现有的线程安全类中添加功能

4.4.1 客户端加锁机制

注意：客户端加锁（Client-side Locking）非常脆弱，因为客户端必须知道对象使用了哪一把锁。一旦类更换锁机制，所有客户端代码都会失效。

4.4.2 组合

  • 更稳健的方法是组合（Composition）：将现有类作为私有成员包含在新类中，新类的方法通过调用现有类的方法实现。
  • 如 ImprovedList 通过 List + 同步方法实现更可靠的扩展。

4.5将同步策略文档化

最佳实践：良好的文档应该说明：类是否是线程安全的、支持哪种程度的加锁（无锁/对象锁/类锁）、是否支持迭代、哪些状态变量受哪把锁保护。
第5章

基础构建模块

本章介绍 Java 平台类库中提供的一些基础的并发构建模块，包括线程安全的容器类、阻塞队列以及同步工具类等。

5.1同步容器类

同步容器类：如 Vector、Hashtable、Collections.synchronizedXxx 等。这些类通过内置锁实现线程安全，但有性能与功能局限。

5.1.1 同步容器类的问题

  • 同步容器类对所有方法使用单一锁（粗粒度），并发性能较差。
  • 复合操作（如"先检查再执行"）仍然需要客户端加锁。

5.1.2 迭代器与 ConcurrentModificationException

  • 同步容器的 Iterator 在迭代过程中若其他线程修改容器，会抛出 ConcurrentModificationException（fail-fast）。
  • 即使不修改，迭代过程也可能看到过期数据。

5.1.3 隐藏迭代器

陷阱：toString()、hashCode()、equals()、containsAll()、removeAll() 等方法会隐式迭代容器，因此即使代码中没有显式迭代，仍可能出现并发问题。

5.2并发容器

并发容器：通过更细粒度的锁（如分段锁、CAS）实现高并发。代表类有 ConcurrentHashMap、CopyOnWriteArrayList、ConcurrentLinkedQueue 等。

5.2.1 ConcurrentHashMap

  • 使用分段锁（Java 7） / CAS + synchronized（Java 8+） 实现高并发读写。
  • 迭代器是弱一致的，不会抛出 ConcurrentModificationException，但可能反映部分修改。
  • 支持原子的复合操作：putIfAbsent、compute、merge、computeIfAbsent 等。

5.2.2 额外的原子 Map 操作

  • putIfAbsent、remove(key, value)、replace(key, oldValue, newValue) 等原子操作是构建复合操作的基础。

5.2.3 CopyOnWriteArrayList

  • 每次修改都会创建并发布新的底层数组副本，读操作无需加锁，适合读多写少的场景。
  • 常见用途：监听器列表（add/remove listener vs. fire event）。

5.3阻塞队列和生产者-消费者模式

阻塞队列（BlockingQueue）：支持阻塞的 put 和 take，是实现生产者-消费者模式的核心组件。
  • 实现类：LinkedBlockingQueue、ArrayBlockingQueue、PriorityBlockingQueue、SynchronousQueue、DelayQueue。
  • 无界队列（如 LinkedBlockingQueue）可能导致 OOM；需根据场景选择有界队列。

5.3.1 示例：桌面搜索

  • 多个爬虫线程（生产者）将文件放入阻塞队列，索引线程（消费者）取出并建立索引。

5.3.2 串行线程封闭

  • 对象从生产者交给消费者后，只能由消费者线程访问；通过安全发布实现对象所有权转移。

5.3.3 双端队列与工作密取

  • Deque 实现类（如 LinkedBlockingDeque）支持两端操作，适合工作密取（Work Stealing）模式：每个消费者有自己的双端队列，当自己队列空时，从其他消费者队列"窃取"任务。

5.4阻塞方法与中断方法

  • 线程可能因为多种原因阻塞：等待 I/O、等待锁、等待其他线程的结果等。
  • Thread 提供了中断机制：interrupt() 设置中断标志，isInterrupted() 检查，可用于取消阻塞操作。
  • 大多数可中断的阻塞方法在收到中断时抛出 InterruptedException。
  • 在捕获 InterruptedException 后通常应恢复中断状态：Thread.currentThread().interrupt()。

5.5同步工具类

同步工具类：根据自身的状态来协调线程的控制流。包括 闭锁（Latch）、FutureTask、信号量（Semaphore）、屏障（Barrier） 等。

5.5.1 闭锁

  • CountDownLatch：通过计数器实现，线程调用 await() 阻塞，countDown() 计数减一；计数器为零时所有等待线程被唤醒。
  • 典型应用：等待多个并发任务完成、启动信号（确保所有资源就绪后再开始）。

5.5.2 FutureTask

  • FutureTask 表示一个异步计算，可通过 get() 获取结果（如果未完成则阻塞）。
  • 实现类 RunnableFuture，可以包装 Callable 或 Runnable，并通过 Executor 执行。
PART 2

第二部分 · 结构化并发应用程序

第6章至第9章。本部分将介绍如何利用线程来提高并发应用程序的吞吐量或响应性。涵盖任务执行框架、任务取消与关闭、线程池的高级特性以及 GUI 应用程序的并发模式。

第6章

任务执行

"任务"是抽象且离散的工作单元。本章介绍如何识别可并行执行的任务，以及如何在任务执行框架中执行它们。
  • 大多数并发应用围绕"任务执行"展开：服务器接受请求 → 创建任务 → 处理。
  • 串行执行：简单但吞吐差；为每个任务创建线程：资源消耗大，可能耗尽。
  • Executor 框架：基于生产者-消费者模式，提供了灵活的任务执行机制。
    • Executor 接口：execute(Runnable)。
    • ExecutorService：扩展 Executor，增加生命周期管理（shutdown）。
    • ScheduledExecutorService：支持定时和周期任务。
    • Executors 工厂类：newFixedThreadPool、newCachedThreadPool、newSingleThreadExecutor、newScheduledThreadPool。
  • 任务的生命周期：提交、执行中、完成。
  • Callable 与 Future：Callable 可以返回结果或抛出异常，Future 用于获取结果或取消任务。
  • 批量任务：invokeAll / invokeAny 用于批量执行任务并获取结果。
第7章

取消与关闭

在健壮的并发应用程序与"看似能正常工作的"应用程序之间存在的重要差异之一就是：如何处理任务的取消与线程的关闭。
  • 任务取消的机制：
    • 使用 volatile boolean cancelled 标志位。
    • 通过 Future.cancel(...) 取消任务（mayInterruptIfRunning）。
    • 处理不可中断的阻塞（如 socket IO、synchronized 块）。
  • 线程的中断：Thread.interrupt()、Thread.interrupted()、Thread.isInterrupted()。
  • 处理 InterruptedException 的两条准则：
    • 传递异常：让调用者处理。
    • 恢复中断状态：Thread.currentThread().interrupt()，使上层代码能看到中断标志。
  • JVM 关闭：正常关闭（最后一个非守护线程结束）、强制关闭（Runtime.halt）、Shutdown Hook、守护线程（Daemon Thread）等。
  • 避免在 finalize 中执行关闭/清理工作（不可靠、影响 GC 性能）。
第8章

线程池的使用

线程池（ThreadPool）是管理一组工作线程的资源池，提供了更灵活的任务执行策略。
  • 任务执行策略：在什么线程中执行、按什么顺序执行、多少个任务可并发、最大等待队列长度、拒绝策略等。
  • ThreadPoolExecutor 构造参数：corePoolSize、maximumPoolSize、keepAliveTime、workQueue、handler。
  • 饱和策略（RejectedExecutionHandler）：AbortPolicy（抛异常）、CallerRunsPolicy（调用者执行）、DiscardPolicy（丢弃）、DiscardOldestPolicy（丢弃最旧）。
  • ThreadFactory：自定义线程创建（命名、守护标志、UncaughtExceptionHandler）。
  • 扩展 ThreadPoolExecutor：beforeExecute、afterExecute、terminated 钩子方法。
  • 并行递归算法（如 fork/join）和 ForkJoinPool：Java 7 引入，专门为"分而治之"设计，采用工作密取策略。
第9章

图形用户界面应用程序

GUI 应用程序中只有一个特殊的线程：事件分发线程（EDT），负责处理所有 UI 事件。耗时的任务不能放在 EDT 中执行，否则会"冻结"界面。
  • 为什么 GUI 是单线程的：简化组件模型，避免竞态条件、可见性问题、死锁。
  • 耗时的任务应在后台线程中执行，完成后通过 SwingUtilities.invokeLater 或 SwingWorker 把结果发布回 EDT。
  • SwingWorker：Java 6 引入，封装了"后台执行 + EDT 中回调"的模式，简化线程切换。
  • 线程封闭的扩展：所有 UI 组件只能由 EDT 创建/修改，这是隐式线程封闭。
  • 数据模型的共享：使用线程安全的数据模型（如不可变对象 + 同步访问）让后台线程安全地修改数据。

第三部分 · 活跃性、性能与测试

第10章至第12章。本部分介绍如何确保并发程序执行预期的任务并获得理想的性能。包括避免活跃性故障、提高性能与可伸缩性、以及测试并发代码的技术。

第10章

避免活跃性危险

活跃性失败会使线程无法继续执行。本章讨论常见的活跃性危险：死锁、活锁、饥饿。
  • 死锁（Deadlock）：每个线程都在等待其他线程持有的资源，导致永久阻塞。
    • 锁顺序死锁：两个线程以不同顺序获取相同的锁。
    • 动态锁顺序死锁：参数传递导致的不可预测的锁顺序。
    • 协作对象间的死锁：相互调用导致锁顺序不一致。
    • 资源死锁：线程饥饿/死锁的复合。
  • 避免死锁的策略：
    • 固定锁顺序（如 System.identityHashCode 比较）。
    • 开放调用（Open Call）：不持锁调用外部方法。
    • 使用定时锁（tryLock） + 回退 + 重试。
    • 使用线程转储（Thread Dump）分析死锁。
  • 活锁（Livelock）：线程不断响应对方的行为但无法推进（如互相礼让）。
  • 饥饿（Starvation）：线程由于优先级、调度等原因一直得不到资源。
  • 公平性（Fairness）：ReentrantLock 提供公平锁选项，但会降低吞吐。
第11章

性能与可伸缩性

性能是多维度的：服务时间、吞吐、效率、可伸缩性等。本章讨论影响并发程序性能的关键因素。
  • 性能 vs 可伸缩性：性能指"单个请求快慢"，可伸缩性指"在增加资源时吞吐是否线性增长"。
  • Amdahl 定律：加速比 = 1 / ((1 - P) + P/N)，其中 P 是可并行部分比例，N 是处理器数。
  • 线程引入的开销：
    • 上下文切换：数千 CPU 周期。
    • 内存同步：synchronized、volatile 会导致缓存失效。
    • 阻塞：线程挂起/唤醒的开销。
  • 减少锁竞争：
    • 缩小锁范围（lock splitting）。
    • 减少锁粒度（lock striping，如 ConcurrentHashMap）。
    • 使用并发容器代替同步容器。
    • 使用读写锁（ReadWriteLock）分离读写。
    • 使用无锁算法（CAS、原子变量）。
  • 使用 vmstat、mpstat、perf 等工具监测 CPU 利用率与上下文切换。
第12章

并发程序的测试

并发程序测试比串行程序更困难。挑战包括：竞态条件难以复现、活跃性问题需要足够负载才显现、性能测试需要稳定的环境。
  • 正确性测试：
    • 自动化：ThreadJiggleRunner（增加上下文切换）、MultithreadedTester。
    • 单元测试并发类：对状态空间进行"暴力搜索"（如 BoundedBuffer 的状态机）。
    • 阻塞操作的测试：Thread.getState + assertTrue(t.getState() == Thread.State.WAITING)。
  • 活跃性测试：通过让程序"卡住"来发现问题，如 ThreadMXBean.findDeadlockedThreads。
  • 性能测试：
    • 增加线程数测量吞吐变化（衡量可伸缩性）。
    • 多种算法/数据结构对比。
    • 使用 jmh（Java Microbenchmark Harness）做微基准测试。
  • 避免性能测试的陷阱：JVM 预热不够、GC 干扰、编译优化等。
  • 代码审查清单：
    • 所有共享变量是否都受到正确的同步保护？
    • 是否存在"先检查后执行"模式？
    • 是否有不必要的对象发布（逸出）？
    • 复合操作是否原子化？
    • 锁顺序是否固定？

第四部分 · 高级主题

第13章至第16章。本部分面向资深开发人员，深入探讨显式锁、自定义同步工具、原子变量与非阻塞算法，以及 Java 内存模型的底层细节。

第13章

显式锁

Java 5.0 引入了 java.util.concurrent.locks 下的显式锁（Lock 接口），提供了 synchronized 之外更灵活的锁机制。
  • Lock 接口：lock()、unlock()、tryLock()、tryLock(time, unit)、lockInterruptibly()、newCondition()。
  • 轮询锁 + 定时的 tryLock：能解决死锁（如转移资金业务），比 synchronized 更灵活。
  • 可中断的锁获取：lockInterruptibly 允许线程在等待锁时响应中断。
  • 公平性：ReentrantLock 构造参数 fair=true 表示公平锁，按等待时间分配锁。代价是吞吐下降。
  • 读-写锁（ReadWriteLock）：
    • 允许多个读者并发访问，写者独占。适合读多写少场景。
    • 实现类 ReentrantReadWriteLock，支持公平/非公平、可重入、降级（写锁降级为读锁）。
  • 何时选择 ReentrantLock vs synchronized：
    • 需要 tryLock、lockInterruptibly、公平性、多条件变量时选 ReentrantLock。
    • 简单同步场景优先 synchronized，更简洁且 JVM 持续优化。
第14章

构建自定义的同步工具

基于状态（State-dependent）的同步工具类，如闭锁、信号量、屏障等。本章讨论如何基于 Condition 或 AQS 构建自定义同步工具。
  • 状态依赖性管理：如 BlockingQueue.put 在队列满时阻塞，take 在队列空时阻塞。
  • 通常模式：在锁内检查状态条件，调用 await() 释放锁并阻塞；满足条件后被唤醒，重新获取锁。
  • 条件队列（Condition Queue）：
    • Condition 接口：await、signal、signalAll。
    • 一个 Lock 可以有多个 Condition，比 Object.wait/notify 更灵活。
  • 使用条件队列的准则：
    • 每个对象都可以作为条件队列，但显式锁对应的 Condition 更灵活。
    • 条件谓词（如 !queue.isEmpty()）必须由 Lock 保护。
    • signal vs signalAll：signalAll 更安全但效率低；signal 适用于条件谓词为单次事件。
    • 使用 while 而非 if 包裹 await，防止"虚假唤醒"。
  • AbstractQueuedSynchronizer（AQS）：用于构建锁和同步器的框架。ReentrantLock、Semaphore、CountDownLatch 等都基于 AQS。
  • java.util.concurrent 中的同步工具：Semaphore（计数信号量）、CountDownLatch、CyclicBarrier、Exchanger、Phaser。
  • CyclicBarrier：让一组线程相互等待，全部到达屏障点后继续。可重用。
  • Exchanger：两线程间交换数据的同步点，常用于"双缓冲"流水线。
第15章

原子变量与非阻塞同步机制

锁是悲观策略；非阻塞算法基于比较并交换（CAS）实现乐观并发，性能通常更优。
  • 锁的劣势：挂起/恢复线程的开销、优先级反转、死锁。
  • 硬件对并发的支持：CAS（Compare-and-Swap）、getAndIncrement 等原子指令。
  • 原子变量类（java.util.concurrent.atomic）：
    • 标量类：AtomicInteger、AtomicLong、AtomicBoolean、AtomicReference。
    • 数组类：AtomicIntegerArray 等。
    • 字段更新器：AtomicIntegerFieldUpdater 等。
    • 复合变量：AtomicReference + AtomicReferenceFieldUpdater。
    • JDK 8+：LongAdder、DoubleAdder（高竞争下性能更好）、LongAccumulator。
  • 非阻塞算法（Non-blocking Algorithm）：
    • 无锁（Lock-free）：保证系统整体进度。
    • 无等待（Wait-free）：保证每个线程在有限步骤内完成。
  • 构建非阻塞算法的关键：CAS + 版本号（如 AtomicStampedReference 解决 ABA 问题）。
  • ABA 问题：CAS 看到值未变，但实际经历了 A→B→A 的变化，可能造成错误。解决方案：版本戳（Stamp）、AtomicStampedReference。
  • 非阻塞算法的优势：避免死锁、优先级反转；吞吐更高（但单线程延迟可能更高）。
第16章

Java 内存模型

Java 内存模型（JMM）定义了线程之间的共享变量在程序中的可见性规则，是理解并发编程的底层基础。
  • 内存模型的必要性：现代硬件（CPU 多级缓存、写缓冲器、写重排、流水线）以及编译器优化都会改变指令执行顺序，导致跨线程的可见性问题。
  • Java 内存模型（JSR 133，Java 5.0+）：
    • Happens-Before 关系：定义操作之间的偏序关系，程序顺序、监视器锁、volatile、线程启动、线程终止、线程中断、对象终结、传递性。
    • 同步语义：synchronized、volatile、final 提供 Happens-Before 关系。
    • 只要一个操作 Happens-Before 另一个操作，则前者的结果对后者可见。
  • 重排序（Reordering）：
    • 编译器重排序。
    • 指令级并行重排序。
    • 内存系统重排序（缓存、写入缓冲器）。
  • Final 域的内存语义：JMM 保证正确构造的 final 字段在构造函数返回前一定被冻结，其他线程无需同步即可看到正确的 final 值。
  • Word Tearing：32 位 JVM 上对 long/double 的非原子读写。
  • 双重检查锁定（DCL）：必须配合 volatile 才能保证正确性（否则可能看到"部分构造"的对象）。
  • JMM 的设计目标：在不牺牲性能的前提下提供清晰的并发语义；为开发者提供"足够强"的内存可见性保证。

核心要点速查

★编写线程安全类的核心技术

1. 封装 + 不可变
尽量让对象不可变，不可变对象天然线程安全。
2. 线程封闭
把可变状态局限在一个线程内（栈封闭、ThreadLocal）。
3. 委托给线程安全类
优先使用 ConcurrentHashMap、ConcurrentLinkedQueue 等。
4. 加锁保护共享状态
synchronized 或 Lock + 单一锁原则 + 固定锁顺序。
5. 文档化同步策略
明确类是否线程安全、锁对象、不变性条件。

★常见并发 Bug 与避免

  • 竞态条件：使用原子变量或加锁保证复合操作原子性。
  • 死锁：固定锁顺序、开放调用、tryLock + 回退。
  • 可见性：使用 volatile、synchronized 或 final。
  • 对象逸出：不在构造函数中发布 this 引用。
  • 迭代时修改：使用并发容器的弱一致迭代器，或克隆再迭代。
  • 线程饥饿：避免在持锁时调用外部方法，使用公平锁或合理调度。

★JDK 并发包速记

  • 原子类：AtomicXxx、LongAdder、AtomicStampedReference。
  • 并发容器：ConcurrentHashMap、ConcurrentLinkedQueue、CopyOnWriteArrayList。
  • 阻塞队列：LinkedBlockingQueue、ArrayBlockingQueue、PriorityBlockingQueue、SynchronousQueue、DelayQueue。
  • 同步器：CountDownLatch、CyclicBarrier、Semaphore、Exchanger、Phaser。
  • 显示锁：ReentrantLock、ReentrantReadWriteLock、StampedLock。
  • 执行器：ExecutorService、ScheduledExecutorService、ForkJoinPool。
  • 并行流：JDK 8+ 的 Stream parallel() 底层使用 ForkJoinPool。
