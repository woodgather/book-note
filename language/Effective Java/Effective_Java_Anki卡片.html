为什么要考虑使用静态工厂方法替代构造方法？
一个类允许客户端获取其实例的传统方式是提供公共构造方法，但还有另一种技术应成为每个程序员工具箱的一部分。

请说出静态工厂方法相比构造方法的主要优势（至少 3 点）和劣势。
点击翻转
✓ 答案 静态工厂方法

四大优势

  1. 有名字——如果构造方法参数不能描述返回对象，命名良好的静态工厂更易读。例如 BigInteger.probablePrime() 比 BigInteger(int, int, Random) 更清晰。
  2. 不必每次调用都创建新对象——可以预先构建实例或缓存复用，如 Boolean.valueOf(boolean) 返回的是预先创建好的 TRUE / FALSE。
  3. 可以返回原返回类型的任何子类型——API 可以隐藏实现类，返回接口类型。例如 Collections.unmodifiableList() 返回的实现类是包私有的。
  4. 返回对象的类型可以随调用参数变化——同一个方法可根据参数返回不同实现。如 EnumSet.of() 元素 ≤64 时返回 RegularEnumSet，否则返回 JumboEnumSet。

主要劣势

  • 只提供静态工厂方法的类，如果没有 public/protected 构造方法，无法被子类化。
  • 静态工厂方法在 API 文档中不像构造方法那样显眼，程序员不容易发现它们。

当构造方法参数过多时，为什么推荐使用 Builder 模式？
考虑一个代表营养成分标签的类：有 3 个必需参数，以及超过 20 个可选参数。

传统的「可伸缩构造方法模式」和「JavaBean 模式」各有什么问题？Builder 模式如何解决？
点击翻转
✓ 答案 Builder 模式

可伸缩构造方法（Telescoping Constructor）的问题

  • 参数太多时客户端代码难以编写和阅读，容易把参数顺序搞混导致 bug。

JavaBean 模式的问题

  • 构造过程被分到了多个调用中，对象可能处于不一致状态。
  • 类无法做成不可变的，需要额外的同步努力。

Builder 模式的优势

  • 兼具安全性（构造完成才得到对象）和可读性（像命名参数一样设置）。
  • 可以有多个 build() 变体，也可以对参数进行校验。
  • 类可以是不可变的。
  • Builder 本身可以作为方法参数传递。

适用场景

当类的构造方法或静态工厂中有多个参数（尤其是许多可选参数或相同类型的参数）时，Builder 是不错的选择。通常参数数 ≥4 个时就值得使用。

实现 Singleton 单例属性的几种方式及最佳实践是什么？

点击翻转
✓ 答案 Singleton

方式一：public static final 字段

public class Elvis {
    public static final Elvis INSTANCE = new Elvis();
    private Elvis() { }
}

优点：简单清晰。缺点：反射攻击可调用私有构造方法（需防御）、序列化时需特殊处理。

方式二：静态工厂方法

public class Elvis {
    private static final Elvis INSTANCE = new Elvis();
    private Elvis() { }
    public static Elvis getInstance() { return INSTANCE; }
}

优点：灵活性（可以改是否单例而不改变 API）。缺点：同样存在反射和序列化问题。

方式三：单元素枚举（最佳）

public enum Elvis {
    INSTANCE;
}
  • 无偿提供序列化机制，防止多次实例化。
  • 可以防止反射攻击。
  • 代码最简洁。
  • 单元素枚举类型已成为实现 Singleton 的最佳方法（前提是单例类不需要继承自其他类）。
ITEM 04 创建与销毁对象
如何确保一个工具类（utility class）无法被实例化？
类似 java.lang.Math、java.util.Arrays 这样只包含静态方法和静态字段的类，不应该被实例化。

为什么用抽象类不行？正确做法是什么？
点击翻转
✓ 答案 非实例化

为什么抽象类不行？

  • 抽象类可以被子类化，子类仍然可以被实例化。
  • 会误导用户以为它是为继承而设计的。

正确做法：私有构造方法

public class UtilityClass {
    // Suppress default constructor
    private UtilityClass() {
        throw new AssertionError();
    }
}

要点

  • 因为类不含显式构造方法时编译器才会生成默认构造方法，所以包含私有构造方法即可防止默认构造方法生成。
  • 构造方法中抛出 AssertionError 是额外保险，防止类内部意外调用。
  • 副作用：这个类不能被子类化（子类构造方法必须调用父类构造方法，而父类没有可访问的构造方法）。

为什么依赖注入（Dependency Injection）优于硬连接资源？
考虑一个拼写检查器类，它依赖于字典。将其实现为静态工具类或单例有什么问题？依赖注入如何解决？
点击翻转
✓ 答案 依赖注入

静态工具类 / 单例的问题

  • 假设只有一本字典可用，不够灵活。实际上有多种字典（英英、英汉、医学词典等）。
  • 难以测试——无法注入 mock 字典进行单元测试。
  • 不支持动态切换底层资源。

依赖注入的做法

将资源（或工厂）作为构造方法参数传入：

public class SpellChecker {
    private final Lexicon dictionary;
    public SpellChecker(Lexicon dictionary) {
        this.dictionary = Objects.requireNonNull(dictionary);
    }
    public boolean isValid(String word) { ... }
}

优势

  • 灵活性——支持多个底层资源实现。
  • 可测试性——容易注入 mock 依赖。
  • 保留了不可变性（依赖是 final 的）。
  • 适用范围广：构造方法注入、静态工厂、Builder 都可以结合使用。

虽然大型项目常使用框架（Spring, Dagger），但底层原理就是依赖注入——不要硬编码依赖，将它们传入。

避免创建不必要的对象——常见的性能陷阱有哪些？
重用一个功能相同的对象通常比每次都创建新对象更合适。请举出几个典型的反面例子及改进方法。
点击翻转
✓ 答案 对象复用

反面例子 1：String 构造方法

new String("hello") → 每次都创建新对象。

改进：直接用 "hello"，字符串常量会被 JVM 重用。

反面例子 2：昂贵对象重复创建

例如 Pattern.matches() 每次调用都会创建一个 Pattern 实例（创建成本高）。

改进：将 Pattern 缓存为 static final 常量，复用同一个实例。

反面例子 3：自动装箱（autoboxing）

// 慢！创建了大量 Long 实例
private static long sum() {
    Long sum = 0L;
    for (long i = 0; i < Integer.MAX_VALUE; i++)
        sum += i;
    return sum;
}

改进：使用基本类型 long sum = 0L，避免不必要的装箱。

关键原则

  • 优先使用基本类型而非装箱基本类型（见 Item 61）。
  • 注意隐藏的对象创建（字符串拼接、正则、装箱）。
  • 但不要走向极端——小对象创建回收成本很低，不必为了"省"而牺牲代码清晰性。
ITEM 07 创建与销毁对象
什么是"过期的对象引用"？它如何导致内存泄漏？
考虑一个自定义的 Stack 类，内部用数组保存元素。当元素被 pop 出栈后，如果数组中的引用没有被清空，会发生什么？为什么？
点击翻转
✓ 答案 内存泄漏

问题所在

如果 Stack 先增长后收缩，那么被弹出的对象不会被 GC 回收，因为 Stack 内部仍维护着对它们的过期引用（obsolete reference）——即永远不会再被解除引用的引用。

修复方法

对象引用过期时，手动清空它们：

public Object pop() {
    if (size == 0)
        throw new EmptyStackException();
    Object result = elements[--size];
    elements[size] = null; // 清除过期引用
    return result;
}

常见的内存泄漏来源

  1. 自己管理内存的类（如 Stack、缓存）——只要类自己管理内存，就应警惕内存泄漏。
  2. 缓存——对象放入缓存后容易被遗忘。使用 WeakHashMap（当键不再有外部引用时条目自动删除）或定期清理。
  3. 监听器和回调——客户端注册回调后如果没有显式取消注册，会累积。用弱引用保存监听器。

最佳防御：让垃圾回收器确定对象何时无用——当引用过期时，将其设为 null。

ITEM 08 创建与销毁对象
为什么要避免使用 Finalizer 和 Cleaner 机制？
Finalizer 在 Java 9 中被弃用了，Cleaner 被作为替代。但两者都有严重问题。

它们有哪些缺点？资源清理的正确方式是什么？
点击翻转
✓ 答案 Finalizer / Cleaner

主要缺点

  1. 不保证及时执行——GC 何时触发 finalization 完全不确定，不同 JVM 实现差异很大。不能用于时间关键的操作。
  2. 不保证会执行——程序退出时甚至可能根本不运行。不能依赖它们来更新持久状态。
  3. 严重的性能损失——使用 finalizer 会显著减慢对象创建和回收。
  4. 安全风险——finalizer 攻击：子类 finalize 方法可以在构造时抛出异常后仍然调用 finalize，复活"半构造"的对象。

正确做法：try-with-resources

让类实现 AutoCloseable 接口，客户端使用 try-with-resources 语句在不需要时关闭资源。

Finalizer / Cleaner 的合法用途

  • 作为安全网——当客户端忘记调用 close() 时，作为"迟做总比不做好"的最后清理手段（但要接受可能不及时）。
  • 回收本地对等体（native peer）——Java 对象通过本地方法委托给本地对象，GC 无法回收本地部分。Cleaner 比 finalizer 好一些，因为它不阻塞 finalizer 线程。

为什么 try-with-resources 优于 try-finally？
在 Java 7 之前，try-finally 是确保资源被关闭的最佳方式。但它有一个严重的缺陷。

是什么缺陷？try-with-resources 如何解决？
点击翻转
✓ 答案 try-with-resources

try-finally 的问题：异常被吞噬

如果 try 块和 finally 块中都抛出异常，finally 中的异常会"抹掉"try 中的异常。第一个异常（真正的原因）丢失了，调试非常困难。

多个资源时，嵌套的 try-finally 代码也极其臃肿难看。

try-with-resources 的优势

  • 更简洁——自动关闭资源，代码更短更清晰。
  • 保留所有异常信息——第一个异常被保留，后续异常被"抑制"（suppressed），可以通过 getSuppressed() 获取。
  • 可以配合 catch 和 finally 使用。
// 推荐做法
try (InputStream in = new FileInputStream(src);
     OutputStream out = new FileOutputStream(dst)) {
    byte[] buf = new byte[1024];
    int n;
    while ((n = in.read(buf)) >= 0)
        out.write(buf, 0, n);
}

使用条件

资源必须实现 AutoCloseable 接口（Java 库中许多类已实现）。编写自己的资源类时也应该实现 AutoCloseable。

ITEM 10 通用方法
重写 equals 方法时必须遵守的五条通用约定是什么？
Object 的 equals 方法有明确的通用约定。不遵守约定的类会破坏依赖约定的其他类（如 HashMap、HashSet）。

请说出五条约定的名称及其含义。
点击翻转
✓ 答案 equals 约定

五条通用约定

  1. 自反性（reflexive）——对于任何非 null 引用值 x，x.equals(x) 必须返回 true。
  2. 对称性（symmetric）——对于任何非 null 引用值 x 和 y，当且仅当 y.equals(x) 返回 true 时，x.equals(y) 才返回 true。
  3. 传递性（transitive）——对于任何非 null 引用值 x、y、z，如果 x.equals(y) 返回 true 且 y.equals(z) 返回 true，则 x.equals(z) 必须返回 true。
  4. 一致性（consistent）——对于任何非 null 引用值 x 和 y，只要 equals 的比较操作在对象中所用的信息没有被修改，多次调用就会一致地返回 true 或 false。
  5. 非空性（non-null）——对于任何非 null 引用值 x，x.equals(null) 必须返回 false。

高质量 equals 的诀窍

  1. 用 == 检查「参数是否为这个对象的引用」
  2. 用 instanceof 检查「参数是否为正确的类型」
  3. 把参数转换成正确的类型
  4. 对类中的每个关键（significant）域进行比较
ITEM 11 通用方法
重写 equals 时为什么必须同时重写 hashCode？
一个最常见的错误来源。如果不这样做，会违反 Object 通用约定的哪一条？会造成什么实际后果？
点击翻转
✓ 答案 hashCode 约定

违反的约定

相等的对象必须具有相等的散列码（hash code）。如果两个对象通过 equals 比较相等，那么调用它们的 hashCode 方法必须产生同样的整数结果。

实际后果

类的实例无法正常结合所有基于散列的集合一起工作，包括 HashMap、HashSet 和 Hashtable。

例：两个 equals 相等的对象放入 HashSet 后，你可能用另一个"相等"的对象去 get() 却找不到——因为 hashCode 不同，它们被放到了不同的桶里。

编写好的 hashCode 方法

  1. 声明一个 int 变量 result，初始值为第一个关键域的散列码 c。
  2. 对每个剩余的关键域 f：
    • 计算该域的散列码 c
    • 合并：result = 31 * result + c
  3. 返回 result。

或者直接用 Objects.hash()（简洁但稍慢），或考虑延迟初始化（缓存 hashCode，适用于不可变类）。

ITEM 12 通用方法
为什么始终应该重写 toString 方法？
Object 提供的默认实现（类名@散列码）通常对用户毫无帮助。重写 toString 带来什么好处？编写时应注意什么？
点击翻转
✓ 答案 toString

为什么要重写

  • 当对象被传递给 println、字符串拼接、断言、或者被调试器打印时，toString 会被自动调用。
  • 好的 toString 能让类更易于使用和调试。
  • 实际使用中，toString 应该返回对象中包含的所有值得关注的信息。

实现要点

  1. 返回简洁但信息丰富的字符串——视觉上易于阅读。
  2. 明确指定返回值的格式（对于值类尤其重要），并在文档中说明。指定格式后，就可以前后一致地使用。
  3. 如果指定了格式，考虑提供一个匹配的静态工厂或构造方法（如 valueOf(String)），方便解析。
  4. 为 toString 返回值中包含的所有信息提供独立的访问方法（getter），否则程序员必须解析 toString 的输出。

即使不指定格式，也应该在文档中说明意图，让调用者知道能指望什么、不能指望什么。

ITEM 13 通用方法
为什么要"谨慎地重写 clone 方法"？Cloneable 接口有什么问题？
Cloneable 接口的目的是作为一个 mixin 接口，表示对象允许被克隆。但它存在许多设计缺陷。

它有什么问题？有什么替代方案？
点击翻转
✓ 答案 clone

Cloneable 的设计问题

  1. 接口中没有 clone 方法——它是一个标记接口，但标记的是 Object 中一个 protected 方法的行为。
  2. 行为约定模糊——约定要求 x.clone().getClass() == x.getClass() 且 x.clone().equals(x) 为 true，但这些都是"应该"而非"必须"。
  3. 与 final 域不兼容——如果类有指向可变对象的 final 域，clone 后修改克隆体会影响原对象（浅拷贝问题）。
  4. 不支持协变返回类型的历史包袱（Java 5 之前）。
  5. 构造机制绕过了构造方法——对象创建不通过构造方法，增加风险。

更好的替代方案

  • 复制构造方法：public Yum(Yum yum) { ... }
  • 复制工厂：public static Yum newInstance(Yum yum) { ... }

这些方法不依赖于存在风险的对象创建机制、不要求遵守未详细说明的约定、与 final 域不冲突、不会抛出不必要的受检异常、不需要类型转换。

简而言之：Cloneable 有许多缺陷，新的接口不应该扩展它，新的可复制类也不应该实现它。

ITEM 14 通用方法
什么时候应该考虑实现 Comparable 接口？compareTo 有哪些约定？
compareTo 虽然不是 Object 的方法，但与 equals 有许多相似之处。它的约定是什么？与 equals 的关系如何？
点击翻转
✓ 答案 Comparable

何时实现 Comparable

如果一个类有明显的内在排序关系（如字母顺序、数值顺序、按日期排序），就应该实现 Comparable 接口。实现后，该类就能与依赖比较的通用算法和集合实现协作（Arrays.sort()、TreeSet、Collections 工具等）。

compareTo 约定

  1. 对称：sgn(x.compareTo(y)) == -sgn(y.compareTo(x))
  2. 传递：若 x.compareTo(y) > 0 且 y.compareTo(z) > 0，则 x.compareTo(z) > 0
  3. 一致性：x.compareTo(y) == 0 意味着 sgn(x.compareTo(z)) == sgn(y.compareTo(z))
  4. 强烈建议与 equals 一致：(x.compareTo(y) == 0) == (x.equals(y))。如果不一致，最好在文档中说明。

实现要点

  • 比较关键域，从最重要的域开始。
  • 从 Java 8 开始，优先使用 Comparator 接口提供的比较器构造方法，配合 lambda 写出更简洁的代码。
  • 避免使用 < 和 > 运算符比较基本类型，应使用静态的 compare 方法（如 Integer.compare(int, int)）。

ITEM 15 类与接口
为什么要使类和成员的可访问性最小化？Java 有哪些访问控制级别？
这是区分设计良好组件和设计不佳组件的最重要因素。基本原则是什么？各级别的含义和使用场景？
点击翻转
✓ 答案 信息隐藏

基本原则：信息隐藏 / 封装

将 API 和实现分离开。组件只通过 API 通信，不需要知道彼此的内部工作。

四个访问级别（从高到低）

  1. public——任何地方都可访问。
  2. protected——同一个包和子类可访问。
  3. 包级私有（package-private）——默认级别，同一个包内可访问。
  4. 私有（private）——只有类本身能访问。

实践建议

  • 让每个类或成员尽可能地不可访问——使用与功能一致的最低访问级别。
  • 实例域决不能是 public（见 Item 16）。
  • 包含可变域的类不能是不可变的。
  • 公共类的公共可变域几乎总是错误的。
  • 长度非零的数组总是可变的——如果有 public static final 的数组域，客户端可以修改数组内容。解决方案：返回不可变列表或返回数组的防御性拷贝。

为什么公共类中应该使用访问方法（getter/setter）而不是公共属性？

不可变类的五条规则

  1. 不要提供任何修改对象状态的方法（mutator）。
  2. 确保类不会被扩展——final 类或私有构造方法 + 静态工厂。
  3. 让所有域都是 final 的。

  • 线程安全——不需要同步，可以自由共享。

ITEM 18 类与接口
为什么组合（composition）优于继承（inheritance）？
继承是代码重用的有效方式，但不总是最好的工具。为什么"用继承来实现代码重用"是危险的？什么是"转发类"？
点击翻转
✓ 答案 组合优于继承

继承的问题

  1. 破坏封装——子类依赖于父类的实现细节。父类的后续版本可能改变内部实现，即使其 API 没变，子类也可能被破坏。
  2. 脆弱的基类问题——父类新增方法可能与子类方法签名冲突，或导致子类状态不一致。
  3. 跨包继承尤其危险——不同包之间的继承是脆弱的。

组合 + 转发（Composition + Forwarding）

在新类中包含一个私有域，引用现有类的实例（组合）。新类中的每个实例方法都可以调用被包含的现有类实例中对应的方法（转发），并返回结果。

这样得到的类非常稳固，不依赖于现有类的实现细节。即使现有类增加新方法，也不会影响新类。

装饰器模式

这种组合+转发的经典应用就是装饰器模式（Decorator Pattern）——用装饰类包装另一个类，添加新功能。如 Collections.synchronizedList()。

何时适合用继承

只有当两个类之间确实存在"is-a"关系时才使用继承。即使如此，如果父类在同一个包内且是为继承而设计的（Item 19），继承才是安全的。

为什么需要特殊设计

为了继承而设计一个类，是一项重大的责任。子类依赖于父类的实现细节，如果不精心设计并文档化"自用模式"（self-use），父类的改变就会破坏子类。

设计继承的要点

  1. 文档化自用模式——类必须在文档中精确描述每个可覆盖方法的自用情况：何时被调用、调用顺序、调用结果如何影响后续处理。
  2. 以谨慎的设计提供受保护（protected）的成员——只暴露必要的钩子方法。
  3. 构造方法绝不能调用可被覆盖的方法——父类构造方法在子类构造方法之前运行，如果父类构造调用了被子类覆盖的方法，方法会在子类状态初始化之前执行，往往导致失败。
  4. 谨慎实现 Cloneable 和 Serializable——因为 clone 和 readObject 的行为类似于构造方法，也不能调用可覆盖方法。

如果不打算继承

让类成为 final 的，或提供私有/包级私有构造方法（防止外部继承）。对于具体类，最佳实践通常是不让它们可被继承。

为什么接口优于抽象类？什么是骨架实现（skeletal implementation）？

点击翻转

默认方法的引入

Java 8 之前，不可能在不破坏现有实现的情况下给接口添加方法。Java 8 之后可以通过默认方法来添加，但这并不意味着可以随意添加。

主要风险和注意事项

  1. 不能保证所有实现都能正常工作——默认方法是"一刀切"的，可能不适用于所有现有的实现。例如 Collection.removeIf() 的默认实现可能不兼容某些同步集合实现。

  • 默认方法主要用于在标准接口中提供工具方法（如 stream、forEach、removeIf 等）。
  • 发布前必须在尽可能多的实现上测试默认方法。
  • 设计新接口时仍然要谨慎——虽然有默认方法的帮助，但接口一旦发布就很难改变。
ITEM 22 类与接口
为什么接口仅用来定义类型？什么是"常量接口反模式"？

点击翻转
✓ 答案 常量接口

什么是常量接口反模式

有些接口不包含任何方法，只包含静态 final 常量。实现这种接口的类只是为了"继承"常量，省去类名前缀。

为什么这是不好的

  1. 违背接口的用途——接口应该用于定义类型（描述类可以做什么），而不是用来导出常量。
  2. 污染 API——常量成为类导出的 API 的一部分，但实际上只是实现细节。用户会困惑这些常量的用途。
  3. 实现细节泄露——类内部使用了哪些常量本应是实现细节，却暴露在 API 中。
  4. 向后兼容负担——如果将来类不再需要这些常量，仍然必须保留（因为 API 已承诺）。

正确做法

  • 如果常量与某个类或接口关系紧密，就将其放入该类或接口中（如 Integer.MAX_VALUE）。
  • 如果常量是一组枚举常量，使用枚举类型（Item 34）。
  • 否则，放入一个工具类中，通过类名引用（如 Math.PI）。

为什么类层次结构优于标签类（tagged class）？
有时候一个类的实例有两种或更多"风格"，用一个标签域来区分。为什么这种做法有问题？应该用什么替代？

✓ 答案 标签类

标签类的问题

标签类是一个类用一个字段（如 shape 枚举）标记自己的"种类"，然后根据种类在方法中用 switch 分支处理。

  1. 臃肿混乱——多个实现塞在一个类里，可读性差。
  2. 内存浪费——每个实例都带着不属于自己"种类"的域。
  3. 无法做成 final 域——除非在构造方法中初始化不相关的域。
  4. 添加新种类需要修改所有 switch——容易遗漏，违反开闭原则。
  5. 类型安全差——实例的实际语义靠标签值判断，编译器无法帮助验证。

替代方案：类层次结构（子类型化）

用抽象类或接口定义一个类型，每种"风格"作为一个具体子类实现。

  • 每个类只有自己需要的域，简洁清晰。
  • 所有域都可以是 final 的。
  • 新增种类只需新增子类，无需修改已有代码。
  • 编译器确保类型正确。

简而言之：标签类几乎总是类层次结构的拙劣替代品。发现标签类时，考虑将其重构为继承层次。

ITEM 28 泛型
为什么列表（List）优于数组？两者在类型系统上有什么根本差异？
数组和泛型有两大区别：协变 vs 不变，具体化 vs 擦除。请解释这些概念及其影响。
点击翻转
✓ 答案 列表 vs 数组

差异一：协变 vs 不变

  • 数组是协变的（covariant）——如果 Sub 是 Super 的子类型，那么 Sub[] 也是 Super[] 的子类型。
  • 泛型是不变的（invariant）——对于两个不同类型 Type1 和 Type2，List<Type1> 既不是 List<Type2> 的子类型，也不是超类型。

影响：数组可以在编译时通过类型检查但运行时失败（如 Object[] a = new Long[1]; a[0] = "x"; 会抛出 ArrayStoreException）。而泛型错误在编译时就能发现。

差异二：具体化 vs 擦除

  • 数组是具体化的（reified）——运行时知道并强制执行元素类型。
  • 泛型通过擦除（erasure）实现——编译时执行类型约束，运行时擦除类型信息。

影响：创建泛型数组（如 new List<E>[]）是非法的，因为不是类型安全的。

结论：优先选择列表

  • 列表 + 泛型提供了编译时类型安全，比数组更安全。
  • 数组和泛型不能很好地混合——如果发现自己把数组和泛型混合使用且收到编译错误，第一反应应该是用列表替换数组。
ITEM 29 泛型
如何将一个使用 Object 的类（如 Stack）泛型化？有哪些技术选择？
将 Stack 类从用 Object 存储元素改造成泛型类 Stack<E>，会遇到什么障碍？有哪两种主流解决方案？
点击翻转
✓ 答案 泛型化

障碍：不能创建泛型数组

当你把 Object[] elements 改为 E[] elements，然后用 new E[DEFAULT_CAPACITY] 初始化时，编译器会报错——不能创建泛型数组（Item 28）。

解决方案一：使用 Object[] 存储 + 强转读取

private Object[] elements;
public E pop() {
    @SuppressWarnings("unchecked")
    E result = (E) elements[--size];
    elements[size] = null;
    return result;
}

这是 Java 类库（如 ArrayList）常用的做法。每次读取元素时做 unchecked 转换。

解决方案二：将数组声明为 E[]，创建时强转

private E[] elements;
@SuppressWarnings("unchecked")
public Stack() {
    elements = (E[]) new Object[DEFAULT_CAPACITY];
}

只在构造时转换一次，之后直接使用。代码更简洁。

如何选择

第一种（读取时转换）在运行时更安全（数组的实际运行时类型始终是 Object[]），第二种（创建时转换）代码更简洁。实际中第二种更常用。

声明了一个或多个类型参数的方法。类型参数列表位于方法的修饰符和返回类型之间。

  • 不需要创建整个泛型类——如果只有一个方法需要类型参数，只需让那个方法是泛型的。

泛型单例工厂（Generic Singleton Factory）

对于不可变但适用于多种类型的对象，可以使用泛型静态方法来分发（如 Collections.reverseOrder()、Collections.emptySet()）。因为泛型是通过擦除实现的，所以一个实例可以适用于所有类型参数。

递归类型限制（Recursive Type Bound）

如 <T extends Comparable<T>>，表示 T 必须实现与自身的比较——这是确保可以对集合进行排序的标准方式。

ITEM 31 泛型
如何使用限定通配符（bounded wildcard）增加 API 的灵活性？PECS 是什么意思？
参数化类型是不变的（invariant），但有时你需要更多灵活性。生产者和消费者分别应该用什么通配符？
点击翻转
✓ 答案 通配符 / PECS

PECS 原则

Producer Extends, Consumer Super

生产者-extends，消费者-super。

生产者（生产 T 实例）→ extends

如果参数化类型表示一个 T 的生产者，使用 <? extends T>。

例：pushAll(Iterable<? extends E> src)——src 生产 E 类型的元素供栈使用。

消费者（消费 T 实例）→ super

如果参数化类型表示一个 T 的消费者，使用 <? super T>。

例：popAll(Collection<? super E> dst)——dst 消费栈中弹出的 E 元素。

记忆方法

如果方法从参数中读取（获取）元素，参数是生产者 → extends。

如果方法向参数中写入（添加）元素，参数是消费者 → super。

如果既读又写，则不需要通配符。

注意

  • 不要用通配符作为返回类型——它迫使客户端也考虑通配符。
  • Comparable 和 Comparator 永远是消费者——通常用 Comparable<? super T>。
ITEM 32 泛型
为什么泛型和可变参数（varargs）结合时要小心？什么是堆污染？
可变参数方法在调用时会创建一个数组来保存参数。如果可变参数的类型是泛型或参数化类型，会发生什么问题？
点击翻转
✓ 答案 泛型可变参数

问题根源

可变参数（varargs）的底层实现是数组。而泛型数组是不安全的（Item 28）。两者结合就会产生混乱。

堆污染（Heap Pollution）

当一个参数化类型的变量引用了一个不属于该类型的对象时，就发生了堆污染。

// 危险的示例
static void dangerous(List<String>... stringLists) {
    List<Integer> intList = List.of(42);
    Object[] objects = stringLists;
    objects[0] = intList;  // 堆污染！
    String s = stringLists[0].get(0);  // ClassCastException
}

@SafeVarargs 注解

  • 用于在方法作者保证类型安全的情况下，抑制客户端的警告。
  • 方法是安全的条件：
    1. 方法没有在可变参数数组中存储任何东西。
    2. 没有让对数组的引用逃逸到不信任的代码中。

更安全的替代

当方法同时有泛型和可变参数时，考虑用 List 参数替代可变参数，这样编译器可以保证类型安全。

思路：参数化键（key），而不是容器

不是让容器有一个类型参数，而是让每个键都是参数化的。将参数化的键提交给容器以插入或检索值。

Class<T> 扮演参数化键的角色。因为 Class 是泛型的：String.class 的类型是 Class<String>。

Favorites 示例

public class Favorites {
    private Map<Class<?>, Object> favorites = new HashMap<>();
    public <T> void putFavorite(Class<T> type, T instance) {
        favorites.put(Objects.requireNonNull(type),
                      type.cast(instance));
    }
    public <T> T getFavorite(Class<T> type) {
        return type.cast(favorites.get(type));
    }
}

关键点

  • Map 的值类型是 Object，但键是参数化的 Class<T>。
  • 使用 Class.cast() 方法将值动态转换回正确的类型，确保类型安全。
  • 限制：不能用于不可具体化的类型（如 List<String>），因为 List<String>.class 不存在。

int 枚举模式的问题

  • 类型不安全——可以将 APPLE 常量传给期望 ORANGE 的方法。

  • 性能问题（字符串比较）。

ITEM 35 枚举与注解
为什么要使用实例属性（instance field）替代 ordinal()？
所有枚举都有一个 ordinal() 方法返回常量在枚举类型中的位置。为什么不应该依赖它？
点击翻转
✓ 答案 ordinal

问题

ordinal() 返回枚举常量在枚举声明中的位置（从 0 开始）。如果使用 ordinal 来表示与业务相关的值（如顺序编号、状态码），一旦常量顺序改变或在中间插入新常量，所有依赖 ordinal 值的代码都会出错。

反例

// 错误的做法
public enum Ensemble {
    SOLO, DUET, TRIO;
    public int numberOfMusicians() {
        return ordinal() + 1;  // 脆弱！
    }
}

正确做法：使用实例属性

public enum Ensemble {
    SOLO(1), DUET(2), TRIO(3);
    private final int numberOfMusicians;
    Ensemble(int size) { this.numberOfMusicians = size; }
    public int numberOfMusicians() { return numberOfMusicians; }
}

ordinal 的用途

API 设计时特意说明：ordinal() 是为基于枚举的通用数据结构（如 EnumSet 和 EnumMap）设计的。除非你在编写这样的结构，否则最好避免使用 ordinal()。

ITEM 36 枚举与注解
为什么 EnumSet 替代位属性（bit field）？

点击翻转
✓ 答案 EnumSet

位属性的问题

  • 打印输出时难以理解——只是一个数字。
  • 遍历所有元素需要手动移位。
  • 类型不安全——不同枚举的位属性无法区分。

EnumSet 的优势

  1. 类型安全——是 Set 接口的实现。
  2. 高性能——内部用单个 long 表示（如果枚举 ≤64 个），性能与位属性相当。
  3. 丰富的 Set 操作——removeAll、retainAll、containsAll 等。
  4. 可读性好——打印输出就是集合内容。
  5. 可遍历——可以直接迭代。
// 位属性（旧方式）

为什么 EnumMap 替代序数索引（ordinal indexing）？

✓ 答案 EnumMap

使用 ordinal 做数组索引的问题

  • 类型不安全——数组不知道索引代表什么，编译器无法检查正确性。
  • 需要手动处理偏移——ordinal 从 0 开始，如果想从 1 开始要做偏移转换。

ITEM 40 枚举与注解
为什么应该始终使用 @Override 注解？
一个看似简单的习惯，但能防止一类常见且难以发现的 bug。是什么 bug？
点击翻转
✓ 答案 @Override

防止"看似重写实则重载"的 bug

当你想重写父类方法但不小心参数写错了（或返回类型错了、方法名拼错了），编译器不会报错——因为你以为在重写，实际上只是定义了一个新方法（重载）。这是一个静默的 bug。

如果你加了 @Override 注解但方法并没有真正重写父类方法，编译器会报错。这样你在编译时就能发现问题。

应该在哪里使用

  • 在你想要重写父类或接口中方法声明的每个方法上都使用。
  • 无论是重写具体类的方法、抽象类的方法、还是接口的方法，都应该使用。
  • 现代 IDE 可以自动添加，但需要养成习惯。

一个例外

在具体类中重写抽象方法时，虽然可以不加（编译器已经会检查），但加了也无害且能保持一致性。

简单的习惯，巨大的价值——几秒钟的输入，可能省下几小时的调试。

标记接口（marker interface）与标记注解各有什么优势？何时用哪个？

为什么 lambda 表达式优于匿名类？

匿名类的问题

  • 模板代码太多——即使是一个只有一行方法的类，也要写一大段代码。
  • 可读性差——样板代码掩盖了真正的逻辑。
  • 创建实例有开销。

  1. 简洁——省略了类定义、方法声明等一切冗余，只保留核心逻辑。

// 匿名类

为什么方法引用（method reference）优于 lambda 表达式？

优势

  • 比 lambda 更简洁、更清晰。
  • 方法名就是文档——一眼就能看出意图。
  • 当 lambda 变得复杂时，替换成命名方法 + 方法引用是提高可读性的好方法。

  1. 静态方法：Integer::parseInt → str -> Integer.parseInt(str)
  2. 实例方法（绑定接收者）：str::length → () -> str.length()
  3. 实例方法（未绑定接收者）：String::length → str -> str.length()

ITEM 45 Lambda 与 Stream
为什么要"明智审慎地使用 Stream"？Stream 有什么陷阱？
Stream API 很强大，但过度使用或不当使用会让代码难以阅读和维护。什么情况下不应该用 Stream？
点击翻转
✓ 答案 Stream 慎用

Stream 的价值

Stream 提供了声明式编程风格，可以简洁地表达复杂的数据转换，适合序列计算、过滤、映射、归约等操作。

主要陷阱

  1. 可读性下降——过度使用 Stream（特别是长 pipeline）会让代码变得晦涩难懂。没有显式的变量名和中间步骤。
  2. 难以调试——Stream pipeline 中的异常堆栈信息很难追踪。
  3. 不适合需要局部变量的场景——Stream 是无状态的 pipeline，如果计算需要在多步中读写局部变量，就很难用 Stream 表达。
  4. 滥用 peek 等方法——在 Stream 中做副作用操作是反模式。
  5. 无限流需要谨慎处理——可能导致程序挂起。

最佳实践

  • 使用有意义的方法名来提取复杂的 stream 操作，保持 pipeline 简洁。
  • Stream 和迭代式代码各有优势，选择最清晰、最简洁的方式，不必强行用 Stream。
  • 如果计算需要修改局部变量或使用 try-catch，迭代方式可能更好。
  • 用方法引用替代 lambda 来提高可读性。

为什么 Stream 中应优先使用无副作用的函数？

问题

有些人把 Stream 当作"增强的 for-each 循环"，在 forEach 或 peek 中做各种副作用操作（修改变量、写外部数据结构）。这完全背离了 Stream 的设计初衷。

为什么不好

  1. 失去并行化能力——有副作用的函数无法安全地并行执行。
  2. 可读性差——Stream pipeline 的价值在于声明式、纯函数的转换。夹杂副作用让代码意图不清晰。
  3. 难以推理——纯函数的结果只取决于输入，有副作用则依赖外部状态。

正确做法

Stream 的中间操作（map、filter、flatMap 等）应该是无副作用的纯函数。结果通过收集器（Collector）聚合，而不是通过副作用累积。

收集器（Collectors）是 Stream 的最佳搭档：

  • toList()、toSet()、toMap() — 收集到集合
  • groupingBy() — 分组
  • joining() — 字符串拼接
  • counting()、summingInt() — 统计
  • maxBy()、minBy() — 最大/最小
  • partitioningBy() — 分区（true/false）

为什么方法返回类型应优先选择 Collection 而不是 Stream？
既然 Stream 这么强大，为什么不把所有返回集合的方法都改成返回 Stream？
点击翻转
✓ 答案 Collection vs Stream

问题

Stream 只能被消费一次——如果你试图遍历两次会抛出异常。如果方法返回 Stream，客户端可能想做简单的 for-each 遍历，却不得不处理一次性迭代的限制。

为什么 Collection 通常更好

  1. 双重用途——Collection 既可以用于 for-each 遍历，也可以通过 stream() 方法转为 Stream。
  2. 可重复遍历——Collection 可以反复迭代。
  3. 丰富的 API——size、contains、isEmpty 等方法立即可用。
  4. 互操作性好——更多代码接受 Collection 参数而不是 Stream 参数。

什么时候返回 Stream 是合理的

  • 返回的是大量数据且只需要 Stream 处理。
  • 返回的是无限或延迟计算的数据。
  • 方法本身就是 Stream pipeline 的一部分（如中间操作）。

什么时候返回 Iterable

当集合可能很大但客户端只需要遍历（不需要 size() 等方法）时，Iterable 是一个轻量选择。但大多数情况下 Collection 更好。

简而言之：编写公共 API 时，优先返回 Collection 而不是 Stream——给客户端最大的灵活性。

为什么要谨慎使用 Stream 并行？

点击翻转
✓ 答案 流并行

并行不是免费的性能提升

并行化有开销：任务划分、线程调度、结果合并。如果数据量不大或计算不密集，并行化的开销可能超过收益。

并行效果好的条件

  1. 数据量大——数据元素足够多，每个元素的计算开销足够大。
  2. 数据源可有效拆分——ArrayList、数组、IntStream.range 等效果好；LinkedList、Stream.iterate 效果差。
  3. 终端操作适合并行——reduce、collect 等有可合并的结果；forEach 等有副作用的不适合。
  4. Q 因素高——即每个元素的计算成本高。

常见陷阱

  • 性能下降——开销超过收益，特别是小数据集。
  • 结果错误——如果使用了有状态的中间操作（如 distinct、sorted、limit）或有副作用的函数。
  • 死锁——共享公共的 ForkJoinPool。

原则

不要为了"可能更快"就随便加 parallel()。只有在有性能问题、数据足够大、计算足够重、并且经过基准测试验证的情况下才使用并行流。大多数情况下，顺序流是正确且高效的选择。

什么是防御性拷贝（defensive copy）？什么时候需要做？

点击翻转
✓ 答案 防御性拷贝

问题场景

一个看似不可变的时间段类：

public final class Period {
    private final Date start;
    private final Date end;
    public Period(Date start, Date end) {
        if (start.after(end)) throw new IllegalArgumentException();
        this.start = start;
        this.end = end;
    }
    public Date start() { return start; }
    public Date end() { return end; }
}

攻击方式 1：客户端修改传入的 Date 对象。

攻击方式 2：客户端通过 getter 修改内部的 Date 对象。

防御方法

  1. 构造方法中做防御性拷贝： 
    this.start = new Date(start.getTime());
    注意：先拷贝再校验（防止在拷贝和校验之间被并发修改）。
  2. getter 返回拷贝而非原引用： 
    public Date start() { return new Date(start.getTime()); }

什么时候需要

  • 类持有客户端可能修改的可变组件时（如 Date、数组）。
  • 特别是在不可变类中——引用了可变对象就必须保护好。

提示

Java 8 之后应该用 Instant 或 LocalDate 替代 Date，因为它们是不可变的，就不需要防御性拷贝了。

ITEM 52 方法
为什么要明智审慎地使用重载（overloading）？重载有什么陷阱？
重载方法的选择是在编译时决定的，重写方法的选择是在运行时决定的。这个区别会导致什么意外？
点击翻转
✓ 答案 重载

核心问题：重载是静态选择的

对于重载方法，调用哪个版本取决于编译时的参数类型，而不是运行时的实际类型。这与重写（override）正好相反。

例：

public static String classify(Set<?> s) { return "Set"; }
public static String classify(List<?> l) { return "List"; }
public static String classify(Collection<?> c) { return "Collection"; }

// 意外的行为：
Collection<?>[] collections = { Set.of(), List.of() };
for (Collection<?> c : collections)
    System.out.println(classify(c));
// 全部打印 "Collection"！
// 因为编译时类型是 Collection，运行时不参与重载选择

重写 vs 重载

  • 重写：运行时根据对象的实际类型选择方法。
  • 重载：编译时根据参数的声明类型选择方法。

建议

  1. 避免歧义——不要重载相同数量参数的方法，尤其是参数类型可以互相转换的情况。
  2. 用不同的方法名替代重载（如 writeInt、writeLong）。
  3. 如果必须重载，确保重载方法的行为一致——不管调用哪个重载，结果应该一致（如 String.valueOf 对各种类型都返回合理的字符串）。

为什么要明智审慎地使用可变参数（varargs）？

点击翻转
✓ 答案 可变参数

可变参数的特点

每次调用都会创建并初始化一个数组。如果参数数量不固定，这很方便，但有性能开销。

性能优化技巧

如果方法通常被调用时参数数量很少，可以提供多个重载版本：

public void foo() { }
public void foo(int a1) { }
public void foo(int a1, int a2) { }
public void foo(int a1, int a2, int... rest) { }

这样大多数调用（0、1、2 个参数）不需要创建数组，只有参数更多时才使用可变参数版本。EnumSet 就是这样做的。

与泛型结合的风险

泛型 + 可变参数 = 堆污染风险（Item 32）。只有在方法确实类型安全时才使用 @SafeVarargs 注解。

使用建议

  • 当方法确实需要接受可变数量的参数时才使用。
  • 如果性能是关键考虑因素，考虑提供固定参数数量的重载。
  • 与泛型一起使用时务必确保类型安全（Item 32）。

为什么应该返回空的数组或集合，而不是返回 null？

返回 null 的问题

  1. 客户端必须处理 null——每次调用后都要做 null 检查，代码臃肿。忘记检查就会导致 NullPointerException。
  2. 降低可读性——客户端代码充斥着 if-null 检查。

  • 返回空集合：Collections.emptyList()、Collections.emptySet()、Collections.emptyMap()——这些都是单例，没有分配开销。

public List<Cheese> getCheeses() {

        ? Collections.emptyList()

}

关于性能的说明

有人担心每次都返回新的空集合会有性能问题。其实 Collections.emptyList() 返回的是同一个不可变实例，完全没有分配开销。空数组也可以缓存为静态常量。

什么时候应该返回 Optional<T>？与返回 null 或抛出异常相比有什么优势？

Optional 的优势

  1. 明确表示可能没有结果——方法签名就说明了"可能返回空"，调用者必须处理。

  • optional.orElse(defaultValue)——提供默认值。

为什么最小化作用域

  1. 可读性和可维护性——变量在哪里声明、用来做什么一目了然。

传统 for 循环的问题

ITEM 60 通用编程
为什么需要精确答案时要避免使用 float 和 double？

点击翻转
✓ 答案 float / double

问题：二进制浮点数的精度限制

float 和 double 是基于 IEEE 754 标准的二进制浮点数。它们不能精确表示 0.1 这样的十进制小数（就像十进制不能精确表示 1/3 一样）。

经典示例：

System.out.println(1.00 - 9 * 0.10);
// 输出：0.09999999999999998

替代方案

  1. BigDecimal——精确的十进制运算。适合货币计算等需要精确结果的场景。缺点：性能较慢、代码稍繁琐。
  2. 使用 int 或 long——如果小数位数固定（如 2 位小数表示金额），可以乘以 100 用整数计算。性能最好。

什么时候用 float/double

科学计算、工程计算等对精度要求不高（但范围要求大）的场景。float 主要用于大型 float 数组以节省内存，否则优先用 double（因为 Java 对 double 优化更好）。

总结

货币计算、精确金额、会计系统——绝对不要用 float/double。选择 BigDecimal 或整数分/厘计算。

✓ 答案 基本类型 vs 包装类

主要区别

  • 基本类型（int, long, double 等）——直接存储值，速度快，占内存少，没有 null。
  • 包装类（Integer, Long, Double 等）——是对象，有引用开销，可以为 null，可用于泛型。

包装类的问题

  1. 性能差——对象创建和 GC 开销，自动装箱/拆箱有运行时成本。
  2. NullPointerException 风险——自动拆箱时如果是 null 会抛 NPE，而且可能发生在很隐蔽的地方。
  3. == 比较的是引用而不是值——Integer a = 128; Integer b = 128; a == b 为 false（超出缓存范围）！
  4. 内存占用大——一个 Integer 对象占的内存远大于一个 int。

什么时候必须用包装类

  • 作为泛型类型参数——泛型不允许基本类型（如 List<Integer>）。
  • 需要表示"无值"（null）的场景——但考虑用 OptionalInt 替代（Item 55）。

原则

能用基本类型就用基本类型。只有在必须用对象的场合（泛型、null 值）才用包装类。自动装箱/拆箱虽然方便，但掩盖了两者的区别，要格外小心。

✓ 答案 字符串滥用

字符串被滥用的常见场景

  1. 代替枚举类型——用字符串常量表示枚举值。没有类型安全，拼写错误运行时才发现。用枚举类型（Item 34）。
  2. 代替聚合类型——把多个字段拼成一个字符串传递。难以解析、容易出错、性能差。写一个小类或使用 record。
  3. 代替能力表（capability）——用字符串作为钥匙/权限标识。无法进行安全检查，容易伪造。应该用不可伪造的对象引用。

为什么字符串不适合

  • 没有类型安全——任何字符串都可以传入。
  • 没有语义——"admin" 是角色名、用户名还是权限名？从类型上看不出来。
  • 解析成本高——从字符串中提取信息需要解析，既慢又容易错。
  • 无法利用编译期检查——拼写错误、格式错误都要到运行时才发现。

原则

如果有更合适的数据类型，就不要用字符串。数值用数值类型，是/否用 boolean，枚举用枚举类型，复合数据用类。字符串只适合表示文本数据。

ITEM 63 通用编程
字符串连接的性能陷阱是什么？正确做法是什么？
用 + 运算符连接字符串有什么性能问题？在什么情况下才是问题？应该如何优化？
点击翻转
✓ 答案 字符串拼接

问题

使用 + 运算符在循环中拼接字符串时，每次循环都会创建新的 StringBuilder 和新的 String 对象，时间复杂度是 O(n²)。当字符串很多时性能急剧下降。

// 慢！O(n²)
String result = "";
for (int i = 0; i < numItems; i++) {
    result += lineForItem(i);
}

正确做法：使用 StringBuilder

// 快！O(n)
StringBuilder sb = new StringBuilder();
for (int i = 0; i < numItems; i++) {
    sb.append(lineForItem(i));
}
String result = sb.toString();

注意事项

  • 只有在循环/大量拼接时才会有显著性能问题。简单的几个字符串用 + 拼接完全没问题，编译器会优化。
  • 提前预估 StringBuilder 的容量（new StringBuilder(capacity)）可以避免多次扩容，进一步提升性能。
  • 不要过早优化——先确定这里真的是性能瓶颈再优化。

简单的经验法则：如果字符串拼接的数量不固定（特别是在循环中），就用 StringBuilder。如果只是固定几个字符串拼接，用 + 既清晰又足够快。

为什么用接口类型

  1. 灵活性——以后想换个实现类（比如从 ArrayList 换成 LinkedList），只需改构造方法那一行，其他代码完全不变。
  2. 面向接口编程——这是面向对象设计的基本原则。依赖于抽象而不是具体实现。

ITEM 65 通用编程
为什么接口优于反射？反射有什么代价？

点击翻转
✓ 答案 反射

反射的代价

  1. 编译时类型检查失效——拼写错误、参数类型错误都要到运行时才发现。
  2. 代码冗长丑陋——需要处理大量异常，代码可读性差。
  3. 性能差——反射调用比普通方法调用慢得多（几十到几百倍）。
  4. 安全限制——在安全管理器下可能无法使用。

反射的合理用途

  • 创建对象——根据类名动态创建实例（如插件系统、SPI）。但创建后仍应通过接口访问。
  • 框架和工具——如依赖注入框架、ORM 框架、测试框架等。

最佳实践

对于大多数应用程序，正常情况下不应该使用反射。如果只是想动态创建对象，可以用以下模式：

  1. 用反射创建实例（Class.newInstance() 或构造方法）。
  2. 将创建的对象通过其接口或超类类型来访问（Item 64）。

这样只在创建时使用反射（一次性能开销），后续访问都是正常的方法调用，既灵活又高效。

ITEM 67 通用编程
为什么要明智审慎地进行优化？有哪些常见的优化误区？
"过早优化是万恶之源"——这句话经常被引用。在 Java 中优化代码应该遵循什么原则？
点击翻转
✓ 答案 优化

优化的三个谬论

  1. "随便哪里优化一下都有帮助"——大多数代码的性能对整体影响微乎其微。
  2. "我能猜出瓶颈在哪里"——人类对性能瓶颈的直觉非常不可靠。
  3. "优化后代码还是一样清晰"——为了性能做的折中往往损害可读性和可维护性。

正确的做法

  1. 先写好代码，再考虑性能——写出清晰、正确、结构良好的代码。好的结构本身就更容易优化。
  2. 用性能分析工具（profiler）找瓶颈——不要猜，用数据说话。
  3. 测量优化效果——每次优化后都要测量，确认真的变快了。
  4. 在更高层次优化——通常算法和数据结构的改进比低层微调效果大得多。

API 设计层面也要考虑性能

虽然不应为了性能而牺牲好的 API 设计，但 API 设计会影响性能（例如可变类型 vs 不可变类型的选择、方法调用的开销）。值得在设计时就考虑到可能的性能影响，但不要因此牺牲设计的清晰性。

总结：努力写出好的代码，而不是快的代码。如果代码不够快，再去测量和优化。

为什么只在真正异常的情况下才使用异常？
有些人滥用异常来做控制流（比如用异常来结束循环）。为什么这是不好的做法？
点击翻转
✓ 答案 异常只用于异常

为什么不能用异常做控制流

  1. 慢——异常的创建、堆栈填充等开销很大，比正常控制流慢得多。JVM 也不会优化异常路径。
  2. 代码意图不清晰——异常是用来表示异常情况的，用它做正常控制流会迷惑读者。
  3. 可能掩盖真正的 bug——如果异常被用来做流程控制，真正的异常（如空指针、数组越界）可能被意外捕获并忽略。
  4. 违反设计初衷——异常机制就是为异常情况设计的，不要滥用。

正确做法

状态检查优先于异常——在执行可能失败的操作之前，先检查状态。

// 错误：用异常做控制流
try {
    int i = 0;
    while (true)
        range[i++].climb();
} catch (ArrayIndexOutOfBoundsException e) { }

// 正确：用边界检查
for (Mountain m : range)
    m.climb();

状态检查方式的选择

  • 用 Optional 或返回特殊值（如 null、-1）表示失败。
  • 或者提供 hasNext() / isEmpty() 等状态检查方法。
ITEM 70 异常
受检异常、运行时异常、Error 分别用于什么场景？
Java 有三种可抛出结构。何时用受检异常？何时用运行时异常？Error 又是什么？
点击翻转
✓ 答案 异常分类

受检异常（checked exception）

  • 继承自 Exception（但不是 RuntimeException 的子类）。
  • 用于调用者可以合理地恢复的情况。
  • 方法必须声明 throws，调用者必须捕获或继续抛出。
  • 示例：IOException、SQLException。

运行时异常（unchecked / RuntimeException）

  • 继承自 RuntimeException。
  • 用于编程错误——即调用方违反了 API 约定。
  • 不强制捕获，通常也不应该捕获（因为是 bug，应该修复而不是处理）。
  • 示例：NullPointerException、IllegalArgumentException、IllegalStateException。

Error

  • 继承自 Error。
  • 由 JVM 保留使用，表示资源不足、约束失败或其他不可恢复的错误。
  • 应用程序通常不应该抛出 Error，也不应该捕获。
  • 示例：OutOfMemoryError、StackOverflowError。

判断标准

问自己：调用者能做些什么来恢复？如果能，用受检异常。如果是调用方的编程错误，用运行时异常。

ITEM 71 异常
为什么要避免不必要地使用受检异常？
受检异常强制调用者处理，这是好事。但过度使用会让 API 难以使用。什么时候不该用受检异常？
点击翻转
✓ 答案 避免不必要的受检异常

受检异常的代价

  • 调用者必须处理——要么 try-catch，要么继续 throws 声明。
  • Stream 和 lambda 中使用不方便（lambda 不能抛出受检异常）。
  • 过度使用会让方法调用变得繁琐，程序员可能会"吞掉"异常了事。

替代方案

  1. 返回 Optional（Item 55）——如果失败是常见的且只有一种失败原因，返回空 Optional 比抛受检异常更简洁。
  2. 提供状态检查方法——让调用者可以先检查再调用（如 hasNext()），从而避免异常。
  3. 改为运行时异常——如果异常表示的是编程错误而不是可恢复的情况，应该是 RuntimeException。

何时用受检异常

只有当：

  1. 异常是无法避免的（即使正确使用 API 也可能发生）。
  2. 调用者可以采取有意义的恢复措施。

两个条件都满足时才使用受检异常。否则用未受检异常或 Optional。

ITEM 73 异常
什么是"异常转译"（exception translation）？为什么需要它？
当底层抛出的异常与高层抽象不匹配时，应该怎么做？什么是异常链（exception chaining）？
点击翻转
✓ 答案 异常转译

什么是异常转译

捕获低层异常，然后抛出一个对应高层抽象的新异常。让异常与抽象层次相匹配。

// 异常转译示例
try {
    // 使用低层资源
    ...
} catch (LowerLevelException e) {
    throw new HigherLevelException("详细信息", e);
}

为什么需要

  • 调用者不需要了解底层实现细节。
  • 异常应该反映 API 的抽象层次，而不是泄露实现细节。
  • 让 API 更干净、更稳定。

异常链（Exception Chaining）

在转译时将原始异常作为 cause 传入新异常（使用带 cause 参数的构造方法或 initCause()）。这样既提供了高层视角，又保留了底层原因，便于调试。

与"异常转译"相关的实践

  • 异常转译优于"异常静默吞掉"。
  • 但不要滥用——如果可以避免异常就更好（如在更高层做参数校验）。
  • 低层方法如果能确保自己抛出的异常对高层也是合适的，就不需要转译。

为什么重要

异常描述了方法在什么情况下会失败。不文档化异常，调用者就不知道如何正确处理失败。

文档化要求

  • 所有受检异常都应该用 @throws 标签单独文档化，说明在什么条件下抛出。
  • 未受检异常（RuntimeException）也应该文档化——虽然不强制捕获，但调用者知道可能发生什么异常仍然很重要。
  • 接口方法的异常文档也很重要——它定义了实现者必须遵守的约定。

常见做法

/**
 * 从列表中获取指定位置的元素。
 * @param index 要获取的元素索引
 * @return 指定位置的元素
 * @throws IndexOutOfBoundsException 如果索引越界
 *         ({@code index < 0 || index >= size()})
 */
E get(int index);

注意事项

  • 不要把所有可能的异常一股脑儿列出来——只文档化那些方法本身承诺可能抛出的。
  • 运行时异常通常是编程错误的信号，说明调用者违反了约定。文档化它们就是在说明约定。
ITEM 75 异常
为什么异常的细节消息中应该包含失败捕获信息？

点击翻转
✓ 答案 异常细节消息

为什么重要

异常发生后，堆栈信息告诉你哪里出了错，但异常的细节消息告诉你为什么出错。好的细节消息能让你不用看源代码就理解问题。

应该包含什么

  • 所有参与失败的参数和字段的值。
  • 例如 IndexOutOfBoundsException 应该包含：下界、上界、实际索引值。

示例

public IndexOutOfBoundsException(int lowerBound, int upperBound, int index) {
    super(String.format(
        "Lower bound: %d, Upper bound: %d, Index: %d",
        lowerBound, upperBound, index));
    this.lowerBound = lowerBound;
    this.upperBound = upperBound;
    this.index = index;
}

注意事项

  • 异常消息是为程序员看的，不是给最终用户看的。所以应该包含技术细节，而不是用户友好的描述。
  • 不需要冗长的叙述——简洁地列出关键值即可。
  • 对于受检异常，可以考虑提供访问方法（getter）来获取失败信息，以便编程方式访问。

什么是"失败原子性"（failure atomicity）？如何实现？
一个方法抛出异常后，对象应该处于什么状态？为什么这很重要？有哪些实现技术？
点击翻转
✓ 答案 失败原子性

什么是失败原子性

方法抛出异常后，对象应该仍然处于定义良好的一致状态。换句话说，失败的方法调用不应该把对象搞坏。

为什么重要

  • 对象被破坏后，后续操作可能产生不可预测的结果。
  • 调用者可能尝试恢复，前提是对象还处于有效状态。
  • 对于不可变类，天然满足失败原子性。

实现技术

  1. 参数校验放在修改之前——先检查所有参数是否合法，检查通过后才修改对象状态。（Item 49）
  2. 调整操作顺序——把可能失败的操作放在前面，状态修改放在后面。
  3. 写时复制（copy-on-write）——先在副本上操作，成功后再替换原对象。
  4. 恢复代码（recovery / rollback）——用事务或回滚机制恢复到操作前状态。

注意

虽然失败原子性通常是期望的，但不一定总能实现（如并发修改导致的 ConcurrentModificationException）。即使如此，也应该在文档中说明失败后的状态。

为什么不要忽略异常？

忽略异常的危险

// 糟糕的代码！

    ...
} catch (SomeException e) {
    // 空的！
}
  1. 静默失败——错误发生了但没有人知道，后续可能在完全不相关的地方导致更严重的问题。
  2. 难以调试——没有堆栈信息，找不到根因。
  3. 对象可能被破坏——异常可能意味着不变量被违反，忽略它会让对象处于不一致状态。

  • 处理异常——采取恢复措施，或向上抛出。

极少数情况下，异常是预期的且无害的。例如：

  • 关闭资源时的异常（但 try-with-resources 已经处理了）。
  • FileInputStream 关闭时的异常（文件已经读完了）。

ITEM 78 并发
为什么要同步访问共享的可变数据？同步仅仅是互斥吗？
很多人对 synchronized 的理解仅限于"互斥"。但同步还有另一个同样重要的作用。是什么？
点击翻转
✓ 答案 同步访问共享可变数据

同步的两个作用

  1. 互斥（mutual exclusion）——同一时刻只有一个线程能执行临界区代码，防止对象状态不一致。
  2. 可见性（visibility）——确保一个线程的修改能被其他线程看到。进入同步块时读取最新值，退出时把修改刷回主存。

很多人只知道互斥，忽略了可见性。这也是为什么即使操作是原子的（如读写一个 int 变量），仍然可能需要同步。

没有同步的可怕后果

一个线程修改了变量，另一个线程可能永远看不到修改——它可能一直读到旧值。这就是"活性失败"（liveness failure）。

volatile 关键字

volatile 只保证可见性，不保证原子性。当不需要互斥只需要可见性时可以使用（例如状态标记位）。但如果是读-改-写操作（如 increment），volatile 不够，需要 synchronized 或原子类。

最佳建议

最好的方法是不共享可变数据——让数据不可变（Item 17），或把可变数据限制在单个线程内。如果必须共享，就正确同步。

ITEM 79 并发
为什么要避免过度同步？过度同步有什么问题？
同步不够会有问题，同步太多也会有问题。过度同步会导致什么？应该怎么避免？
点击翻转
✓ 答案 避免过度同步

过度同步的问题

  1. 性能下降——不必要的同步浪费资源。
  2. 死锁风险——在同步块内调用外部方法（可能也加了锁），容易导致死锁。
  3. 意外结果——在同步块中回调外部方法，外部方法可能修改对象状态或抛出异常，导致不一致。

正确做法

  • 同步区域内做尽可能少的工作——只做必要的状态访问/修改。
  • 永远不要在同步区域内调用外来方法（alien method）——即可能被重写的方法或作为参数传入的方法。
  • 如果必须通知客户端，在同步区域外调用（先保存需要的数据，解锁后再回调）。

并发性和性能的平衡

在同步区域内做的工作越少越好。将耗时的计算移出同步块。

总结

在同步区域中，不要调用设计为被重写的方法，也不要调用以函数对象形式提供的方法。从类的角度来看，这些都是外来方法，可能在持有锁的时候做各种事情（修改状态、获取其他锁……），导致死锁和数据损坏。

直接操作线程的问题

  • 每个任务创建一个新线程——线程创建和销毁有开销。
  • 线程数量不受控——太多线程会耗尽内存和 CPU。
  • 需要手动管理线程生命周期。

  1. 线程池复用——线程可以被重复使用，减少创建/销毁开销。
  2. 任务与执行解耦——你提交任务（Runnable/Callable），由执行器决定如何运行。
  3. 丰富的配置——可以配置线程数、队列、拒绝策略等。

ITEM 81 并发
为什么并发工具优于 wait 和 notify？

点击翻转
✓ 答案 并发工具

wait/notify 的问题

  • 容易出错——必须在循环中调用 wait（防止虚假唤醒），很容易遗漏。
  • 代码晦涩——正确使用 wait/notify 的代码很难写对，也很难读。
  • 需要手动管理条件队列。

并发工具分类

  1. 同步器（Synchronizers）
    • CountDownLatch——一次性门闩，等待计数归零。
    • Semaphore——信号量，控制并发数量。
    • CyclicBarrier——循环栅栏，多线程互相等待。
    • Future / CompletableFuture——异步结果。
  2. 并发集合
    • ConcurrentHashMap——高并发 Map。
    • ConcurrentSkipListMap/Set——并发有序集合。
    • BlockingQueue——阻塞队列（生产者-消费者模式）。
  3. 原子类（java.util.concurrent.atomic）
    • AtomicLong、AtomicReference 等——无锁原子操作。

用高层并发工具，几乎没有理由再使用 wait/notify。如果不得不使用（例如维护老代码），一定要在循环中调用 wait，并且使用标准模式。

ITEM 82 并发
为什么线程安全属性应该写在文档中？
一个类的线程安全性是它 API 的重要组成部分。线程安全性有哪些级别？应该如何文档化？
点击翻转
✓ 答案 线程安全文档

为什么重要

如果类的文档没说它是不是线程安全的，用户只能猜。猜错了可能导致并发 bug。或者用户被迫给每个调用都加锁，浪费性能。

线程安全级别（从高到低）

  1. 不可变（Immutable）——实例不可修改，多线程共享完全安全。如 String、Long。
  2. 无条件线程安全——可变对象，但内部有足够同步，客户端无需外部同步。如 ConcurrentHashMap、AtomicLong。
  3. 有条件线程安全——某些方法需要外部同步。如 Collections.synchronized 包装的集合（迭代时需要外部同步）。
  4. 非线程安全——客户端必须自己加锁。如 ArrayList、HashMap。
  5. 线程对立——即使每个方法都同步也不安全（因为有静态可变状态等）。尽量避免。

如何文档化

  • 在类级别的 Javadoc 中说明线程安全级别。
  • 有条件线程安全的类，需要说明哪些操作需要同步、同步在哪个锁上。
  • 如果类暴露了内部锁（或建议使用某个锁），也需要文档化。

不要假设类应该是线程安全的还是不安全的——明确地把你的承诺写在文档里。

ITEM 83 并发
为什么要谨慎使用延迟初始化（lazy initialization）？
延迟初始化就是"直到第一次用到才初始化"。听起来很有用，为什么这条建议是"谨慎使用"？有哪些实现方式？
点击翻转
✓ 答案 延迟初始化

为什么要谨慎

  • 性能收益通常被夸大——大多数情况下，正常初始化就够快了。
  • 增加复杂性——延迟初始化的代码更复杂，更容易出错（尤其是并发场景）。
  • 可能反而更慢——双重检查锁定等模式在某些实现下可能比直接初始化还慢。

实现方式（按推荐程度排序）

  1. 正常初始化（默认选择）——大多数时候直接初始化最好。 
    private final FieldType field = computeFieldValue();
  2. holder 类模式（静态字段）——利用 JVM 的类加载延迟。 
    private static class FieldHolder {
    static final FieldType field = computeFieldValue();
}
static FieldType getField() { return FieldHolder.field; }
  3. 双重检查锁定（实例字段）——需要 volatile。 
    private volatile FieldType field;
FieldType getField() {
    FieldType result = field;
    if (result == null) {
        synchronized (this) {
            if (field == null)
                field = result = computeFieldValue();
        }
    }
    return result;
}

总结：除非确实需要，否则不要用延迟初始化。多数情况下，即时初始化是最好的选择。

ITEM 84 并发
为什么不要依赖线程调度器？
线程调度器决定哪个线程运行多久。程序的正确性或性能不应该依赖于它。为什么？应该怎么做？
点击翻转
✓ 答案 线程调度器

为什么不能依赖

  • 不可移植——不同 JVM、不同操作系统的线程调度策略不同。
  • 脆弱——操作系统版本更新或 JVM 升级都可能改变调度行为。
  • Thread.yield() 和线程优先级不可靠——它们只是对调度器的"建议"，具体行为取决于实现。

常见错误做法

  • 用 Thread.yield() 来"让其他线程有机会运行"——不可靠。
  • 调整线程优先级来"确保"某些线程先运行——不可移植。
  • 通过 Thread.sleep() 来等待某个操作完成——竞态条件，不可靠。

正确做法

  1. 使用并发工具（Item 81）——用锁、同步器、并发集合来控制线程交互。
  2. 保持可运行线程的合理数量——线程数 ≈ CPU 核心数时性能最好（CPU 密集型）。
  3. 让每个线程做有意义的工作——不要让线程忙等（busy waiting）。
  4. 使用 wait/notify 或并发工具进行协调，而不是靠线程优先级或 yield。

如果程序因为线程调度器的原因无法正常工作，那么它就是有 bug 的。修复方法是重构程序的并发结构，而不是调整线程优先级。

为什么优先选择 Java 序列化的替代方案？

点击翻转
✓ 答案 序列化替代方案

Java 序列化的问题

  1. 安全漏洞——反序列化不可信数据可能导致远程代码执行等严重漏洞。
  2. 类的"后门"构造——readObject 相当于另一个构造方法，绕过了正常的对象创建过程。
  3. 版本兼容问题——类的结构变化可能导致序列化格式不兼容。
  4. 测试负担重——需要测试序列化/反序列化的正确性和兼容性。
  5. 跨语言不友好——只有 Java 能读。

  • JSON（如 Jackson、Gson）——文本格式，人类可读，跨语言。
  • Protocol Buffers（protobuf）——二进制格式，高性能，跨语言，前向/后向兼容。
  • MessagePack、Avro、Thrift 等。

选择建议

  • 需要人类可读 → JSON。
  • 需要高性能和紧凑表示 → Protocol Buffers 等二进制格式。
  • 跨语言通信 → 一定选跨平台格式。

ITEM 86 序列化
为什么要非常谨慎地实现 Serializable？
实现 Serializable 看起来很简单——什么都不用做，类就可以序列化了。但这其实是一个重大的承诺。为什么？
点击翻转
✓ 答案 谨慎实现 Serializable

实现 Serializable 的代价

  1. 降低了改变类实现的灵活性——一旦发布，序列化格式就成了 API 的一部分，以后改变类结构需要考虑向后兼容。
  2. 增加了 bug 和安全漏洞的可能性——序列化是"语言之外的对象创建机制"，可能绕过构造方法的约束。
  3. 测试负担加重——需要测试序列化/反序列化，以及不同版本之间的兼容性。
  4. 影响子类设计——父类实现了 Serializable，子类也必须处理序列化问题。

什么时候应该实现

  • 类主要用于数据传输（如 DTO）。
  • 类需要参与 Java 序列化框架（如 RMI、JMS）。

设计为继承的类要特别小心

  • 如果类设计为被继承，通常不应该实现 Serializable（给子类增加不必要的负担）。
  • 如果父类没有实现 Serializable，子类实现时要确保父类有可访问的无参构造方法。

内部类（Item 24）通常不应该实现 Serializable——编译器生成的字段不稳定。

ITEM 87 序列化
什么时候应该考虑使用自定义的序列化形式？
默认序列化形式（Serializable 什么都不用写）方便但不一定合适。自定义序列化形式有什么优势？
点击翻转
✓ 答案 自定义序列化形式

默认序列化形式的问题

  • 与内部表示绑定——默认序列化直接输出所有非 transient 字段，把内部结构暴露在序列化格式中。
  • 体积大——保存了不必要的信息（如冗余的链表指针）。
  • 速度慢——递归遍历对象图。
  • 栈溢出风险——对象图太深可能导致序列化时栈溢出。

什么时候用自定义形式

  • 当类的物理表示与逻辑表示差异较大时。例如：
    • HashSet/HashMap——逻辑上是键值对集合，物理上是哈希表 + 链表/红黑树。
    • String——逻辑上是字符序列，物理上有 offset/count 等内部字段（历史上）。

  • writeObject() / readObject()——自定义序列化/反序列化逻辑。
  • transient 关键字——标记不参与默认序列化的字段。

原则

如果默认序列化形式合理（类的物理表示基本就是逻辑表示），就用默认的。否则，应该认真考虑自定义序列化形式。设计好的序列化形式与设计好的 API 一样重要。

ITEM 88 序列化
为什么 readObject 方法要"保护性地编写"？
readObject 本质上是一个"以字节流为参数的构造方法"。但它没有构造方法的保护。有哪些常见陷阱？
点击翻转
✓ 答案 readObject 防御

核心问题

反序列化会创建新对象，但绕开了正常的构造方法和参数校验。攻击者可以构造恶意字节流，让反序列化出来的对象违反类的不变量。

readObject 必须做的事

  1. 参数校验——反序列化后验证所有字段的合法性，确保对象处于有效状态。（Item 49）
  2. 防御性拷贝——对可变对象的字段做拷贝，防止攻击者通过修改原始字节流中的引用结构来篡改内部状态。（Item 50）
  3. 不要调用可覆盖的方法——与构造方法一样，readObject 中也不能调用可被覆盖的方法。（Item 19）
  4. 保持失败原子性——反序列化失败不应该留下半初始化的对象。

常见攻击方式

  • 伪造字节流让对象字段值违反约束（如负数长度）。
  • 构造对象图让内部字段引用可变对象，反序列化后通过外部引用修改。
  • 反序列化链（gadget chain）——利用一系列反射和方法调用达到远程代码执行。

防御

永远不要反序列化不可信数据。如果必须实现 readObject，确保它像构造方法一样严格——校验所有参数，做防御性拷贝。

ITEM 89 序列化
为什么对于实例控制（Singleton），枚举类型优于 readResolve？
如果一个 Singleton 类实现了 Serializable，反序列化会创建新实例，破坏单例。readResolve 可以解决，但枚举更好。为什么？
点击翻转
✓ 答案 readResolve vs 枚举

问题：序列化 + Singleton

默认情况下，每次反序列化一个 Serializable 的单例类都会创建一个新对象——单例被破坏了！

readResolve 方案

提供一个 readResolve 方法，在反序列化后返回正确的单例实例，替换刚创建的对象：

private Object readResolve() {
    return INSTANCE; // 返回真正的单例
}

readResolve 的问题

  1. 依赖所有字段都是 transient 的——如果有非 transient 的引用字段，攻击者可以在 readResolve 执行前获取到对象引用，进行"盗用"攻击。
  2. 容易写错——访问修饰符、返回类型不对就不会被调用。
  3. 不能阻止攻击者创建多个实例——通过字节流操纵仍然可能。

枚举方案（最佳）

用单元素枚举实现单例（Item 3），序列化由 Java 保证：

  • Java 保证枚举反序列化后还是同一个实例。
  • 没有 readResolve 那种漏洞。
  • 代码最简单。

结论：如果你需要对实例进行控制，并且序列化很重要，枚举类型是最佳选择。

什么是序列化代理模式（Serialization Proxy）？为什么它更安全？

✓ 答案 序列化代理

基本思路

不直接序列化/反序列化原对象，而是用一个简单的代理对象来做序列化。

序列化时：原对象 → 创建代理对象（保存逻辑数据）→ 序列化代理。

反序列化时：反序列化代理 → 代理创建原对象（通过正常构造方法）→ 返回原对象。

实现要点

  1. 在原类中定义一个私有静态内部类作为序列化代理，实现 Serializable。
  2. 原类提供 writeReplace() 方法，返回代理对象（序列化时自动调用）。
  3. 代理类提供 readResolve() 方法，调用原类构造方法创建实例。
  4. 原类的 readObject() 抛异常（防止直接反序列化攻击）。

优势

  • 极大的安全性——反序列化时使用正常的构造方法，所有构造方法的校验都生效。不需要防御性拷贝。
  • 灵活性——代理的字段可以与原类完全不同，解耦了物理表示和序列化格式。
  • 不影响类的不可变性——反序列化出来的就是构造好的不可变对象。

局限

  • 不能与继承体系中的用户扩展类兼容（因为 readResolve 返回的是新对象，不是子类对象）。
  • 有轻微的性能开销。

对于不可变类，序列化代理模式是一个非常值得考虑的方案。
