介绍如何高效、安全地创建和销毁对象

📋 共 9 条
第 1 条

考虑使用静态工厂方法替代构造方法

💬 探讨使用静态工厂方法替代公共构造方法的优缺点。
  • 有名字：静态工厂方法有名称，比构造方法更易读懂、便于使用，避免重载歧义
  • 不必每次创建新对象：可重复返回相同实例（实例控制），是单例、不可变类、享元模式的基础
  • 可返回子类型：隐藏实现类、API更紧凑，特别适合基于接口的框架
  • 根据参数返回不同子类型：如 EnumSet 根据枚举大小返回 RegularEnumSet/JumboEnumSet
  • 编写时返回类型可不存在：是 JDBC 等服务提供者框架的基础，可使用 java.util.ServiceLoader
  • 缺点：没有公开构造方法的类无法被继承；难以在 API 文档中查找，需遵守 from/of/valueOf/instance/getInstance 等命名规范
public static Boolean valueOf(boolean b) {
    return b ? Boolean.TRUE : Boolean.FALSE;
}
默认优先选择静态工厂方法，再考虑公共构造方法。
第 2 条

当构造方法参数过多时使用builder模式

💬 当构造方法参数过多时，使用 Builder 模式解决伸缩构造方法与 JavaBeans 模式的问题。
  • 伸缩构造方法：参数过多时难用、易出错、相同类型参数顺序易混
  • JavaBeans 模式：无参构造 + setter，无法保证不可变性、可能处于不一致状态
  • Builder 模式：用链式 setter 构建不可变对象，代码清晰且线程安全
  • 层级 Builder：子类的 builder 模拟自限定型（self-typed）方法
  • 优点：比构造方法更易扩展参数、利于阅读、可保证状态一致性、支持泛型与可变参数
NutritionFacts cocaCola = new NutritionFacts.Builder(240, 8)
    .calories(100).sodium(35).carbohydrate(27).build();
参数 ≥ 4 个或将来可能扩展时，Builder 模式是最佳选择。
第 3 条

使用私有构造方法或枚类实现Singleton属性

💬 实现 Singleton 属性的三种方法及其序列化问题。
  • 方法一：公有静态 final 字段，简单、可序列化（在 JDK 1.5 之前是最佳方法）
  • 方法二：静态工厂方法，可灵活改为泛型、改变 API（如 ThreadPoolExector 的方法）
  • 方法三：单元素枚举类型，最佳方法 — 自动支持序列化机制、防止多次实例化
  • 序列化陷阱：实现 Serializable 的单例必须实现 readResolve 方法，否则会创建新实例
public enum Elvis {
    INSTANCE;
    public void leaveTheBuilding() { ... }
}
单元素枚举是实现 Singleton 的最佳方式，简洁、免费提供序列化、线程安全。
第 4 条

使用私有构造方法执行非实例化

💬 通过私有构造方法实现非实例化来阻止类被创建实例。
  • 用途：工具类（如 java.lang.Math、java.util.Arrays）不希望被实例化
  • 做法：显式声明私有构造方法并抛出 AssertionError
  • 好处：显式表达意图；防止类被意外实例化；继承时子类不会意外获得公共构造方法
public class UtilityClass {
    private UtilityClass() {
        throw new AssertionError();
    }
}
工具类应显式声明私有构造方法以禁止实例化。
第 5 条

依赖注入优于硬连接资源(hardwiring resources)

💬 依赖注入优于硬连接资源（hardwiring resources），提高可测试性和灵活性。
  • 反模式：静态工具类或单例依赖底层资源（如拼写检查器使用静态字典）
  • 正确做法：通过构造方法或 setter 注入资源（Dependency Injection）
  • 优点：提高灵活性、可测试性、可复用性
  • 常见形式：构造方法注入、Spring 框架、Guice、Java EE 容器等
public class SpellChecker {
    private final Lexicon dictionary;
    public SpellChecker(Lexicon dictionary) {
        this.dictionary = Objects.requireNonNull(dictionary);
    }
}
类不应直接 new 资源对象，应通过依赖注入获取。
第 6 条

避免创建不必要的对象

💬 避免创建不必要的对象，特别是不可变对象和适配器。
  • 重用不可变对象：String s = "bikini"; 而不是 new String("bikini")
  • 静态工厂方法：Boolean.valueOf(String) 优于构造方法
  • 适配器模式：Map.keySet() 每次返回同一 Set 视图
  • 装箱陷阱：避免无意中的自动装箱（long sum 与 Long sum 性能差异巨大）
  • 不要误用：池化对象在现代 JVM 上成本可能高于直接创建小对象
// 反例：每次都创建相同实例
String s = new String("bikini");
// 正例：复用
String s = "bikini";
能重用的对象就不要新建；注意自动装箱的隐藏成本。
第 7 条

消除过期的对象引用

💬 消除过期的对象引用以避免内存泄漏。
  • 常见场景：数组实现的栈/队列/缓存 — 弹出元素后应将引用置 null
  • 缓存：使用 WeakHashMap 或定时清理
  • 监听器/回调：只注册必要的回调，并及时注销
  • 内存泄漏的征兆：OutOfMemoryError 异常或 heap dump 异常
public Object pop() {
    if (size == 0) throw new EmptyStackException();
    Object result = elements[--size];
    elements[size] = null; // 消除过期引用
    return result;
}
只要类自己管理内存，就要警惕内存泄漏。
第 8 条

避免使用Finalizer和Cleaner机制

💬 避免使用 Finalizer 和 Cleaner 机制，二者都不能保证及时执行且已被废弃。
  • Finalizer：不可预测、危险、严重性能损失（JDK 9 起已弃用）
  • Cleaner：比 Finalizer 稍好，但仍不可控，不能保证及时执行
  • 替代方案：实现 AutoCloseable，配合 try-with-resources
  • 唯一合法用途：作为 native peer 的安全网或终止关键本地资源（仍需提供 close 方法）
try (CleanableResource res = new CleanableResource()) {
    // 使用资源
} // 自动关闭
不要使用 Finalizer/Cleaner，请用 try-with-resources 和 AutoCloseable。
第 9 条

使用try-with-resources语句替代try-finally语句

💬 使用 try-with-resources 语句替代 try-finally，提高可读性和正确性。
  • try-finally 问题：多层嵌套时难以阅读；异常可能被屏蔽
  • try-with-resources：自动关闭多个资源，代码简洁、异常完整
  • 实现要求：资源必须实现 AutoCloseable 接口（其 close 方法可抛出 Exception）
  • catch 子句：可与 try-with-resources 结合使用，处理特定异常
try (BufferedReader br = new BufferedReader(new FileReader(path))) {
    return br.readLine();
}
处理必须关闭的资源时，try-with-resources 永远优于 try-finally。

讨论equals、hashCode、toString等通用方法

📋 共 5 条
第 10 条

重写equals方法时遵守通用约定

💬 重写 equals 方法时遵守通用约定，避免破坏集合等依赖 equals 的逻辑。
  • 不需要重写的情况：每个实例本质唯一（如 Thread）；类是逻辑单例；父类已重写；私有类且只比较内存地址
  • equals 约定：自反性、对称性、传递性、一致性、非空性
  • 实现步骤：== 检查、instanceof 检查、强转、关键字段比较
  • 使用 Objects.equals 简化比较
@Override public boolean equals(Object o) {
    if (o == this) return true;
    if (!(o instanceof PhoneNumber)) return false;
    PhoneNumber pn = (PhoneNumber) o;
    return pn.lineNum == lineNum && pn.prefix == prefix;
}
重写 equals 必须严格遵守五大约定，否则 HashMap/HashSet 等行为会出错。
第 11 条

重写equals方法时同时也要重写hashcode方法

💬 重写 equals 时必须同时重写 hashCode，违反会导致 HashMap/HashSet 行为异常。
  • 约定：相等的对象必须有相等的散列码（equals 相等 → hashCode 相等）
  • 实现思路：选择非零初始值，对关键字段计算 c = 31 * c + (boolean ? 1 : 0) 等，累加后返回
  • 延迟初始化：缓存 hashCode 值（不可变类适用）
  • 不要试图排除关键字段（追求性能除外），不要用 getClass() 测试替代 instanceof
@Override public int hashCode() {
    int result = Short.hashCode(areaCode);
    result = 31 * result + Short.hashCode(prefix);
    result = 31 * result + Short.hashCode(lineNum);
    return result;
}
equals 与 hashCode 必须同时重写，否则 HashMap 等集合会出现严重 bug。
第 12 条

始终重写 toString 方法

💬 始终重写 toString 方法，提供清晰有用的对象表示。
  • 约定：简洁、易读、包含对象所有感兴趣的信息
  • 格式：是否在文档中指定格式需谨慎权衡（影响灵活性和价值）
  • 提供静态工厂或构造方法：方便从 toString 重建对象
  • 建议：无论是否指定格式，文档中应清晰说明意图
@Override public String toString() {
    return String.format("PhoneNumber(%03d) %03d-%04d",
        areaCode, prefix, lineNum);
}
toString 是对象的"名片"，务必清晰、包含关键信息。
第 13 条

谨慎地重写 clone 方法

💬 谨慎地重写 clone 方法，因为其机制复杂且与正常构造方法冲突。
  • Cloneable 接口：marker interface，规定 clone 应返回字段拷贝
  • 问题：构造方法不会执行、约定薄弱、与 final 字段冲突、抛出受检异常
  • 替代方案：优先使用拷贝构造方法或拷贝工厂（如 new MyClass(original)）
  • 何时实现 Cloneable：仅当类设计上主要为了继承且受限于 final 字段时考虑数组复制
public MyClass(MyClass original) {
    this.data = original.data; // 深拷贝
}
不要使用 Cloneable，应提供拷贝构造方法或拷贝工厂。
第 14 条

考虑实现Comparable接口

💬 考虑实现 Comparable 接口，让对象支持自然排序。
  • 优势：享受 Arrays.sort、TreeMap、TreeSet、Collections.sort 等排序能力
  • 约定：确保 sgn(x.compareTo(y)) == -sgn(y.compareTo(x))；传递性；x.compareTo(y) == 0 ⇔ x.equals(y)（建议）
  • 实现技巧：比较关键字段，使用 Comparator 工具方法简化（comparingInt、thenComparingInt）
  • 新旧 API：Java 8+ 优先用 Comparator 链式 API
private static final Comparator<PhoneNumber> COMPARATOR =
    Comparator.comparingInt((PhoneNumber pn) -> pn.areaCode)
        .thenComparingInt(pn -> pn.prefix)
        .thenComparingInt(pn -> pn.lineNum);
实现 value class 时让其实现 Comparable，便于排序与集合管理。

第 15 条

使类和成员的可访问性最小化

💬 使类和成员的可访问性最小化，良好的封装是软件设计的基础。
  • 访问级别：private（仅本类）→ package-private（默认）→ protected（子类）→ public（全部）
  • 原则：尽可能使每个类或成员不被外界访问
  • 实例字段：绝不能是 public（非 final 会失去线程安全；final 限制灵活性）
  • 静态 final 字段：可以暴露但要注意其引用对象的可变性（如 public static final Thing[] 是危险的）
  • 模块化（Java 9+）：模块提供了超出包级别的封装机制
public class Access {
    public static final int VALUE = 10;          // OK
    public static final Thing[] VALUES = {...}; // 危险
    private int x;                              // 默认 private
}
API 越小越好，越小越易维护。
第 16 条

在公共类中使用访问方法而不是公共属性

💬 在公共类中使用访问方法（getter）而不是公共属性。
  • 理由：保留改变内部表示的灵活性；可在访问方法中执行同步、校验、通知等操作
  • public 字段的缺点：无法改变数据表示；无法在访问时执行额外操作；破坏封装
  • 例外：package-private 或 private 嵌套类可直接暴露字段
public class Point {
    private double x;
    private double y;
    public Point(double x, double y) { this.x = x; this.y = y; }
    public double getX() { return x; }
    public double getY() { return y; }
}
公共类应使用 private 字段 + 公共访问方法，保持封装性。
第 17 条

最小化可变性

💬 最小化可变性，让类成为不可变类是最简单也最安全的设计。
  • 五大规则：不提供修改对象状态的方法；类不能被继承；所有字段 final；所有字段 private；防御性拷贝可变组件
  • 优点：线程安全、可共享、可作为 Map key 或 Set 元素、可安全共享内部信息
  • 缺点：每个不同的值都需要一个对象；可能带来性能问题
  • 折中方案：让类不可继承、构造方法私有，提供静态工厂；或考虑 builder 模式
public final class Complex {
    private final double re, im;
    public Complex(double re, double im) { this.re = re; this.im = im; }
    public Complex plus(Complex c) { return new Complex(re + c.re, im + c.im); }
}
类应尽量不可变，String、基本类型包装类都是优秀范例。
第 18 条

组合优于继承

💬 组合优于继承，打破继承的滥用局面。
  • 继承的危险：子类继承父类所有 API 细节，父类修改会破坏子类；跨包继承尤其危险
  • 包装类模式：通过组合 + 接口转发实现代码复用（装饰器模式）
  • 何时使用继承：当子类和父类之间存在真正的 is-a 关系，且在同一包内、专为继承设计时
  • 包装类的代价：不适合 callback 框架；影响性能（极少）
// 包装类 - 优于继承
public class InstrumentedSet<E> extends ForwardingSet<E> {
    private int addCount = 0;
    @Override public boolean add(E e) { addCount++; return super.add(e); }
}
能用组合就用组合，继承仅在 is-a 关系明确时使用。
第 19 条

要么设计继承并提供文档说明，要么禁用继承

💬 要么为继承而设计并提供文档说明，要么禁用继承。
  • 关键：文档必须说明可重写方法的实现细节与自用模式
  • 构造方法中：不要调用可重写方法（会导致子类字段未初始化即被使用）
  • Cloneable 和 Serializable：实现时要特别小心，因为 clone/readObject 行为类似构造方法
  • 禁用继承两种方式：类声明为 final；构造方法私有 + 静态工厂
// 禁用继承
public final class FinalClass { ... }
// 或：私有构造方法 + 静态工厂
专为继承设计的类需要投入大量设计成本，否则应禁用继承。
第 20 条

接口优于抽象类

💬 接口优于抽象类，Java 只支持单继承但可实现多个接口。
  • 接口优势：现有类可轻松实现新接口；可使用 mixin（混合类型）
  • 抽象骨架类：配合接口使用（AbstractList、AbstractSet、AbstractMap），提供部分实现
  • Java 8+：接口支持默认方法，但仍有局限（不能引用字段、Object 方法不能默认等）
  • 设计 API：先定义接口，再考虑是否需要抽象骨架类
public interface List<E> {
    boolean add(E e);
    default void shuffle() { /* 默认实现 */ }
}

为后代设计接口

💬 为后代设计接口，默认方法可能打破现有实现的契约。
  • 默认方法风险：在已有实现类上注入方法可能引起编译错误或行为变化
  • 设计原则：默认方法应谨慎设计，避免依赖未知的状态；尽量提供完整文档
  • 不可移除：默认方法无法从接口中移除（兼容性问题）
  • Java 8 教训：Collections 接口添加的 default 方法在 Servlet 容器等场景下导致二进制兼容问题
default boolean removeIf(Predicate<? super E> filter) {
    boolean result = false;
    for (Iterator<E> it = iterator(); it.hasNext(); )
        if (filter.test(it.next())) { it.remove(); result = true; }
    return result;
}
默认方法让添加 API 更简单，但每个方法都应被精心设计。

接口仅用来定义类型

// 正确做法

支持使用静态成员类而不是非静态类

💬 支持使用静态成员类而不是非静态类，节省内存。

// 静态成员类 - 更好
public static class MyStaticNested { ... }

第 26 条

不要使用原始类型

💬 不要使用原始类型，泛型带来类型安全和更好的可读性。
  • 原始类型 vs 参数化类型：List vs List<String>，前者绕过类型检查
  • 安全性：参数化类型在编译期检查类型，运行时无需强制转换
  • Set<Object> 与 Set<?> 的区别：Object 可放入任意类型；? 表示未知类型，不能添加
  • List 与 List<Object> 的区别：后者可放任意类型；List<String> 不可赋给前者
// 错误
List list = new ArrayList();
// 正确
List<String> list = new ArrayList<>();
永远不要在代码中使用原始类型，否则失去泛型的所有好处。
第 27 条

消除非检查警告

💬 消除非检查警告，反映代码的真实问题。
  • 原则：每条非检查警告都代表潜在的运行时 ClassCastException
  • 消除方法：完善类型参数；用 @SuppressWarnings("unchecked") 但需评论说明原因
  • 作用域最小化：@SuppressWarnings 尽量放在最小作用域（如局部变量），不要放在整个类上
  • 重新启用：当 @SuppressWarnings 应用范围扩大时记得添加 @SuppressWarnings("unchecked")
@SuppressWarnings("unchecked") // 由 List<String>.toArray 决定
public <T> T[] toArray(T[] a) { ... }
非检查警告不可忽视，逐一消除。
第 28 条

列表优于数组

💬 列表优于数组，泛型在编译期、数组在运行时体现类型差异。
  • 数组协变：Long[] 是 Object[] 的子类，可能导致运行时 ArrayStoreException
  • 泛型不可变：List<Long> 与 List<Object> 无关系，编译期保证类型安全
  • 数组 vs List：性能敏感且明确知道不存在泛型擦除相关问题时才用数组
  • 混合使用：用 List 替代数组，必要时将 List 转为数组
// 不安全
Object[] arr = new Long[1];
arr[0] = "string"; // ArrayStoreException
// 安全
List<Long> list = new ArrayList<>();
新代码优先使用 List，避免数组与泛型混用。
第 29 条

优先考虑泛型

💬 优先考虑泛型，让类支持类型参数化。
  • 基础步骤：将普通类改造为泛型类，移除 Object 类型和强制转换
  • 迭代演进：从支持 Object 的类逐步重构为泛型类
  • 类型擦除：泛型信息仅存在于编译期，运行时擦除
  • 限制：无法创建泛型数组；不能实例化类型参数（new T()）
public class Stack<E> {
    private E[] elements;
    public E pop() { /* ... */ }
}
新代码应直接使用泛型，老代码应演进为泛型。
第 30 条

优先使用泛型方法

💬 优先使用泛型方法，使 API 更加类型安全。
  • 静态工具方法：特别适合泛型化（如 Collections.emptyList()）
  • 类型推导：Java 7+ 的菱形语法 <T> T reduce(...)，更简洁
  • 递归类型限制：<T extends Comparable<T>> T max(T... args)
  • 泛型单例工厂：identityFunction() 返回 Function<T,T>，适用于所有 T
public static <E> Set<E> union(Set<? extends E> s1, Set<? extends E> s2) { ... }
静态工具方法几乎都应该泛型化。
第 31 条

使用限定通配符来增加API的灵活性

💬 使用限定通配符来增加 API 的灵活性。
  • PECS 原则：Producer 用 extends（? extends T），Consumer 用 super（? super T）
  • 何时用 ? extends：从集合中读取 T 类型对象（生产者）
  • 何时用 ? super：向集合中写入 T 类型对象（消费者）
  • Comparable/Comparator：永远是 Consumer，用 ? super T
  • 类型推导：Java 8+ 大多数情况无需显式类型参数
public void pushAll(Iterable<? extends E> src) { ... }
public E reduce(List<? super E> list, Function<E, E> f, E initVal) { ... }
记住 PECS：频繁读取用 extends，写入用 super。
第 32 条

合理地结合泛型和可变参数

💬 合理地结合泛型和可变参数，谨慎处理数组创建。
  • 问题：泛型可变参数 T... 在 Java 中实际是 T[]，会创建泛型数组
  • 安全使用场景：@SafeVarargs 标注的纯转发方法（如 List.of、Collections.addAll）
  • 禁止使用：在泛型可变参数上存储到字段、返回给调用方
  • 替代方案：用 List<T> 替代 T...（如 Arrays.asList(T... a) → toList(T... a)）
@SafeVarargs
public static <T> List<T> toList(T... args) {
    return List.of(args);
}
@SafeVarargs 让可变参数泛型方法变得安全，但请确保方法确实安全。

优先考虑类型安全的异构容器

💬 优先考虑类型安全的异构容器，如 Typesafe-Heterogeneous-Container 模式。
  • 问题：单个对象的容器参数化（如 Set<T>）通常只支持固定数量的类型参数
  • 解决方案：用 Class<T> 作为 key 模拟不同类型，Map<Class<?>, Object> 存储
  • 实现要点：putFavor、favorites(Class<T> type) 配合 cast() 进行类型转换
  • 应用：JDK 中的 AnnotatedElement、Guice 的 TypeLiteral
public <T> void putFavorite(Class<T> type, T instance);

使用枚举类型替代整型常量

💬 使用枚举类型替代整型常量，枚举是更优雅的常量集合。
  • 优势：类型安全、命名空间隔离、可关联数据和行为
  • 枚举本质：枚举值本质是 public static final 字段，每个值都是枚举类的实例

public enum Operation {

使用实例属性替代序数

💬 使用实例属性替代序数，告别基于 ordinal() 的代码。
  • 反模式：用 ordinal() 作为数组索引、保存枚举状态信息
  • 问题：常量顺序改变导致行为变化；难以维护多个状态信息
  • 正确做法：用实例字段（int 或 EnumSet）保存所需信息

public enum Ensemble {

}

使用EnumSet替代位属性

  • 限制：不能创建不可变 EnumSet；无法在 Java 8 之前用 Collection 操作
  • 何时回退到位属性：用 long 位运算时（EnumSet 内部实现）

用 EnumSet 替代位标志，简洁安全且性能优异。

💬 使用 EnumMap 替代序数索引，类型安全的二维映射。
  • 反模式：用 ordinal() 作为数组索引（如 phases[Phase.ordinal()][Transition.ordinal()]）
  • 问题：类型不安全、性能不如 EnumMap、数组维度难理解
  • EnumMap 优势：用枚举作为 key，类型安全、内部用数组实现、性能极佳
  • 高级用法：嵌套 EnumMap（EnumMap<K, EnumMap<K, V>>）模拟多维数组

使用接口模拟可扩展的枚举

  • 解决方案：用接口 + 基础枚举实现，客户端编写操作接口的方法

  • 限制：实现无法继承基础枚举的状态字段
public interface Operation { double apply(double x, double y); }
public enum BasicOperation implements Operation { ... }
public enum ExtendedOperation implements Operation { ... }

注解优于命名模式

💬 注解优于命名模式，使用注解代替过期的前缀式约定。
  • 命名模式问题：拼写错误难发现、参数无关联、缺乏一致的命名规范

  • 设计原则：使用 @Retention(RetentionPolicy.RUNTIME) 才能运行时通过反射读取
  • 使用场景：JUnit (@Test)、Spring 框架的众多注解
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Test { }

始终使用Override注解

第 42 条

lambda表达式优于匿名类

💬 Lambda 表达式优于匿名类，让函数式编程更简洁。
  • Lambda 优势：简洁、可读性强、无类型膨胀
  • 适用场景：函数式接口（单抽象方法的接口）的实例创建
  • 限制：无法访问外部非 final 变量；不能有命名；this 指代外层
  • 匿名类适用：需要实现多个方法、需要访问构造方法、引用自身
// 匿名类
Collections.sort(words, new Comparator<String>() {
    public int compare(String s1, String s2) { return Integer.compare(s1.length(), s2.length()); }
});
// Lambda
Collections.sort(words, (s1, s2) -> Integer.compare(s1.length(), s2.length()));
函数式接口的实现一律用 Lambda。
第 43 条

方法引用优于lambda表达式

💬 方法引用优于 Lambda 表达式，更具表现力。
  • 五类方法引用： - 类::实例方法 (String::length) - 类::静态方法 (Math::max) - 实例::实例方法 (expensiveTransaction::getValue) - 类::new (TreeMap<K,V>::new) - 实例::new (MyClass::new)
  • 何时用 Lambda：方法引用过长、方法不存在、参数不直接映射
  • 经验：能用方法引用就用方法引用
map.merge(key, 1, Integer::sum); // 优于 (count, incr) -> count + incr
方法引用让代码如散文般自然。
第 44 条

优先使用标准的函数式接口

💬 优先使用标准的函数式接口，如 java.util.function 包中的接口。
  • 六大基本接口：Function、Consumer、Supplier、Predicate、UnaryOperator、BinaryOperator
  • 基本类型特化：IntFunction、LongToDoubleFunction 等避免装箱
  • 何时自定义接口：当有自己的契约或需要 default 方法时
  • @FunctionalInterface 注解：明确函数式接口意图
@FunctionalInterface
public interface MyFunc<T> {
    boolean test(T t);
    default MyFunc<T> negate() { return t -> !test(t); }
}
先看 java.util.function 是否满足需求，再考虑自定义。
第 45 条

明智审慎地使用Stream

💬 明智审慎地使用 Stream，stream 不是所有场景的银弹。
  • Stream 优点：表达力强、可读性高、易于并行化
  • Stream 缺点：难以调试、难以重用中间操作、某些场景性能不如普通循环
  • 何时不用：char 值处理（应使用 stream 之外的方式）；无法直接做 break/continue；复杂业务逻辑
  • 经验：以可读性为先，stream 和循环结合使用
// 适合 Stream
List<String> names = users.stream().map(User::getName).collect(toList());
// 不适合：复杂循环逻辑
Stream 是工具，不是教条。
第 46 条

优先考虑流中无副作用的函数

💬 优先考虑流中无副作用的函数，避免修改外部状态。
  • forEach 是报告式：应只用于打印等最终操作，不应用于计算
  • 收集器 Collectors：toList、toSet、toMap、joining、groupingBy、partitioningBy
  • 避免陷阱：不要在 lambda 中修改外部可变对象（导致难以诊断的问题）
  • 收集器的强大：嵌套 groupingBy、mapping、reducing、teeing
Map<City, List<String>> byCity = people.stream()
    .collect(groupingBy(Person::getCity, mapping(Person::getLastName, toList())));
Stream 流水线要保持纯函数风格，副作用留给终止操作。
第 47 条

优先使用Collection而不是Stream来作为方法的返回类型

💬 优先使用 Collection 而不是 Stream 来作为方法的返回类型。
  • Collection 优势：支持 for-each 循环；支持 stream()；支持 size()；可同时满足多种需求
  • Stream 仅适合作返回值：如果只做 for-each 循环操作
  • 何时用 Stream：未来一定会做流处理；返回的是巨大序列（IntStream.range）
  • 性能：Collection 的 stream() 是廉价的，返回 iter 也很高效
// 优先
public List<Cheese> getCheeses() { return cheesesInStock; }
// 当需要延迟序列时
public Stream<Cheese> stream() { return cheesesInStock.stream(); }
让调用方决定何时用 stream、何时用循环。
第 48 条

谨慎使用流并行

💬 谨慎使用流并行，确保理解底层成本与正确性。
  • 适用场景：ArrayList、HashMap、数组；规模足够大（N >= 几十到几万）；计算密集
  • 不适用场景：limit、findFirst 等短路操作；iterators 慢；流水线大量 boxing
  • 正确性问题：共享可变状态、reduce/collect 操作的 combiner 必须正确
  • 性能陷阱：fork-join 池的线程调度开销可能超过并行收益
// 适合
long count = primes.parallelStream().filter(p -> p > 1_000_000).count();
// 危险：自定义 reduce 需仔细编写
并行前要测量，并行后要验证。

检查参数有效性

💬 检查参数有效性，越早失败越好。

  • 做法：方法开头检查参数，使用 Objects.requireNonNull、checkFromToIndex 等

public Period(Date start, Date end) {

    this.end = Objects.requireNonNull(end, "end");
    if (start.compareTo(end) > 0) throw new IllegalArgumentException();
}

}

优先选择 Java 序列化的替代方案

💬 优先选择 Java 序列化的替代方案，反序列化是巨大的攻击面。

非常谨慎地实现 Serializable

💬 非常谨慎地实现 Serializable，实现成本远高于想象。
  • 代价： - 失去灵活性：内部表示变更会破坏序列化兼容 - 增加 bug 风险：构造方法不会执行、transient 字段处理 - 安全风险：反序列化攻击 - 测试成本：跨版本兼容性

public class Foo implements Serializable {
    private static final long serialVersionUID = 1L;

}

保护性的编写 readObject 方法

💬 保护性的编写 readObject 方法，避免反序列化的潜在风险。
  • 问题：readObject 行为类似构造方法但不调用构造方法
  • 关键：用 @throws 标注 readObject 抛出的异常；不变量在 readObject 结束时必须成立
  • 禁止：readObject 中调用可被重写的方法
  • 反序列化攻击：不可信数据 + 危险方法 = RCE，使用 ObjectInputFilter 防护

    s.defaultReadObject();
    // 验证不变量
    if (start.compareTo(end) > 0) throw new InvalidObjectException("...");
}

对于实例控制，枚举类型优于 readResolve

💬 对于实例控制，枚举类型优于 readResolve。
  • readResolve 作用：在反序列化后返回替代对象，实现 Singleton 持久性
  • 风险：所有实例字段都应是 transient；readResolve 本身需要实现；容易遗漏
  • 枚举优势：自动实现单例、线程安全、序列化机制由 JVM 保证

考虑用序列化代理代替序列化实例

💬 考虑用序列化代理代替序列化实例，保护不可变性并防止攻击。
  • 序列化代理模式：编写私有静态内部类（serialization proxy），仅保存对象逻辑状态
  • writeReplace：返回代理对象；readObject：调用代理的 readResolve 返回真实对象
  • 优势： - 防止伪造攻击 - 防止盗用构造函数 - 不必担心不变量与字段约束 - 与客户端扩展兼容
  • 代价：性能略低（多一次转换）
private static class SerializationProxy implements Serializable {
    private final Date start, end;
    SerializationProxy(Period p) { this.start = p.start; this.end = p.end; }
    private Object readResolve() { return new Period(start, end); }
}
private Object writeReplace() { return new SerializationProxy(this); }
需要实现 Serializable 时，序列化代理是最安全的方式。
