📖 前言

作者：霍丙乾

本书从异步程序的设计入手，探讨异步程序设计中要面对的关键问题，并在之后围绕这几个关键问题对Kotlin协程的设计实现展开探讨。

为什么要写这本书

作者作为国内较早接触Kotlin的开发者，在Google I/O 2017之后开始系统地写文章和视频教程，最终出版本书。Kotlin协程不像Python、JavaScript的async/await那样容易上手，官方文档过于精练，因此需要一本系统性的书籍。

读者对象

适用于有一定基础的Kotlin开发者，包括但不限于正在使用和希望使用Kotlin开发Android、Web服务、iOS、前端等应用的开发者。Kotlin初学者建议先阅读基础书如《Kotlin核心编程》。

本书特色

1. 紧紧抓住概念问题，从各个角度去阐释什么是协程；2. 用实际问题引入，逐步给出解决思路；3. 提供丰富的状态图、时序图帮助理解；4. 围绕关键问题（结果传递、异常处理、取消响应、复杂分支）展开探讨。

📕 第1章　异步程序设计介绍

Kotlin协程主要应用于构建各类异步程序模型，因此本章先从异步程序的构建和设计入手，探讨常见的异步程序设计思路和模型。

1.1 异步的概念

异步是相对于同步的执行方式。处理器逐条执行指令，但程序要描述复杂的业务逻辑时，多个事件可能并发作用于同一个结果。

1.1.1 程序的执行

处理器是大脑，程序执行是对指令的阅读理解。同步执行是按顺序执行，异步执行是非顺序执行。

1.1.2 异步与回调

异步通过回调实现。回调函数作为参数传递给异步函数，在异步操作完成时被调用。Java风格的回调如：fun asyncBitmap(url, onSuccess, onError)。

1.1.3 回调地狱

当回调嵌套多层时，代码会形成金字塔结构，可读性和可维护性急剧下降，这就是回调地狱（Callback Hell）。

1.2 异步程序设计的关键问题

与同步程序相比，异步程序的设计复杂度往往更高。需要解决四大关键问题：

1.2.1 结果传递

异步操作的结果如何从异步执行单元传递到调用方，是异步程序设计的首要问题。

1.2.2 异常处理

同步逻辑可以用try...catch直接捕获异常，但异步逻辑的异常处理不那么直接，需要通过回调（如onError）来处理。

1.2.3 取消响应

异步操作可能耗时较长，如何在用户取消请求时及时中断异步操作，是一个需要解决的问题。

1.2.4 复杂分支

多个异步操作之间存在依赖、分支、并行等复杂关系，如何简洁地表达这些逻辑是异步设计的挑战。

1.3 常见异步程序设计思路

业界针对异步程序设计提出了多种思路来解决这些关键问题。

1.3.1 Future

Future<T>是JDK 1.5引入的接口，它有一个get方法，能够同步阻塞地返回Future对应的异步任务的结果。fun bitmapFuture(url): Future<Bitmap>。

1.3.2 CompletableFuture

JDK 1.8引入CompletionStage，提供了thenApply、thenAccept、thenCompose等方法，可以链式地组合多个异步任务。

1.3.3 Promise与async/await

Promise是异步任务，存在挂起、完成、拒绝三个状态。JavaScript的Promise/A+规范定义了这一模型。async/await是基于Promise的语法糖。

1.3.4 响应式编程

响应式编程以数据流为中心，RxJava是典型代表。解决了异步编程中的回调地狱和复杂分支问题。

1.3.5 Kotlin协程

Kotlin协程是Kotlin官方推出的异步编程方案，结合了多种思路的优点，可以用顺序的代码风格编写异步逻辑。

1.4 本章小结

本章介绍了异步程序设计的核心问题，并对比了Future、CompletableFuture、Promise/async-await、响应式编程和Kotlin协程这五种异步程序设计思路。Kotlin协程作为后起之秀，吸收了其他方案的优点。

📕 第2章　协程的基本概念

Kotlin协程从1.1实验版到如今已经非常成熟，但大家对它的概念一直存在疑问。本章从基础概念入手，厘清协程的本质。

2.1 协程究竟是什么

业界对协程的概念一直没有清晰统一的界定。Lua之父Roberto Ierusalimschy在论文'Revisiting Coroutines'中提到，协程鲜见于早期语言实现，究其原因，部分即源于此。我们需要从不同角度去理解协程。

2.2 协程的分类

协程的主流实现虽然在细节上差异较大，但总体来讲仍然有章可循。

2.2.1 按调用栈分类

按调用栈分类：调用栈（CallStack）协程和无栈（Stackless）协程。有栈协程有独立的调用栈，无栈协程通过状态机实现。

2.2.2 按调度方式分类

按调度方式分类：对称协程（任意两个协程可以直接切换）和非对称协程（协程与调用者之间切换）。Kotlin协程属于非对称协程。

2.3 协程的实现举例

通过对比其他语言的协程实现，可以帮助我们理解协程的本质。

2.3.1 Python的Generator

Python的Generator（生成器）是最简单的协程实现之一。通过yield暂停执行，send()方法恢复执行并传入值。

2.3.2 Lua标准库的协程实现

Lua标准库提供了完整的协程API：create、resume、yield、status、wrap。Lua协程是对称协程的代表。

2.3.3 Go的go routine

Go语言的goroutine是轻量级线程，由Go运行时调度，配合channel实现协程间通信。

2.4 本章小结

协程没有统一定义，但可以从调用栈和调度方式两个维度来分类。理解其他语言的协程实现有助于理解Kotlin协程的设计。

📕 第3章　Kotlin协程的基础设施

本章介绍Kotlin协程的基础设施，包括协程的构造、函数的挂起、协程的上下文、协程的拦截器等核心概念。

3.1 协程的构造

要想进入协程的世界，首先需要做的就是构造出一个协程的实例。

3.1.1 协程的创建

Kotlin协程的创建需要Continuation、CoroutineContext和CoroutineStart三个要素。最底层API是createCoroutine和startCoroutine。

3.1.2 协程的启动

协程的启动通过startCoroutine传入的start参数控制，可分为DEFAULT、ATOMIC、UNDISPATCHED、LAZY四种启动模式。

3.1.3 协程体的Receiver

协程体是一个带接收者的lambda，可以访问receiver上的成员和方法。常见receiver类型有Continuation、CoroutineScope等。

3.1.4 可挂起的main函数

Kotlin 1.3引入suspend fun main()，允许在main函数中直接使用协程，无需显式创建协程。

3.2 函数的挂起

Kotlin协程的挂起和恢复能力本质上就是挂起函数的挂起和恢复。

3.2.1 挂起函数

用suspend关键字修饰的函数称为挂起函数。挂起函数只能在协程或其他挂起函数中调用。挂起函数可以像普通函数一样返回值。

3.2.2 挂起点

挂起函数被调用时，编译器会插入一个挂起点（suspension point），协程在此暂停执行，保存状态。挂起函数的执行结果通过Continuation传递。

3.2.3 CPS变换

CPS（Continuation-Passing Style，续体传递风格）是挂起函数的实现基础。编译器将挂起函数转换为接收Continuation作为参数的形式。

3.3 协程的上下文

Continuation除了可以通过恢复调用来控制执行流程的异步返回以外，还有一个重要的属性context，即协程的上下文。

3.3.1 协程上下文的集合特征

CoroutineContext本质是一个数据结构，类似Map，由多个Element组成，Key唯一标识，Value为Element实例。

3.3.2 协程上下文元素的实现

实现CoroutineContext.Element需要实现key和key对应的value。常见元素：Job、CoroutineDispatcher、CoroutineName、CoroutineExceptionHandler。

3.3.3 协程上下文的使用

协程上下文通过+操作符合并，相同Key的元素会被覆盖。可以使用minusKey移除元素，fold进行折叠。

3.4 协程的拦截器

协程如何处理线程的调度？标准库提供了拦截器（Interceptor）组件，允许我们拦截协程异步回调时的恢复调用。

3.4.1 拦截的位置

拦截器通过ContinuationInterceptor接口实现，拦截的是协程的恢复（resume）调用时机。

3.4.2 拦截器的使用

通过实现ContinuationInterceptor接口的interceptContinuation方法，可以对协程的resume调用进行拦截和包装。

3.4.3 拦截器的执行细节

interceptContinuation返回的Continuation会被用来替代原始的Continuation。resumeWith调用时，先经过拦截器处理再传递给原始Continuation。

3.5 Kotlin协程所属的类别

Kotlin协程从不同的角度看属于不同的类别。

3.5.1 调用栈的广义和狭义

广义的调用栈指整个调用关系链，狭义指操作系统线程的调用栈。Kotlin协程是无栈协程，但广义的调用栈很丰富。

3.5.2 调度关系的对立与统一

Kotlin协程是非对称协程，协程与调度器之间切换。dispatch/resume体现了调度关系的统一。

3.6 本章小结

本章详细介绍了Kotlin协程的基础设施：协程的构造、函数的挂起、协程上下文、协程拦截器。理解这些基础设施是深入学习Kotlin协程的关键。

📕 第4章　Kotlin协程的拓展实践

本章通过仿写其他语言的协程实现，深入理解Kotlin协程的设计思想。

4.1 序列生成器

序列生成器包含了'序列'和'生成器'两部分。本节通过仿写Python的Generator来熟悉简单协程的用法。

4.1.1 仿Python的Generator实现

基于Kotlin协程实现Python风格的Generator，通过yield暂停和返回值，支持惰性求值。

4.1.2 标准库的序列生成器介绍

Kotlin标准库提供了sequence和iterator的协程版本实现，sequence { yield(...) }即可创建惰性序列。

4.2 Promise模型

Promise模型是JavaScript异步编程的核心，本节通过Kotlin协程实现类似功能。

4.2.1 async/await与suspend的设计对比

async/await是JavaScript的语法，suspend是Kotlin的关键字。两者都能以同步风格写异步代码，但底层实现机制不同。

4.2.2 仿JavaScript的async/await实现

使用Kotlin协程实现async/await语义，包括Promise的三种状态（pending、fulfilled、rejected）和then/catch链。

4.3 Lua风格的协程API

Lua协程API是经典的对称协程API。

4.3.1 非对称API实现

非对称协程API：create、resume、yield。协程只能在协程体与调用者之间切换。

4.3.2 对称API实现

对称协程API：任意两个协程可以互相切换。通过统一的状态机和共享调度器实现。

4.4 再谈协程的概念

通过前面的实践，我们再回头来理解协程的概念。

4.4.1 简单协程与复合协程

简单协程：仅具备挂起/恢复能力的协程。复合协程：在简单协程基础上封装的状态机框架，具备启动、取消、异常处理等高级功能。

4.4.2 复合协程的实现模式

复合协程通常包含：Job（生命周期）、Dispatcher（线程调度）、Continuation（执行流）、CoroutineExceptionHandler（异常处理）。

4.5 本章小结

通过仿写Python Generator、JS async/await、Lua协程API，我们深入理解了Kotlin协程的底层机制，也理解了简单协程与复合协程的区别。

📕 第5章　Kotlin协程框架开发初探

本章仿照官方协程框架，从零开始实现一个迷你协程框架，帮助深入理解协程框架的设计与实现。

5.1 开胃菜：实现一个delay函数

delay函数的作用是让后面的代码延迟一段时间执行，但不应阻塞线程，应该是个挂起函数，指定时间后能恢复执行。suspend fun delay(time: Long, unit: TimeUnit = TimeUnit.MILLISECONDS)。

5.2 协程的描述

在协程框架中，需要一个数据结构来描述协程的状态。

5.2.1 协程的描述类

协程描述类通常包含：协程状态、Job引用、Continuation引用、上下文等字段。

5.2.2 协程的状态

协程状态通常包括：Active（活跃）、Completing（完成中）、Completed（已完成）、Cancelling（取消中）、Cancelled（已取消）。

5.2.3 支持回调的状态

协程状态需要支持回调通知。当状态发生变化时，通知等待该协程完成的调用者。

5.2.4 协程的初步实现

基于状态机实现协程的描述类，支持状态转换和回调通知。

5.3 协程的创建

仿照官方API实现launch和async。

5.3.1 无返回值的launch

launch(context, start, block)返回一个Job，启动一个不返回值的协程。

5.3.2 实现invokeOnCompletion

Job需要支持注册完成回调，invokeOnCompletion(handler)用于在协程完成时被调用。

5.3.3 实现join

join()是一个挂起函数，挂起当前协程直到目标协程完成。

5.3.4 有返回值的async

async(context, start, block)返回一个Deferred<T>，可通过await()获取结果。

5.4 协程的调度

协程如何在线程之间调度？需要设计调度器（Dispatcher）。

5.4.1 协程的执行调度

协程的执行调度通过拦截器实现。当协程恢复时，拦截器决定在哪个线程上执行resume。

5.4.2 协程的调度位置

调度发生在协程挂起和恢复时。挂起时记录恢复所需的调度器，恢复时调用调度器。

5.4.3 协程的调度器设计

调度器接口：dispatch(context, block)。需要实现将block调度到合适的线程上执行。

5.4.4 基于线程池的调度器

基于Java的Executor实现线程池调度器，如Dispatchers.IO。

5.4.5 基于UI事件循环的调度器

UI调度器基于UI线程的消息循环实现，如Android的Main dispatcher。

5.4.6 为协程添加默认调度器

通过CoroutineContext的继承机制，为子协程提供默认调度器。

5.5 协程的取消

协程的取消是协作式的，需要协程主动检查取消状态。

5.5.1 完善协程的取消逻辑

cancel()方法将协程状态置为Cancelling，递归取消子协程，最终状态变为Cancelled。

5.5.2 支持取消的挂起函数

挂起函数需要在挂起点检查取消状态，抛出CancellationException。

5.5.3 CancellableContinuation的实现

CancellableContinuation是支持取消的Continuation，持有Job引用，在Job取消时也会取消自己。

5.5.4 改造挂起函数

将挂起函数改造成使用CancellableContinuation，使其支持取消。

5.6 协程的异常处理

协程的异常处理需要区分未捕获异常和取消异常。

5.6.1 定义异常处理器

CoroutineExceptionHandler接口用于处理协程中的未捕获异常。

5.6.2 处理协程的未捕获异常

未捕获异常会传递给父协程的异常处理器，最终传递给根协程的处理器。

5.6.3 区别对待取消异常

CancellationException是协程取消的标志，不应该被当作错误处理，应该被静默吞掉。

5.6.4 异常处理器的运用

CoroutineExceptionHandler通常与SupervisorJob配合使用，避免单个子协程的异常影响兄弟协程。

5.7 协程的作用域

作用域（CoroutineScope）管理协程的生命周期。

5.7.1 作用域的概念

CoroutineScope持有CoroutineContext，提供launch、async等方法创建子协程。子协程继承父协程的上下文。

5.7.2 作用域的声明

通过CoroutineScope(context)函数创建作用域。常见的标准作用域有GlobalScope、MainScope等。

5.7.3 建立父子关系

作用域内创建的协程会自动成为该作用域的子协程。父协程等待所有子协程完成后才完成。

5.7.4 顶级作用域

GlobalScope是顶级作用域，协程的生命周期与应用程序一致，不受其他作用域管理。

5.7.5 协同作用域

coroutineScope { ... }创建的协同作用域，作用域内所有子协程完成后作用域才完成。

5.7.6 suspend fun main的作用域

suspend fun main运行在runBlocking创建的作用域中，主协程会等待所有子协程完成。

5.7.7 实现异常的传播

在协同作用域中，子协程的未捕获异常会传播给父协程，导致兄弟协程被取消。

5.7.8 主从作用域

supervisorScope创建主从作用域，子协程的异常不会影响兄弟协程。

5.7.9 完整的异常处理流程

完整的异常处理：子协程未捕获异常→传递给异常处理器→决定是否取消父协程。

5.7.10 父协程等待子协程完成

父协程在所有子协程完成后才完成，类似于Thread.join()的效果。

5.8 本章小结

本章从零实现了一个迷你协程框架，涵盖了协程的描述、创建、调度、取消、异常处理、作用域等核心功能。这为我们理解官方协程框架打下了坚实基础。

📕 第6章　Kotlin协程的官方框架

本章探讨官方协程框架的更多功能，并逐步尝试将协程运用于实际生产当中。

6.1 协程框架概述

官方协程框架提供了完整的协程编程模型。

6.1.1 框架的构成

官方框架由kotlinx-coroutines-core和kotlinx-coroutines-android等模块构成，提供了标准库、调度器、Flow、Channel等组件。

6.1.2 协程的启动模式

CoroutineStart枚举：DEFAULT（默认）、ATOMIC（原子）、UNDISPATCHED（不调度）、LAZY（懒启动）。

6.1.3 协程的调度器

Dispatchers定义：Main（UI线程）、IO（IO线程池）、Default（CPU密集型）、Unconfined（不限定）。

6.1.4 协程的全局异常处理器

通过ServiceLoader加载全局异常处理器，可用于统一处理未捕获异常。

6.1.5 协程的取消检查

ensureActive()用于检查协程是否被取消，yield()会检查并让出执行权。

6.1.6 协程的超时取消

withTimeout { ... }设置超时时间，超时后协程被取消。可通过withTimeoutOrNull返回null代替异常。

6.1.7 禁止取消

withContext(NonCancellable) { ... }内的代码不可被取消，用于必须执行的清理逻辑。

6.2 热数据通道Channel

Kotlin协程框架也提供了类似于Go routine的Channel。

6.2.1 认识Channel

Channel是一个面向多协程的数据传输通道，send发送数据，receive接收数据。Channel是热数据流。

6.2.2 Channel的容量

Channel可设置容量：RENDEZVOUS（0容量）、CONFLATED（1容量，最新）、BUFFERED（默认64）、UNLIMITED（无限）。

6.2.3 迭代Channel

可通过for (y in channel)迭代Channel，或使用consumeEach { ... }消费。

6.2.4 produce和actor

produce是协程构建器，返回ReceiveChannel；actor是协程构建器，返回SendChannel。

6.2.5 Channel的关闭

close()关闭Channel，接收方可以通过isClosedForReceive判断，for循环会自动结束。

6.2.6 BroadcastChannel

BroadcastChannel是广播式的Channel，所有订阅者都会收到相同的数据。

6.2.7 Channel版本的序列生成器

produce { ... }可以看作协程版的序列生成器，按需产出数据。

6.2.8 Channel的内部结构

Channel内部使用链表或数组实现，send/remove是线程安全的。

6.3 冷数据流Flow

随着RxJava的流行，响应式编程模型逐步深入人心。Flow就是Kotlin协程与响应式编程模型结合的产物。

6.3.1 认识Flow

Flow是Kotlin协程的冷流API，只有在被collect时才会发射数据。Flow { emit(value) }创建。

6.3.2 对比RxJava的线程切换

Flow通过flowOn(Dispatcher)切换上游线程，比RxJava的subscribeOn/observeOn更直观。

6.3.3 冷数据流

Flow是冷流：每个collector都会触发一次完整的收集过程。channelFlow提供热流语义。

6.3.4 异常处理

Flow使用catch { }捕获上游异常，onCompletion { }无论成功失败都执行。

6.3.5 末端操作符

末端操作符：collect、toList、first、single、reduce、fold、launchIn等。

6.3.6 分离Flow的消费和触发

通过SharedFlow或StateFlow可以将冷流转为热流。stateIn将Flow转为StateFlow。

6.3.7 Flow的取消

Flow的收集在协程取消时自动取消。cancel()会取消正在进行的收集。

6.3.8 其他Flow的创建方式

flowOf、asFlow、channelFlow、callbackFlow等创建Flow的多种方式。

6.3.9 Flow的背压

Flow通过buffer()、conflate()、sample()等操作符处理背压问题。

6.3.10 Flow的变换

中间操作符：map、filter、transform、take、drop、zip、combine、merge等。

6.4 多路复用select

select可以同时等待多个挂起函数的结果。

6.4.1 复用多个await

select { deferred1.await() ... deferred2.await() }，谁先完成就执行对应的分支。

6.4.2 复用多个Channel

select { channel1.onReceive { } ... channel2.onReceive { } }等待多个Channel的接收。

6.4.3 SelectClause

通过实现SelectClauseN接口，可以让自己的挂起函数支持select。

6.4.4 使用Flow实现多路复用

merge操作符可以合并多个Flow，模拟多路复用效果。

6.5 并发安全

协程中的并发安全与线程类似，需要使用同步工具。

6.5.1 不安全的并发访问

多个协程同时修改共享变量会导致数据竞争。@Volatile、synchronized、ReentrantLock等工具可解决。

6.5.2 协程的并发工具

协程特有工具：Mutex（互斥锁）、Semaphore（信号量）、Channel（通道通信）。

6.5.3 避免访问外部可变状态

最佳实践是避免共享状态，通过消息传递（Channel）和不可变数据实现协程间通信。

6.6 本章小结

本章介绍了官方协程框架的核心组件：Dispatchers、Job、Deferred、Channel、Flow、select、并发工具。这些组件构成了完整的协程编程模型。

📕 第7章　Kotlin协程在Android上的应用

本章介绍Kotlin协程在Android开发中的应用。

7.1 Android上的异步问题

Android开发中异步处理一直是个难题。

7.1.1 基于UI的异步问题分析

Android是单线程UI模型，所有UI操作必须在主线程。耗时操作需要放到子线程，切换线程繁琐。

7.1.2 '鸡肋'的AsyncTask

AsyncTask是早期Android提供的异步API，但内存泄漏、生命周期管理等问题使其'鸡肋'。

7.1.3 '烫手'的回调

纯回调方式虽然灵活，但回调地狱和生命周期管理让人头疼。

7.1.4 '救世'的RxJava

RxJava通过响应式编程模型解决了大部分问题，但学习曲线陡峭，配置繁琐。

7.2 协程对UI的支持

Kotlin协程天然适合Android的UI编程模型。

7.2.1 UI调度器

Dispatchers.Main是UI调度器。launch(Dispatchers.Main) { ... }可直接在UI线程启动协程。

7.2.2 协程版AutoDispose

通过LifecycleScope和viewModelScope自动管理协程生命周期，无需AutoDispose。

7.2.3 Lifecycle的协程支持

Lifecycle 2.2+提供lifecycleScope、repeatOnLifecycle等API，自动响应生命周期变化。

7.3 常见框架的协程扩展

主流Android框架都提供了协程支持。

7.3.1 RxJava的扩展

kotlinx-coroutines-rx2模块提供RxJava与Flow/Deferred的互转。

7.3.2 异步组件ListenableFuture

kotlinx-coroutines-guava模块支持ListenableFuture与协程的互转。await()获取结果。

7.3.3 ORM框架Room

Room 2.1+原生支持协程，DAO方法可以返回suspend函数或Flow。

7.3.4 图片加载框架coil

coil是协程版的图片加载库，ImageView.load(url) { ... }即可加载图片。

7.3.5 网络框架Retrofit

Retrofit 2.6+支持suspend函数作为接口方法定义，自动处理协程。

7.3.6 协程风格的对话框

可以封装suspend函数让AlertDialog的使用更协程化。

7.4 本章小结

Kotlin协程为Android开发带来了一场变革，简化了异步编程模型，配合主流框架可以写出简洁优雅的代码。
